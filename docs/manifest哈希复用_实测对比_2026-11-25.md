# manifest 步哈希复用：实测对比（2026-11-25）

## 改了什么

- 新增 `src/data/hash_cache.py::FactsCache`：把每个文件的 `bytes` / `sha256` / `rows` /
  `columns` 连同当时的 `st_size` 与 `st_mtime_ns` 存到
  `work/cache/manifest_facts.json`（`work/` 已 gitignore）。
- `src/data/manifest_refresh.py::file_facts(path, cache=None)` 支持按
  `(path, size, mtime_ns)` 三项全一致复用；`refresh_manifest_files(..., facts_cache=)` 透传。
- `tools/daily_update.py::_step_manifest` 一条缓存贯穿「manifest 回写 → 逐件对账 → 摘要
  digest」三次取事实：同一文件一轮只算一次 hash/行数；`cache.save()` 落盘供下一轮复用。
- 强制全量重算开关：`--manifest-full-hash` 或 `QUANT_MANIFEST_FULL_HASH=1`
  （跳过读取、全部重算并回刷缓存）。

## 门禁判据未放宽

- 变更集仍由 `_walk` 按「mtime > 开工标记」判定，逻辑一字未动。
- 逐件对账仍按 `rows` / `bytes` / `sha256` 与 manifest 登记值比对；预期外改动、未登记、
  汇总对账三条判据均未改动。缓存只复用「同一文件的事实怎么取」。
- 复用要求 `size` 与 `mtime_ns` **同时**精确相等；任一项不同即丢弃旧值重算。
- 路径消失不会命中：读不到即 `FileNotFoundError`，不会拿旧值顶替。
- 已知边界：文件内容变化但 size 与 mtime 都被外部还原成原值时，会复用旧 hash；这正是
  `--manifest-full-hash` 的兜底场景。

## 实测（只读基准，`work/bench_manifest_hash.py`）

同一份真实 store（22715 件 / 2.92GB），模拟「该步」的 walk → 逐件 `file_facts` → 摘要
digest（不写 manifest、不动 `data/`）。时间窗取最近 30h（命中上一轮日更重写面），
变更集 19253 件：

| 轮次 | walk | 逐件事实 | digest | 合计 | sha256 计算次数 | 缓存命中 |
|---|---|---|---|---|---|---|
| 冷（缓存空） | 5.67s | 91.73s | 28.91s | **126.36s** | **19253** | 0 |
| 热（同一份数据） | 6.72s | 23.88s | 31.71s | **62.36s** | **0** | 38506 |

- 热跑省 64.0s（50.7%），逐个 sha256 计算次数从 19253 → 0。
- 全树模式（marker=0，22715 件）冷跑超过 4 分钟未完成，已终止；说明冷跑成本主要在
  逐件 sha256 + parquet 行数，而这部分在热跑里为 0。
- 本轮改动后单步仍有三处取事实（回写/对账/digest），但同一文件只算一次，后两处命中缓存。
  剩余耗时集中在 manifest JSON 定位与写盘，本次未改、也不在优化范围内。

原始结果：`work/cache/bench_manifest_result.json`（window 段）；基准脚本：
`work/bench_manifest_hash.py`。
