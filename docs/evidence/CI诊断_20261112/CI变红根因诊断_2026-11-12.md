## 2. 失败 1~6：`EligibilityEngine._pseudo_ordinals` 类级默认值写错（① 代码回归）

### 2.1 触发链

`tests/test_clean_set.py` 的 `make_engine()`（L81-L95）用 `object.__new__(EligibilityEngine)` 手工组装引擎，**不跑 `__init__`**，只逐项赋它需要的属性；`_pseudo_ordinals` 不在其中。

于是 `engine.eligible()` 走到 L1217：

```python
if info.data_type == 'fund' and o in self._pseudo_ordinals.get(info.ts_code, ()):
```

实例上没有该属性 → 回落类属性 → 类属性是：

```python
_pseudo_ordinals: dict[str, frozenset[int]] = field(default_factory=dict)   # clean_set.py:453
```

`EligibilityEngine` **没有 `@dataclass` 装饰器**（AST 核查：`CodeInfo decorators=['dataclass']`，`EligibilityEngine decorators=[]`），所以 `field(...)` 不会被 dataclass 机制消费，类属性原样保留为 `dataclasses.Field` 对象 → `'Field' object has no attribute 'get'`。

### 2.2 归属与引入版本

```text
git blame -L 445,457 -- src/data/quality/clean_set.py
707ad7b (th19xcf 2026-11-12 450-453)   _pseudo_ordinals ... = field(default_factory=dict)
```

由 `707ad7b`（`clean_set` 准入加 `structural_pseudo_quote_row`）引入。该行的注释自述用途是「手工组装引擎（测试）时的默认值，避免未跑 `__init__` 的属性缺失」——意图正确，写法在非 dataclass 类上无效，**自述目的完全没达成**。

### 2.3 判定：是「用例期望该更新」还是「门控误伤」

**都不是**，是代码写错。判据（实测，可复算）：运行时只把类默认临时改为 `{}`（不改任何文件），再跑：

```powershell
@'
import pytest
from src.data.quality.clean_set import EligibilityEngine
EligibilityEngine._pseudo_ordinals = {}
raise SystemExit(pytest.main(['tests/test_clean_set.py','-q','--no-header','-p','no:cacheprovider']))
'@ | .venv\Scripts\python.exe -
```

结果：`36 passed`。即 6 条用例的期望值在「门控默认空」下全部成立，**门控没有误伤任何既有语义**，只是类默认值取不到。

### 2.4 为什么 CI 必红、生产却正常

- CI / 单测：手工组装 → 必须依赖类级默认值 → 必炸，且不依赖 `data/`，所以「无 data/ 的 CI 模拟」与「有 data/ + MySQL 的本地」两边同样失败。
- 生产：`__init__` 末尾必调 `_load_pseudo_gate()`（L507），三个分支（L915 / L921 / L931）都会**整体赋值** `self._pseudo_ordinals`，实例属性覆盖类属性，故线上不受影响。**这是测试可观测缺陷，不是线上数据错误。**

### 2.5 建议修法（改代码，不改测试）

首选（不可变空映射，避免共享可变默认）：

```python
# clean_set.py:453 附近
from types import MappingProxyType
_pseudo_ordinals: Mapping[str, frozenset[int]] = MappingProxyType({})
```

备选（最小改动，`_load_pseudo_gate` 三处都是整体赋值、无原地 mutate，实测全仓无 `_pseudo_ordinals[...] =` / `.update(` 写法）：

```python
_pseudo_ordinals: dict[str, frozenset[int]] = {}
```

**明确不采用**：在 6 条用例里补 `engine._pseudo_ordinals = {}`。那等于把缺陷固化进测试，下一处「手工组装引擎」还会再踩；且与类注释声明的设计意图相反。

**顺带加固（非本次失败原因）**：`gate_pseudo_rows` 同样只有 `__init__` 赋值（L480），类上无默认值；任何手工组装后调用 `_load_pseudo_gate()` 而未显式赋值的地方会以同样方式抛 AttributeError（`test_fund_price_basis.py::_bare_engine` 目前显式赋值，故未暴露）。建议同时补 `gate_pseudo_rows: bool = True`。

**改完后的验收**：`pytest tests/test_clean_set.py tests/test_fund_price_basis.py` 应为 6 条恢复通过、只剩第 7 条（依赖数据恢复）；`pytest tests/test_fund_price_basis.py` 应全绿（该文件 6 条 `_bare_engine` 用例走显式赋值，本来就不受影响）。

### 3.3 根因：派生刷新整体覆盖人工补登件

三条独立证据，均只读取得：

1. **磁盘件 = 纯派生重算结果，逐字节相同**。只读调用 `src.data.quality.anomaly_lists._build_placeholder_quote(Path('data/local_store'))` 得 257 行 / 234 只 / `full=true` 83 行，其 `write_csv(None)` 输出与磁盘 CSV 文本完全相同（`identical to live csv text: True`）。该函数只从 `quotes/fund/**` 按「`close==1.0 & volume==0 & amount==0` + 恒定价三段判据」推导，**原理上不可能产出 `nav_series`（上市前净值序列）与 `post_delist`（退市后结转）段**。
2. **manifest 与磁盘不符**。`data/local_store/meta/anomalies/manifest.json`（`generated_at=2026-11-12T20:29:45`）声明该件 `rows=476 / bytes=21424 / sha256=007B4BC1…`，磁盘实测 11,534 B / `AEB1C7F4…`；同目录 `fund_pseudo_registry.json` 的 sha 与 manifest 一致（大小写差异，实为同一个哈希）。
3. **时间线自证「覆盖发生在提交之后」**：JSON 写盘 `20:18:46`（`csv_rows=476, added_spans=130`）→ `8161c67` 提交 `20:24:46`（自述「CSV 346→476 行」）→ manifest 生成 `20:29:45` → 磁盘 CSV mtime **`20:39:59`**（sha 与 16:27 的 257 行旧件 `AEB1C7F4…` 完全相同）。即 20:39 有一次写盘把文件退回到 257 行状态。

**写入口**（写死 `data/local_store/meta/anomalies/placeholder_quote_codes.csv`，`_write_atomic` 整体覆盖、无保留逻辑）：
- `src/data/quality/anomaly_lists.py:288-294`（`refresh_anomaly_lists` → `_build_placeholder_quote`）
- 调用点：`src/data/local_store/build.py:1244`（`build` 末步，L1480/L1534/L1551 三处分支）、`src/data/services/local_store_daily_sync.py:114`（日报同步）
- 命令行：`tools/refresh_anomaly_lists.py`

因此这次覆盖极可能来自另一条任务触发的 `build` / `daily_sync` 末步，属**并发写正式数据的固有风险**，不是 `test_real_registry_spans` 的期望值问题。

### 3.4 附带发现（同源缺陷，建议一并处理）

`manifest.json` 把该 CSV 标为 `level: "A"`（A 级语义是「脚本可独立跑出与正式台账逐字段一致的结果，无需人工补充判断」）。事实上它现在含 130 段人工补登 + 101 段 `nav_series` 等不可派生内容，**级别标错**，也正是「A 级 = 可放心重生成」这一标注导致刷新链路敢整体覆盖。建议改 `level: "B"` 并写明不可重生成的原因。
