### 3.1 抽样方法

固定随机种子 `20261112`，三类分层各取：

- `delete` 5 条（全部 2026-11-10，覆盖不同 staging 目录）；
- 2026-11-05 早期 `create/update` 8 条（按日期分层）；

核验：按「仓库根 → `data/local_store` → `data/local_store/_staging`」三基准逐个 `isfile`，命中后计算磁盘 SHA256 并与记录比对；`delete` 行则核对「磁盘确无该文件」。

明细见同目录 [变更台账抽检_20条_2026-11-12.csv](./变更台账抽检_20条_2026-11-12.csv)（20 行，含 `字面三档`、`记录是否一致`、`命中基准`、磁盘字节与 SHA）。

### 3.2 三档计数

按用户要求的口径（字面「文件是否还在」）：

| 档位 | 条数 | 构成 |
|---|---|---|
| **能对上** | **7** | 全部为 2026-11-12 `update`，磁盘 SHA256 与记录**逐字节一致** |

- 当前 1.95 MB。三种增速情景（按行数×189.85 B 外推 365 天）：

### 4.3 作为「数据变更台账」的可用性

**结论：不能回答「某张正式表在某个时间点是什么值」。** 五条硬依据：

1. **无内容字段**：只有 `path/bytes/sha256/action`，没有行数、列名、schema 版本、任一单元格值。哈希无法反推内容。
2. **无哈希链**：`prev_sha256` 仅 130/10,278 = **1.27%** 有值（恰为 update 行），其余 98.73% 为空 → 无法证明「新版本由旧版本变成」。
3. **无生命周期**：10,278 行 = 10,278 个不同路径，**每个路径只出现 1 次**。同一文件被创建、改写、删除的过程无法在同表内串起来。
4. **路径不可直接定位**：3 套基准混用，需猜测式回退（§2.5）。
5. **漏记严重**：95.62% 的现存文件在记账后又被改写而无新记录（§3.4）。

它能可靠回答的只有一句：**「某路径在某一时刻被登记为 create/update/delete，当时字节数与 SHA256 是多少」**——即写时操作留痕，不是可按时间点取值的版本台账。若要回答「某表某时刻是什么值」，必须依赖内容快照（如 `_backup/<语义>_<日期>/` + 同目录 `manifest.json` 的口径哈希、行数、只数），本 CSV 替代不了。

## 5. 建议（只出方案，未执行）

### 5.1 结构最小修复（前向规范化，不改历史行）

| # | 问题 | 最小修复 | 回滚方式 |
|---|---|---|---|
| 1 | 路径基准混用 | 写端统一写**仓库相对路径 + 正斜杠**；如必须记 store 相对，新增 `path_base` 列（`repo`/`store`），并对历史无前缀行约定「无前缀 = store 相对」写入使用说明 | 只改建行代码，历史行不动；回滚 = 恢复旧写端代码，数据文件无需回滚 |
| 2 | `bytes=-1` | 写端对未知值写**空字段**而非 `-1`；解析端把空值当 `null` | 同上 |
| 3 | `move` 行 `sha256` 为空、`path` 存描述 | 要么禁止 `move` 走单行记账（拆成 `delete` + `create` 两行），要么新增 `dst_path` 列并允许 `move` 无单哈希 | 同上 |
| 4 | `action` 越界 | 写端枚举校验 `{create,update,delete}`（或显式扩到 `move` 并在文档登记） | 同上 |
| 5 | `operator` 两个叫法 | 归一为 `{system,agent}` | 同上 |
| 6 | CRLF/LF 混用 | 写端固定 `utf-8` + `newline='\n'` | 同上 |

- **写端加两道门槛**（这是根因，比修数据更重要）：① 写入前校验 `sha256` 为 64 位十六进制（`move` 除外，按 #3 处理）、`bytes` 为数字或空、`action` 在枚举内、`path` 为正斜杠相对路径；② 追加后校验「行数只增不减 + 末字节为换行」。
- 若确实要修正历史行（**非必需**）：先用 `copy2` 备份到 `_backup/data_changelog_<日期>.csv` 并记录新旧 SHA256，再用 `write_text_atomic` 原子替换；禁止先删后建。
- 现状证明写端仍缺校验：本次审计进行中（22:12:00）就新增了一条 `move` 行，同时违反 `sha256` 必填与 `path` 语义——**这是活证据，不是历史遗留**。

### 5.3 是否继续留在「不进 Git」

**建议维持现状（继续不进 Git）**，理由：

- 该文件 append-only、只增不减，每次提交会在 Git 历史里多存约 1.95 MB 快照，而历史版本几乎没有回溯价值（内容是新记录的前缀）；
- 移出跟踪的提交 `0ea36e9` 已把「单独点名纳入 G: 镜像」写进 `project_rules.md`，副本保障并未削弱。

但必须补两条，否则「不进 Git」会放大风险：

1. **收口单独核对**（沿用现有规则）：`SHA256 + 字节数 + 行数` 三项与 `G:` 比对，任一不等即判备份不完整。
2. **新增「只增不减 + 末行完整」校验**：行数单调不减、文件以换行结尾、末行可解析。因为并发追加是常态（本次 6 分钟 +4 行），读端必须能识别「读到写一半的行」。
3. 可选折中：若希望有 Git 留痕，只提交**已冻结的自然月归档片段**，活跃文件仍不入库——这样历史里不会出现同一文件的重复全量快照。
