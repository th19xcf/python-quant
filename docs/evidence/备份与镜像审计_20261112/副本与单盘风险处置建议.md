## 第三节 重复副本处置建议（只出建议，未删任何文件）

### 3.1 统计口径与差异说明

本次扫描按「同尺寸 → 逐文件 SHA256 全等」归组，覆盖 11 个根：`data/local_store`、`_backup`、`reports`、`backups`、`artifacts`、`research`、`2026-11-12`、`tmp`、`_staging`、`logs`、`E:\www\tmp`。

结果：**3,750 组 / 可省 8,564.1 MB**。清单侧给出的口径是 **1,129 组 / 8,107.1 MB**。

**口径分歧（不掩盖，也不为对齐而重算）**：

| 项 | 本次扫描 | 清单侧 |
|---|---|---|
| 筛选门槛 | **无体积下限**，任何尺寸的重复都计入 | 设了体积下限，**单组可省 < 1 MB 的不计入** |
| 组数 | 3,750 | 1,129 |
| 可省字节 | 8,564.1 MB | 8,107.1 MB |
| 差额 | — | 组数 2,621 组；字节 457 MB（**5.3%**） |

组数差 2.6 倍而字节只差 5.3%，本身就是门槛差异的直接证据：被多计进来的 2,621 组几乎全是小文件（典型如 `reports/data_audit_2026-11-07` 里同一份 1.9 MB 文件存 8 份），**组数多、体量小**。两个数都对，差别只在「算不算小重复」。

**哪个口径用于什么决策**（两个口径各自成立，不要互相替换）：

- **本次无门槛口径 → 用于「是否需要动」的判断**：它回答「全仓到底有多少个冗余副本」，是覆盖率与风险盘点的事实基础。组数多是事实，不是噪音——小重复虽不省空间，但会让「哪份是唯一被引用的」变模糊，属 DG-1 意义上的隐患。
- **清单侧带门槛口径 → 用于「清理能省多少」的执行排序**：清理动作有固定成本（逐组确认引用、确认可重建、留 SHA 证据），1 MB 以下的组做完这些动作净收益为负。要排清理优先级、估回收空间，用 1,129 组 / 8,107.1 MB 这一列。
- **两者共同的结论不变**：冗余集中在 `tmp` 与 `_backup` 的大文件，前 8 组占了可省体量的大头。

### 3.4 结论

- **可安全清理的实际规模远小于 8,564 MB**：B 类 786.2 MB + F 类 126.6 MB 属红线区，**必须保留**（合计 912.8 MB，占 10.7%）；A 类 399.5 MB 涉及外部目录，需你确认；真正可清的 D 类 2,216.4 MB + E 类 213.2 MB + C 类 377.0 MB ≈ **2,806.6 MB**，但 D 类在 `tmp/`（scratch，清不清无收益）、E 类在 `reports/`（需你点头）、C 类需逐任务确认已收口。
- **本轮不删任何重复副本**（已定，不是待办）：
  1. **B 类 786.2 MB 与 F 类 126.6 MB 是红线**：前者是 `_backup` 同一分钟两次快照，后者是正式层与快照层各一份。删任意一份都直接违反 DG-11 / DG-13，等于放弃该时点的回滚能力——这类「省空间」是以不可回滚为代价换来的，不划算。
  2. **C / D / E 三类合计只省 2,806.6 MB，却要逐组确认「删掉的那份不是唯一被引用份」**：本次归组只证明「内容相同」，没有证明「代码 / 配置 / 文档实际读的是哪一份」。在 `src/`、`tools/`、`config/` 里逐个反查消费点的工作量远大于 2.8 GB 的收益；且一旦误删唯一被引用份，破坏面是取数或回测直接断链，比省下的空间严重得多。
  3. **收益最大的 D 类落在 `tmp/`（scratch 层）**：删了不影响备份覆盖率、不影响任何结论，只影响回测重跑速度，属可做可不做的净收益极小项。
- **后续若要做，按此顺序**：先 E 类（`reports/**/work/` 中间件，有正式产物兜底）→ 再 `tmp/pytest_gates_full_stale_1109` 这类明确冗余 → 最后才考虑 C 类逐任务确认；B / F 类任何情况下都不动。
