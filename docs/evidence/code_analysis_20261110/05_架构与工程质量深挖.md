## 二、引擎与数据层的契约边界（换一套数据要改几处）

这是本次最能量的答案。

**引擎内核零文件依赖**（AST 实测）：`execution_core.py` / `base_engine.py` 无 `read_parquet`、无 `local_store`、无字面路径。唯一文件读在分红装载 `corporate_actions.py:246-268`，路径来自 `data/local_store/store.py:532`（`dividend_path`）。引擎入口是一个窄接口：

```
ExecutionCore.run(universe: Dict[str, pl.DataFrame], ...)      execution_core.py:833
BacktestEngine(..., dividends: pl.DataFrame | None)            backtest_engine.py:62,77
PortfolioBacktestEngine(..., dividends: ...)                   portfolio_backtest_engine.py:110,127
```

**换源成本量化**：

| 情形 | 需改处数 | 位置 |
|---|---|---|
| 引擎内核的文件读取 | **0 处** | 无任何路径常量 |
| 新源列名不同（如 `close_hfq` 而非 `close`） | **25 个引用点 / 15 个列名** | `execution_core` 20、`base_engine` 5、`corporate_actions` 2、`benchmark_eval` 4 |
| 新源缺 `raw_open/raw_close` | 1 处 + 口径退化 | `execution_core.py:1106-1107` 成对校验；缺失则成交/盯市退回 hfq 价 |
| 分红来源变化 | 2 处 | `corporate_actions.py:184-211` + 两个引擎构造签名 |
| **真正要改的装配层** | **5 处** | ①`data/managers/data_fetcher.py:673-729` ②`advice/data.py:72-108` ③`quant/factor_lib/data.py:114-122` ④`quant/learning/data.py:49-97` ⑤`core/usecases/run_backtest.py:345-380` |

**一句话结论**：引擎**本身是可换源的**（内核 0 处文件依赖，实际只改装配层 5 处），代价是它对 15 个列名、2 个「硬必需列」**零校验**——新源少一个 `close` 就在 `execution_core.py:928` 抛裸 `KeyError`；缺 `raw_open` 则**静默退回 hfq 价撮合**，净值照常好看。

## 八、先做哪三件（不是平行清单）

排序依据：**能在当前数据上复现的错误 > 会让错误静默的错误 > 只影响可维护性的问题**。

### 第一件：分红修正层贯通 + 缺列契约（6.1 + 6.2）

- **为什么是它**：这是全库唯一一个**既有书面事故记录、又能在当前 `stock_dividend.parquet` 上直接复现**的错误（601258.SH 权益虚增 56.416%）；而且生产端已经修好了，只差消费端。修它只需动 2 个文件 + 1 个共享断言函数 + 1 个测试文件。
- **动作**：①`corporate_actions._parse_frame` 改 `coalesce(fix, raw)` 并支持 `no_ex_rights`；②新增 `assert_div_columns(divs)` 放进 `src/data`，`adj_factor_calculator` 与 `corporate_actions` 共用；③缺 `*_fix` 列时 warning + `degraded=True` 透传到回测结果。
- **判据**：`tests/test_corporate_actions_fix_layer.py` 中断言 601258.SH `share_ratio==0.0 && cash_per_share==0.04`；去掉 `cash_div_fix` 调因子计算必须抛错（现状静默出结果）。
- **不做会怎样**：所有含这两只标的的回测净值都错，且因为曲线平滑、无异常，**错了不会被任何人发现**。

### 第二件：引擎输入契约（2.1 + 2.2 + 6.3/6.5/6.8 的"缺列必炸"统一）

- **为什么是它**：它决定「换一套数据要不要重写引擎」这个问题的答案能不能从「改 25 个列名、靠 `KeyError` 试错」降到「改 5 个装配点」。而且它同时覆盖 6.3/6.5/6.8 三条静默降级——都是同一类错误：**缺列 → 悄悄降级 → 结论偏移**。
- **动作**：①`_prepare_universe` 开头断言必需列（`close/date`）并抛带来源的 `SchemaError`；②`dividends` 参数从「物理表 DataFrame」改规范化 DTO；③财务度量列、`pre_close`、策略指标列缺列统一 `raise` 而非补 null / shift(1) / 返回空信号。
- **判据**：传缺 `close` 的 universe 报错文本含「必需列」；`BacktestEngine` 签名不再接受 `pl.DataFrame` 作为 `dividends`；删 `revenue` 调 `write_table` 抛错；无 `pre_close` 调 `compute_extended_candidates` 抛错。
- **不做会怎样**：任何一次上游字段改名都会静默污染因子与账本，且**症状是"结果看着正常"**——这是最难排查的一类损失。

### 第三件：建议链路口径收口（3.1 + 3.2 + 3.3 + 3.4）

- **为什么是它**：这是**唯一"两条入口同一天产出不同结论"**的业务。它不影响回测正确性，但它直接面向使用者的下单判断：GUI 会把「被延后未成交」的票显示成可下单（3.3），会把上一交易日的清单显示成「数据已更新」（3.4），还会覆盖掉 CLI 写好的 `exec_status/usage_boundary`（3.2）——三处都已在项目自己的 `docs/每日推荐使用边界_2026-11-05.md:34,40` 里被明确禁止。
- **动作**：把「引擎构造 + tiers 默认值 + 快照序列化 + 收盘闸门」收口成 `src/advice` 内唯一工厂函数，CLI 与 usecase 都只调它；DTO 增 `disposition/defer_reason/defer_until` 并在表格渲染。
- **判据**：两入口各生成一次后 `set(json.loads('reports/advice/latest.json').keys())` 完全相同；`{i.tier for i in items} <= {'mid','long'}`；触发换手上限时 `dto.disposition=='deferred'`；10:00 调 usecase 返回 `warnings` 非空且不写 `daily/`。
- **不做会怎样**：GUI 用户按错误信息下单；同一交易日的历史归档内容取决于「最后是谁点的」，事后无法复现当时结论。
