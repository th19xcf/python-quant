4. **隐藏 O(D×N) 空转**：每日全量遍历挂单 `for code in list(ctx.pending.keys())` 与 `schedule.codes()`，与当日活跃标的数无关；500 标的 × 5,000 日即 250 万次纯迭代。【代码直接证据：`execution_core.py:1275,1325-1327`】
5. **全量物化内存**：`column_data = {code: {name: df[name].to_list() for name in df.columns}}` 一次把整张面板导成 Python list；协议所述 12.7M 行面板有 OOM 风险。【代码直接证据：`execution_core.py:899-902`】
6. **降级路径仍逐行造 dict**（`{name: col[i] for name, col in cols.items()}`），仅 warning 不拦截；买入逐手回退 `while shares > 0: shares -= lot_size` 最坏 O(shares/100) 次成本计算。【代码直接证据：`execution_core.py:1020-1025,1033-1038,1094-1097,1676-1684`】
7. 正面项：指标已向量化预计算（`signal_columns[...] = vec(prepared[code]).to_list()`）、日期索引改平行数组 `_build_date_index`、权益 `AccountBook` 增量 O(1)。【代码直接证据：`execution_core.py:407-408,572-574,780-784,1009,1117-1147`；`base_engine.py:163-186`】

### 6.2 策略风险

- **过拟合/信息泄漏（最高）**：`optimize_strategy` 用 `itertools.product` 全网格 + `_select_best_params` 在**含 OOS 段的全样本**上选优并 `self.strategy.set_params(best_params)`，`param_stability_report` 同样基于全样本；虽有 purge+embargo（`purged_train_end = min(test_start - horizon - 1, train_end)`）与 Walk-Forward 实现，但 `walk_forward_windows=0` 默认关闭，且无 PBO / Deflated Sharpe / 多重检验校正。【代码直接证据：`backtest_engine.py:131,156-176,213-218,236,241-244,293-294`；`holdout.py:65-71`；`base_engine.py:298-347`】

## 8. 总体结论

**工程底盘扎实，策略可信度是当前短板。** 静态质量（ruff/mypy 近乎零问题）、测试规模（1,957 用例全通过）、核心撮合与风控覆盖率（88.4% / 94.3%）、数据管道（原子 upsert、多源熔断、列存原子写、日志脱敏）都达到可维护系统水准；性能上向量化指标 2,076 万行/s、组合回测 7.5–8.6 µs/bar，主瓶颈明确且可优化。【测试直接证据 + 静态分析结果 + 代码直接证据】

**但存在一类系统性风险**：多条"静默降级 + 默认放行 + 文档口径漂移"叠加在同一条链路上——分档滑点未注入、风控可整体关闭、参数优化偷看 OOS、失败组合被丢弃、ST/分红失败按无事件处理、README 费率与代码不符。单项看都是局部缺陷，合起来会导致**回测净值在没有告警的情况下系统性偏离真实可交易结果**。建议按第 7 章 P0 五项先做一轮"结果可信度加固"，再投入性能优化。【工程推论：综合第 3–6 章证据的整体判断】

**明确未验证项**：真实 MySQL 连接与事务并发表现、在线行情源（BaoStock/AkShare/TDX）的稳定性与更新频率实测、GUI 交互链路、实盘交易响应时间（项目尚无实盘模块）、真实历史数据下的策略表现与极端行情回撤、网络 IO 在真实行情下的瓶颈。这些均需接入生产like 环境后另立专项。【未验证】
