### 3.2 perf 墙钟门禁（`pytest -m perf`）：读数由收集范围决定，根因为 `tracemalloc`

#### 3.2.1 同一台机器、同一分钟内，三种调用口径的读数差 4 倍

| 调用口径 | 5 次读数区间（µs/bar） | min | median | max | 极差/中位 | 门禁判定（旧阈值 15.0） |
|---|---|---|---|---|---|---|
| `pytest -m perf`（**全量收集**，2182 项 deselected） | 18.48 → 19.27 | 18.48 | 18.50 | 19.27 | 4.3% | **0/5 通过** |
| `pytest -m perf tests/performance_test.py`（**最小收集**） | 4.55 → 4.99 | 4.55 | 4.93 | 4.99 | 9.7% | **5/5 通过** |
| 进程内直接复现 `bench_perf_gate.py` × 5 | — | 4.745 | 4.774 | 4.814 | 1.5%（CV 0.5%） | 5/5 通过 |

结论：门禁读数**不是由代码速度决定，而是由 pytest 收集范围决定**。按项目文档写明的方式（`pytest -m perf`）触发，门禁**恒定失败并报 18.5 µs/bar**；只把收集面缩到单文件，同一份代码立刻回到 4.6 µs/bar `[测试直接证据]`。

#### 3.2.2 根因：`tracemalloc` 在模块导入期被永久开启，放大 3.5 倍

全量收集会 import `tests/test_memory_manager.py` → `src/utils/memory_manager.py` → 模块级单例在 `__init__` 里 `tracemalloc.start()`，此后整个进程所有 Python 分配都被插桩。

| 检查点 | 实测 | 判读 |
|---|---|---|
| `tracemalloc.is_tracing()`（全量收集后） | **True** | 已被开启 |
| per_bar（tracing 开） | 16.114 µs | 与门禁读数同量级 |
| per_bar（**同进程** `tracemalloc.stop()` 后） | **4.599 µs** | 真实算力 |
| 放大倍数 | **3.5×** | 唯一主因 `[测试直接证据]` |
| `gc.disable()` 后的加速 | 1.03× | GC **不是**主因，可排除 |

| 位置 | 语句 | 说明 |
|---|---|---|
| `src/utils/memory_manager.py:68-72` | `tracemalloc.start()` / `self.tracemalloc_enabled = True` | 在 `__init__` 内无条件执行 |
| `src/utils/memory_manager.py:546` | `global_memory_manager = MemoryManager()` | **模块级单例**，import 即生效 |
| `src/main.py:48` | `from src.utils.memory_manager import global_memory_manager` | 生产入口 import 即开启 |

实测确认生产侧同样开启：`python -c "import src.main"` 的日志里出现 `内存跟踪已启动` `[测试直接证据]`。全项目 `tracemalloc` 只出现在 `memory_manager.py`（import / flag / start / 监控条件 / 快照 / 类型标注），没有第二个模块硬依赖 `[代码直接证据]`。

| 工作量 | A（tracing 关） | B（tracing 开） | 放大 | 判读 |
|---|---|---|---|---|
| parquet 整表读（200 文件 / 1,268,461 行） | 0.4745 / 0.4741 s | 0.4747 / 0.5099 s | **1.00–1.07×** | Rust 侧分配不被插桩，**IO 不受影响** `[测试直接证据]` |

| 方案 | 总内存 MB | 相对现状 | 换算 RSS 估算 | 代价 |
|---|---|---|---|---|

| C：`ts_code → Enum` + 两个因子列 `Float32` | **241.3** | 2.07× | ≈345 MB | 数值不再逐位等价 |

`Float32` 精度实测：`qfq_factor` 最大绝对误差 **3.0e-8**、`hfq_factor` **7.5e-6**（相对 3.0e-8），远低于价格最小变动单位，**但会破坏「逐值等价」类断言**，任何依赖 `assert_equal` 的对账都会红 `[测试直接证据]`。

对现有读取方的影响（实测分类编码落盘后读回仍是 `Categorical`；`== '600000.SH'` 过滤正常，与 String 列 `join` 抛 `SchemaError: datatypes of join keys don't match - cat vs str`）`[测试直接证据]`：

| 读取方 | 用法 | 影响 |
|---|---|---|
| `store.py` `_factor_frame` | `filter(ts_code == str)` + `join_asof(trade_date)` | **不受影响**（无 ts_code 等值 join） |
| `build.py:684` / `:720` | `snap.join(remote, on='ts_code')` | **会抛 SchemaError**，需任一侧 `cast(pl.String)` |
| `factor_rebuild.py` `_assemble` | 分块重组的键合并 | 需先 cast 回 String 再写回 |

结论：**放大主因是「按行展开 + Float64」，不是字符串枚举本身**——两个因子列占 55.2%，`ts_code` 占 31.0%。只换 `Enum` 能把内存压到 1.32×，叠加 `Float32` 可到 2.07×；但收益（约 370 MB）远小于「改编码 + 全量重写 + 修 join + 破等价断言」的成本，**本次不动数据文件**。若将来要让全市场因子常驻内存，再按 B 方案统一改造并同步修 `build.py` 的两处 join `[工程推论]`。

#### 3.5.5 因子 LRU：容量自适应 + 命中路径去掉 `stat()`（已落地）

| 问题 | 原实现 | 新实现 |
|---|---|---|
| 命中路径每次 `stat()`（Windows 约 0.18 ms，占命中成本 99%） | `self._factor_path.stat().st_mtime_ns` + 前置 `exists()`（两次 stat） | `_cached_mtime()`：同一路径每 `_FACTOR_MTIME_TTL=2.0 s` 最多 stat 一次；`exists()` 由 `OSError` 分支取代 |
| 容量固定 128 < 5,818 只 → 全市场遍历 100% 抖动 | `_FACTOR_LRU_MAX = 128` | `factor_lru_capacity()`：可用内存 × 10% ÷ 单帧占用（实测 140 KB / 常驻 0.18 MB），夹在 `[128, 8192]` |
| 同进程重建快照只能靠 mtime 被动失效 | 只有 mtime 比较 | 新增 `invalidate()`，由 `factor_rebuild.py` 与 `build.py` 在原子替换后调用；TTL 只兜底跨进程重建 |

容量判定依据：**按可用内存，不按标的数**。单票因子帧大小基本恒定（7,006 行 × 3 列约 140 KB，常驻约 0.18 MB），容量直接由内存预算折算；标的数只作天然上界。上限 8,192 防止在 64 GB 以上机器无节制占用；本机实测容量 **8,192**（32.4 GB 可用 × 10% ÷ 0.18 MB ≈ 18,000，被上限夹住），全市场 5,818 只可全部驻留，内存代价 +818 MB `[测试直接证据]`。

全市场遍历实测（`tmp/bench_factor_lru.py`，两趟，独立进程）：

| 指标 | 旧实现（stat + 容量 128） | 新实现 | 收益 | 标识 |
|---|---|---|---|---|
| 第 1 趟（全冷缺失） | 9.842 s | **7.310 s** | 1.35×（每次省掉两次 stat） | `[测试直接证据]` |
| 第 2 趟（目标口径） | **9.905 s**（容量不足，仍是全缺失） | **0.002 s** | **≈4,950×** | `[测试直接证据]` |
| 第 2 趟单票成本 | 1,702 µs | **0.34 µs** | — | `[测试直接证据]` |
| 常驻内存 | — | +818 MB（5,818 帧全驻留） | 受 10% 可用内存上界约束 | `[测试直接证据]` |
| 结果等价性 | — | 5,818 只逐只 `schema + 列序 + 行数 + equals` **0 处不一致**（`tmp/verify_factor_lru.py`） | 值不变 | `[测试直接证据]` |

结论：原估「10.2 s → 1.1 s」偏保守——0.185 ms/次是**含 stat 的命中成本**，去掉 stat 后第 2 趟只需 2 ms。第 1 趟无法再快：那 7.3 s 全是 parquet 行组扫描（1.25 ms/票），与 LRU 无关 `[工程推论]`。

### 4.6 数据管道健全性

#### 4.6.1 关键路径、失败阻断面与可重入性

| 环节 | 实现 | 失败会阻断什么 | 可重入 | 断点机制 | 等级 |
|---|---|---|---|---|---|
| TDX `.day` → `quotes` 增量 | `build.py` 按 coverage/source 末日期分类 | 全下游（所有回测/推荐） | 是（幂等覆盖） | 逐标的 coverage | 高（影响面） |
| `meta` 覆盖元数据 | `store.flush_meta` | 新鲜度、可交易判定、覆盖统计 | 是 | 重建 meta | 高（影响面） |
| 复权因子 / 分红 | `refresh-factors` | 所有价格可比性与收益计算 | 是 | 全量重写 | 高（影响面） |
| 财务 / 估值 | `financials/collector.py` 分片 | PE/PB、财务筛选、事件 | 是 | `progress.json` + `_mark_valuation_done` | 中 |
| 行业 / ST / 指数成分 | 日频快照 + 差分 | 行业上限、涨跌停幅度、池子 | 是 | 快照日文件 | 中 |

**判断"哪一步失败导致下游全失效"**：`quotes` 与 `factors` 是两个总闸；`meta` 是隐性总闸（不报错、只让覆盖判定退化）。三者都是单文件原子 + 幂等重跑，工程上可收敛；不可收敛的只有"源端已无数据"的情况 `[代码直接证据]` `[工程推论]`。

#### 4.6.3 质量门禁：判据覆盖与漏检

| 判据 | 覆盖范围 | 结构性缺陷 | 是否阻断 | 等级 |
|---|---|---|---|---|
| `internal_gap`（连续缺口） | **仅 `quotes/index`**（源码自述：只能比对指数序列） | 股票侧是**刻意不做**：全量 2,282 只个股存在 ≥20 个交易日的日历空洞，长期停牌与真实缺失在现有字段上不可区分，强上阈值会产生海量误报。因此缺的不是阈值，而是**区分停牌与缺失的手段**：`tushare suspend_d`（token 已解锁）可先建停牌日历、把停牌日从分母剔除，再对剩余空洞判缺失；924 天空洞漏检正是发生在该判据缺位的窗口 | `severity=warn`，仅 `strict=True` 时不可用 | **高** |

#### 5.2.3 四情形判定表

| 候选情形 | 是否成立 | 判定依据 |
|---|---|---|
| ① 没有卡 | ❌ **不成立** | 有 AMD 独显 + Intel 核显，`Status=OK` |
| ② 有卡但驱动 / CUDA 版本不匹配 | ❌ 不成立 | 机器上根本没有 NVIDIA 设备与 CUDA 驱动，谈不上"版本不匹配" |
| ③ **有卡但是非 NVIDIA，所以 cupy 用不了** | ✅ **成立** | cupy 只支持 NVIDIA CUDA；AMD 侧需 ROCm（本机无、Windows 不支持、gfx1010 亦被移出支持列表）；Intel 核显需 oneAPI/SYCL，venv 内无绑定 |
| ④ 有 NVIDIA 卡但未装 cupy | ❌ 不成立 | 未检测到 NVIDIA 设备 |

**正确表述：本机「有 GPU，但没有可被 cupy 使用的 GPU」**，不能写成"没有显卡"或"GPU 不存在" `[测试直接证据]`。

### 5.4 六个候选热点的逐项判断

#### 5.4.1 收益判断的共同基准

GPU 要正收益，必须同时满足三条：① 单次 kernel 数据量足够大（经验阈值 ≥10⁶ float64 元素，否则 kernel 启动 + 传输开销超过计算本身）；② 数据能常驻显存、不需每步回传；③ 逻辑是可并行的算术/归约，不是串行状态机或分支密集控制流。

| 基准项 | 实测值 | 标识 |
|---|---|---|
| Polars 大规模 join：17,957,979 行 × 18,070,885 行，键 `(ts_code, trade_date)` | **1.201 s**，RSS 2.9 → 8.2 GB，输出 17,957,979 行 | `[测试直接证据]` |
| Polars rolling/rank：18,044,637 行 × 3 个表达式（252 日 `rolling_rank` + `rolling_mean` + 截面 `rank`） | **1.291 s**，折合 13.97 M 行·算子/秒 | `[测试直接证据]` |
| 读 `valuation_daily.parquet`（17,957,979 行 × 12 列） | 0.164 s | `[测试直接证据]` |
| 读 `stock_adj_factor.parquet`（18,070,885 行 × 4 列） | 0.032 s | `[测试直接证据]` |
| `np.corrcoef`：5,000 只 × 2,700 日 | 0.413 s（输出 25 M 元素矩阵） | `[测试直接证据]` |
| bootstrap 2,000 次 × 500 / 5,000 / 50,000 样本 | 0.021 s / 0.130 s / 1.585 s | `[测试直接证据]` |
| 回测逐 bar 开销 b | 单独运行 4.24~4.95 µs/bar；250k bar 时 8.33 µs/bar；门禁上界 15 µs/bar（治理后已重定为 8.0，见 3.2.5） | `[测试直接证据]` |

项目目前所有"大规模"算子的 CPU 耗时都在 1.3 秒以内。GPU 的 PCIe 传输成本按 12 GB/s 估，125 MB（15.7 M × float64）单程约 10 ms，一次 kernel 启动 5~10 µs，同步往返 20~50 µs——即使完美移植，收益上限也只是"1.2 秒变 0.4 秒"，端到端占比个位数百分比，代价却是两个按 CUDA 版本分发的重依赖 `[工程推论]`。

#### 5.5.1 等价性容差（必须写具体值，不能写"误差可接受"）

| 比对对象 | 判据 | 理由 |
|---|---|---|
| 指标列逐元素（float64，如 MA/RSI/MACD/ATR） | `np.allclose(gpu, cpu, rtol=1e-9, atol=1e-12)` | float64 不同归约顺序的相对误差上界在 1e-12 量级，1e-9 留 3 个数量级余量；`atol=1e-12` 覆盖接近 0 的读数 |
| 排序 / 分位（`rank`、`rolling_rank`、分桶） | **逐位相等**（整数秩，`==`） | 浮点容差会掩盖秩的换位；秩不同即分位不同，属口径分歧 |
| 前向收益 `fwd_h`、超额 `exc_h` | `rtol=1e-9, atol=1e-12` | 同上 |
| 回测成交判定（涨跌停 / 停牌 / 一字板 / 整手 / ADV 分档） | **布尔 exact** | 离散判定，任何浮点漂移都可能翻转成交与否 |
| 回测 equity 曲线终值与逐日值 | `rtol=1e-9` | 由成交金额累加而来，成交判定 exact 后只剩浮点归约误差 |
| **反向红线** | 若某项必须放宽到 `1e-6` 以上才能通过，判定为**两路口径不同**，拒绝上线，不得调大容差 | 防止用放宽阈值掩盖实现分歧 |

#### 5.5.2 cupy / CUDA 版本对应与失配行为

| 安装方式 | 对应 CUDA | 体积（wheel） | 失配时的行为 |
|---|---|---|---|
| `cupy-cuda12x` | CUDA 12.x | 约 400~500 MB | `import cupy` **成功**，首次 `cp.cuda.runtime.getDeviceCount()` 抛 `CUDARuntimeError: cudaErrorInsufficientDriver` / `cudaErrorNoDevice` |
| `cupy-cuda11x` | CUDA 11.2~11.x | 约 400~500 MB | 同上 |
| `cupy`（PyPI 名，源码分发） | 由本机 CUDA Toolkit 决定 | 需本地编译 | Windows 无 nvcc 时**安装阶段即失败**，这正是 `cupy = "*"` 的真正后果 |
| `cudf-polars-cu12` | CUDA 12.x | 约 1.5~3 GB | 缺失时 `pl.GPUEngine` 抛 `ModuleNotFoundError`（本次已实测）；版本与 polars 不匹配时抛 `ImportError` / `RuntimeError` |

**探测逻辑必须分两层**：`import` 成功 ≠ 可用。正确判定是 `import cupy 成功` **且** `cupy.cuda.runtime.getDeviceCount() > 0` **且**（可选）`cupy.cuda.Device(0).mem_info[0]` 足够大。原项目只做了第一层 `[代码直接证据]`。

若必须安装验证（仅建议，本次未执行）：`cupy-cuda12x`（~450 MB）与 `cudf-polars-cu12`（1.5~3 GB）都应装在**独立 venv 或 conda 环境**、不进主 `.venv`；本机无 NVIDIA 卡，装了也**无法验证功能**，只能验证"import 后正确降级"——要验证真跑，必须在有 NVIDIA 卡的机器上装并把结果作为回归基线 `[工程推论]`。

### 5.7 结论与第一步建议（含执行记录）

| 问题 | 回答 |
|---|---|
| 这台机器上 GPU 值不值得用 | **不值得，也不可用**：有 AMD 独显 + Intel 核显，但无 NVIDIA 设备；gfx1010 不在 ROCm 支持范围且 Windows 不支持 ROCm；Intel 核显无 Python 绑定 |
| 用在哪 | **没有任何一处**：回测引擎/数据采集/相似态去重叠在形态上不匹配（Python 标量控制流 / 网络 IO / 哈希表循环）；相关矩阵与 Ridge 规模不够（K ≈ 25）；剩下两项形态匹配但 CPU 已在 1.3 s 内完成 |
