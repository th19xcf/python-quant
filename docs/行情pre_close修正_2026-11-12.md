# 行情 `pre_close` 修正与合并后重算（2026-11-12）

## 1. 结论摘要

- 修正 **4 行 / 2 只指数** 的 `pre_close`（`change`/`pct_chg` 同步重算），行数守恒 3,193 / 3,606 不变。
- 根因不是「某一行写错」，而是 **`build --incremental`（不带 `--since`）在残缺的源端 `.day` 序列上做 `shift(1)`，再把结果按同日覆盖回正式表**。不修这条链路，同一次重写会把修好的值再抹回去。

- 全库 index 只读复算：**1,335 文件 / 4,649,808 行 / 异常 0 行**。

### 2.1 `1499.21` 的来历（检索证据，不是推测）

对两侧同日收盘做等值检索，`close == 1499.21` **各只命中 1 行，且都落在 `2019-09-17`**：

- 本地正式表 `880581.SH.parquet`：命中 1 行，日期 `2019-09-17`；
- 通达信源 `880581.day`：命中 1 行，日期 `2019-09-17`。

而 `2019-09-17` 正是 **通达信侧最后一个可用 bar**（源端在此之后直接跳到 `2024-11-05`）。因此 `2024-11-05` 的旧 `pre_close=1499.21` = **源端前一日可用 bar 的收盘**，是残缺源端上 `shift(1)` 的产物，不是「缺口后一日的昨收」。

四日期 × 两侧对照（该表是改与不改的前提，先做过再动数据）：

| 日期 | 本地 `880581.SH.parquet` | 通达信 `880581.day` |
|---|---|---|
| 2019-09-17 | 有 bar，`close=1499.21` | 有记录，`close=1499.21` |
| 2024-03-12 | 有 bar，`close=1818.96` | **无记录** |
| 2024-11-04 | **无 bar** | **无记录** |
| 2024-11-05 | 有 bar，`close=1033.70` | 有记录，`close=1033.70` |

结论：**缺口包含 `2024-11-04`**（两侧都取不到该日数据），「`1499.21` = `2024-11-04` 收盘」的说法证伪；`1818.96` 唯一可核来源是**本地 `2024-03-12` 那一行**（第 2,703 行，`close=1818.96`），该行在通达信侧不存在，属**回补行**。

### 2.2 为什么写 `1818.96`，而不是保留 `1499.21`

- `pre_close` / `change` / `pct_chg` 必须与**表内前一行**自洽；前一行就是 `2024-03-12`（`close=1818.96`）。
- 与新代码合并后重算的结果一致：下次增量构建重算 `close.shift(1)` 得到的也是 `1818.96`。不写它，下一次构建就会把值改回去，修正无效。
- 该行的 `pct_chg=-43.17%` 是**缺口的表现，不是 `pre_close` 单独写错**——缺口在 `2024-03-13~2024-11-04`，`2024-11-05` 只是缺口后第一根 bar。**不得以「不具经济含义」为理由保留错值**，也不得据此改写当日 `close`。

## 3. 覆盖根因与代码修法

2026-11-11 18:07:44→18:11:59 的 `python -m src.data.local_store build --incremental`（9,091 文件 / 24,097,931 行，exit 0）走的正是这条链路：

1. `build_frame` 在**源端 `.day` 序列**上 `shift(1)`。880581 源端比本地少 1,087 行，399699 源端起点比本地晚 5 年；
2. `_merge_source_with_existing` 按 `unique(subset=['date'], keep='last')` 合并，**同日以源端为准**；
3. 于是「源端残缺序列推出来的 `pre_close`」覆盖了本地正确值。

修法（`src/data/local_store/build.py`）：

- 抽出 `_derive_price_change(frame)`，`build_frame` 与「合并后」两处共用同一份公式；
- `_rebuild_target` 在 `_merge_source_with_existing` 之后对合并序列重算，**合并后的序列才是「前一日」的正确定义**；
- 收尾接 `DataSourceBase._fill_kline_nulls`（派生列 null → 0.0），与 `_normalize_kline` 第 7 步同口径——否则重算会让**每只标的的首行**从 0.0 变成 null；
- **基金显式跳过**（`kind in ('stock','index')` 才重算），依据写在代码注释里。

## 5. 基金 `pre_close` 的口径差异（不得互相「修正」）

基金行 `pre_close` 是**除权调整口径**：`qfq_factor` 恒为 1.0，除权调整全部落在 `hfq_factor` 上，停更后的回补行 `pre_close` 由基金侧链路按除权口径写入。实测例 `161911.SZ` `2019-09-24`：前收 `1.014`、`hfq_factor` `1.461617→1.488043`、`pre_close = 0.996 = 1.014×1.461617/1.488043`。

若把股票/指数的 `close.shift(1)` 套到基金上，全库 **329 行 / 183 只**的正常除权昨收会被改回原始昨收，`change`/`pct_chg` 同步失真。该口径已写入 `docs/数据权威路径清单.md` 的基金日线行与指数日线行。

## 7. `build --incremental` 不带 `--since` 的行为：建议收紧（本轮不改）

现状：`--incremental` 无 `--since` 时，`build_frame` 仍只看源端 `.day`，而源端**并不保证是本地历史的超集**（880581 少 1,087 行、399699 晚 5 年）。同日覆盖语义把这一缺陷直接写进正式表。

建议（按优先级）：

1. **派生只在合并后做**——本轮已落地，覆盖 `pre_close/change/pct_chg`；
2. 其余由源端直接落地的列（OHLCV）若源端行数 < 本地行数，应在 `_merge_source_with_existing` 前给出 `logger.warning` 并计入构建统计，便于下次审计直接发现「源端比本地短」；
3. `--incremental` 无 `--since` 且存在「源端行数 < 本地行数」的标的时，建议默认**跳过这些标的**（保留本地），需显式 `--force-short-source` 才重建——避免静默截断。

第 2、3 条涉及默认行为变更，本轮不动，留待单独确认。
