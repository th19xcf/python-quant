# 公告事件日更入口（`tools/update_events.py`）

## 为什么需要它

`meta/events/events.parquet` 之前只有按月补历史的 `tools/backfill_events.py`，**没有日更入口**：表里最新 `publish_time` 会一直停在最后一次手工补数的那天，而 `coverage.json` 又是下游判断「有没有事件」的唯一依据。

月级/季度级查询本身不可靠：

- 源端会间歇返回 **HTTP 200 + 空 `announcements`**（实测 2021-12 股权激励第 2/4/7/10~14 页全空，重试 4 次仍空）；
- 单日查询命中通常 ≤30 条、只有一页，**第 1 页同样会空**，不重试就等于整天静默丢失；
- `totalRecordNum` 计入重复行，不能拿它当「取全了」的判据。

本脚本把已经验证过的口径固化成一条命令：**按自然日抓取 + 判空重试 + 同日多轮收敛 + append 入库**，并且**永不自动改覆盖声明**。

## 用法

```bash
# 补当天
python tools/update_events.py

# 指定某一天（当日建议配合 --force 多轮收敛）
python tools/update_events.py --date 2026-11-11 --force --max-rounds 8

# 指定区间（含首尾）
python tools/update_events.py --start 2026-11-07 --end 2026-11-11

# 含今天往前 N 个自然日
python tools/update_events.py --days 3

# 只算不落盘（会照常抓取并落分片）
python tools/update_events.py --date 2026-11-11 --dry-run

# 只用已有分片入库（中断续跑）
python tools/update_events.py --date 2026-11-11 --skip-fetch
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--date` / `--start` `--end` / `--days` | 今天 | 三者互斥优先级：区间 > `--date` > `--days` > 今天 |
| `--max-rounds` | `3` | 同日最多抓几轮；达到上限仍有新增会打告警「可能未收敛」 |
| `--sleep` | `0.3` | 每次请求后的节流秒数（单连接串行，`WORKERS` 强制为 1） |
| `--shard-dir` | `research/events/data/backfill/daily/` | 日分片所在目录（已被 `.gitignore` 覆盖）；断点与合并件另落 `_staging/events_daily/` |
| `--store-root` | `data/local_store` | 事件表与覆盖声明所在根 |
| `--force` | 关 | 重抓已有分片（补当日、或怀疑上次不完整时用） |
| `--skip-fetch` | 关 | 不抓取，只用已有分片入库 |

退出码：`0` 正常；`2` 没有可用分片 / 覆盖声明缺失；`3` 抓取失败（已写 `failed.csv` 并停压）；`4` 入库后既有行对拍不通过（按打印的回滚路径恢复）。

## 它到底做了什么

1. **逐日抓取**：对区间内每个自然日、10 个关键词分别调用 `research/events/fetch_announcements.py` 的 `fetch_cninfo_chunk`，复用其中的「按该页应有条数判空重试（最多 4 次）+ `records < total` 告警」；单日一般只有一页，第 1 页空同样被兜住。
2. **同日收敛**：同一日反复抓，直到**某一轮没有任何新增唯一 `(art_code, stock_code)`** 为止（第一轮必然全算新增，所以最少两轮）。不用 `totalRecordNum` 判收敛，因为它计重复行。
3. **落分片 + 留断点**：每日分片 `daily/YYYYMMDD.parquet` 用 `write_parquet_atomic` 原子写；断点写 `_staging/events_daily/progress.csv`（day / status / rounds / unique / last_round_new / total_hits / elapsed_s）与同目录 `failed.csv`（DG-7：即使零失败也先落表头），失败**立即停止**，不换天硬重试（限速或封禁时继续加压只会延长恢复时间）。
4. **入库**：合并当日/区间分片，按 `(art_code, stock_code)` 去重后调用 `src.data.events.import_file(mode='append')`。append 语义是既定的：**既有行一条不改**；新批次先剔除与既有重复的 `event_id`，再做同标的同类型 30 自然日去重（与既有行相距 ≤30 天的新行丢弃）。
5. **回滚快照 + 对拍**：入库前把 `events.parquet` 与 `coverage.json` `copy2` 到 `_backup/events_daily/<YYYYMMDD_HHMMSS>/` 并校验 SHA 一致；入库后按 `event_id` 逐列比既有行，任何一格改动、任何一处非空→null、任何一条丢失都以退出码 `4` 报错并指向快照。
6. **只报告，不改声明**：把当前 `coverage.json` 的 `start`/`end` **原样**传给 `import_file`（否则它会用数据 min/max 反推，等于偷偷前移）。

## 跑完打印的三件事

```text
本次新增行数: 10（源行 20，规范化 17，与既有近重复丢弃 7）
表行数: 185641 → 185651；SHA256 48a263118ce6c69d → c9c35d86d1d307d0
既有行对拍: 改动 0 格、非空→null 0 行、丢失 0 条
当前覆盖边界: start=2015-01-01 end=2026-11-06（声明行数 185651）
是否需要人工推进 coverage.end: 是
  依据: 表内已有 5 个自然日 / 59 行落在声明终点 2026-11-06 之后（2026-11-07~2026-11-11）
回滚快照: _backup/events_daily/20261111_142052
```

「是否需要人工推进」的判据只有两条：

1. 表内数据 `max(publish_time)` 的日期是否晚于 `coverage.json` 的 `end`；晚于则列出越界的自然日数与行数；
2. 本次请求的区间里是否有抓取失败或分片缺失的天数；有失败日则**即使越界也不建议推进**。

两条都满足（有越界行、且没有失败日）才给出「是」，并在依据里写清越界区间。

## 覆盖边界为什么必须人工推进

- `EventStore.status()` **只认 `coverage.json` 的 `start`/`end`**，不看数据 min/max；区间外一律 `unknown`。`risk_filters` 在 `event_unknown_policy='keep'` 下放行 unknown——所以 unknown 是「诚实地说不知道」，不是「没有事件」。
- 把 `end` 前移等于对外宣告「这段区间已经完整收口」。只要还有一天没收敛、或抓取出过空页没重试成功，前移就把 `unknown` 变成了**假 `clear`**：过滤看着正常，实际漏掉的处罚/并购公告不再有任何标记。这与「不得把未接线当成无数据」同一条红线。
- 前移还需要满足：区间内每一天都跑过稳定化收敛（末轮新增为 0）、`failed.csv` 为空、入库后既有行对拍全 0。
- 因此本脚本**没有** `--advance-coverage` 这类开关，只打印判断依据。确认要推进时，人工用 `src/data/atomic_write.write_text_atomic` 改 `coverage.json`（保留其余字段，追加一条 `coverage_advance_<YYYY-MM-DD>` 记账：依据、越界天数/行数、SHA256），不要用编辑器直接覆盖。

## 边界与禁止项

- **不注册系统调度**：`schtasks /create` 与 `Register-ScheduledTask` 在本环境均返回 `Access is denied`（非提权会话），该结论仍然有效；需要定时执行时用外部已有调度或手动跑本命令。
- **不改既有行、不删分片**：append 模式下既有行只读；`daily/` 下的历史分片不自动清理（它是续跑依据）。
- **不碰别的数据**：只读写 `meta/events/`、`research/events/data/backfill/daily/`、`_staging/events_daily/`、`_backup/events_daily/`。
- **当日是移动靶**：11-11 这类当天数据在收盘前后还会新增公告，上午收敛不代表下午不再有。当日补数建议晚间再跑一次 `--force`，并仍不推进声明。
