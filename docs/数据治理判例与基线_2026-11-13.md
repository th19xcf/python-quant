**统计行反例（2026-11-13 实测）**：单参数 `git diff HEAD~1` 比的是「上个提交 ↔ 工作区」，会把他路在途改动一并列进来，不能代表本次提交内容——该写法把他人 23 条 `M` 列成「本次变更」，而本次实际只有 `.gitignore` 1 个文件。必须取双提交形式 `git diff --stat HEAD~1 HEAD`（等价 `HEAD^ HEAD`）的第一行。

**第 2 块格式反例**：把整个 5 块模板再包进外层代码块时，嵌套围栏会让聊天窗口把消息内容渲染吞掉。

### 1.2 备份增量同步脚本

规则锚点：「Git 提交规则」中「备份方式」。目标固定 `G:\git\python-quant\`。

````powershell
python -c "
import subprocess, shutil, os
src=r'E:\code\python\quant'; dst=r'G:\git\python-quant'
# 1. 获取本次 commit 变更文件列表
r=subprocess.run(['git','-C',src,'diff','--name-only','HEAD~1','HEAD'],capture_output=True,text=True)
changed=[l for l in r.stdout.strip().split('\n') if l]
# 2. 获取被删除的文件列表
r2=subprocess.run(['git','-C',src,'diff','--name-only','--diff-filter=D','HEAD~1','HEAD'],capture_output=True,text=True)
deleted=set(l for l in r2.stdout.strip().split('\n') if l)
# 3. 同步修改/新增
for rel in changed:
    s=os.path.join(src,rel); d=os.path.join(dst,rel)
    if os.path.isfile(s):
        os.makedirs(os.path.dirname(d),exist_ok=True)
        shutil.copy2(s,d)
    elif rel in deleted and os.path.exists(d):
        os.remove(d)
print(f'synced {len(changed)} files, removed {len(deleted)} deleted')
"
````

### 1.3 为什么不能删整个备份目录

备份目录 `G:\git\python-quant` 是独立 git 仓库（有自己的 `.git`），`shutil.rmtree` 会把备份仓库一并干掉。历史上有过「精确匹配」方案，属于过度设计——用户只需要同步文件内容。

## 二、隔离索引判例

### 2.1 提交后未回填共享索引 → 成片假 `MM`

规则锚点：「Git 提交规则」中「隔离索引提交后必须回填共享索引」。

实测（可复算）：11-11 全天提交 122 个（`git log --since="2026-11-11 00:00:00" --until="2026-11-12 00:00:00" --format=%H | wc -l`），叠加当日 10 次 `reset: moving to HEAD` 与多条空 message 的 HEAD 更新，共享索引最终停在祖先版本——11-12 盘点时 20 项里有 16 项是假 `MM`，其工作区内容与 HEAD 逐字节相同（`git hash-object` == `git rev-parse HEAD:<path>`），索引 blob 可在祖先提交中逐一找到；11-12 09:54:56 / 09:55:22 / 09:55:45 三笔隔离索引提交（`7b087b2` / `281e79c` / `7850f5c`）后当场复现同一签名，新命令执行 `git read-tree HEAD` 后索引重写为 83,332 字节、`git status --short` 只剩真实改动。

### 2.2 用前未种子化 → 整棵空树提交，790 个文件被记删除

规则锚点：「Git 提交规则」中「隔离索引用前必须先种子化」。

实测（可复算）：2026-11-12 提交 G-093 登记行时，`GIT_INDEX_FILE` 指向空索引直接 `update-index --cacheinfo` 后 `commit`，该笔 `633294c` 记为 `791 files changed, 240400 deletions(-)`，790 个文件在树中被误删（工作区未受影响）；随即以 `633294c^` 的完整树重建索引、只替换缺口表一个 blob，前向修复提交 `184997c` 记 `790 files changed, 240400 insertions(+)`，`git diff --stat 633294c^ HEAD` = 1 file changed, 1 insertion；全程未 reset、未 amend、未改写历史，`633294c` 留在历史中可追溯。

### 2.3 种子化基准漂移 → 提交树回退他路已落文件

规则锚点：「Git 提交规则」中「种子化基准必须是提交那一刻的父提交」。

**反例一（父提交已落、临时索引仍基于旧 HEAD）**：2026-11-12 `d07764c`（补布林带语义注释与 BOLL 用例）的隔离索引在其父提交 `563c0d9` 落库之前已从旧 HEAD 种子化，提交树因此回退 5 个文件（`src/data/local_store/store.py`、`tools/build_cn_bond_tables.py`、`tools/build_futures_continuous.py`、`tools/build_name_history.py`、`tools/manifest_tool.py`），该笔提交记为 7 files changed, 166 insertions(+), 64 deletions(-)；因工作区内容与 `563c0d9` 逐字节相同（`git diff 563c0d9 --stat -- <5 文件>` 为空）才未丢成果，随后由 `74e2a77` 按 `563c0d9` 的 blob 写回树完成前向修复，`git diff 563c0d9 HEAD` 只剩 2 个文件。同轮 `8105d04` 已改用提交前实时取基准（`before` 在五步开头取、提交前复取 `after` 比对，不一致即整体重做），属正确形态。

**反例二（假成功）**：2026-11-13 `2350903` 那笔首次尝试漏了 `hash-object -w`，`git commit` 报 `invalid object 100644 …`、HEAD 停在 `1b1c550` 没动，脚本却未校验退出码、无条件打印了 `COMMITTED`。教训：`commit` 没报错或报错后脚本继续往下走，都不等于新提交存在，只有「`git rev-parse HEAD` ≠ `before`」这条断言能堵住这种假成功。

## 三、备份仓库提交与推送

### 3.1 推送代理实测（2026-11-12）

规则锚点：「备份仓库提交规范」中「推送失败先判别代理与直连」。

现象：`git push` 报 `Failed to connect to github.com:443 over proxy 127.0.0.1` 或 `Recv failure: Connection was reset`。起作用的始终是全局 `.gitconfig` 里那条 `http.proxy=http://127.0.0.1:10808`，环境变量 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` 为空，与它们无关。

实测：`127.0.0.1:10808` 探测 **True**（代理在跑）、`github.com:443` 直连探测 **False**（直连不通）；清空代理后 push 报 `Recv failure: Connection was reset`，恢复默认代理配置后同一笔 push 成功（`922bd19..289254d main -> main`）。旧写法「统一清空代理直连」在本机现有网络下必然失败，故改为按探测结果分支。

提交标题示例：`chore(backup): 2026-11-9，同步 2026-11-09 数据质量、研究脚本与审计文档`。

### 7.9 DG-34 运行时字段使 SHA 失效

`meta/daily_index.parquet` 的 `built_at` 每次 `flush_meta()` 都写新值、`source_mtime_ns` 记源 `.day` 的 mtime；`meta/st/st_price_inferred.parquet`、`factors/stock_turnover.parquet`、`meta/name_history.parquet` 的 `fetched_at` 每次重建都写新抓取时刻，同输入重跑字节必然不同。

两条绕开方式：① 让时间戳确定化——`st_history._input_timestamp()` 取输入缓存最大 mtime 而非 `datetime.now()`，同输入重跑逐字节一致，SHA 对拍才有意义；② 按业务主键 join 逐值比对——G-045 验收用 `eq_missing` 逐元素证明未改动的 9,761 行全等，SHA 仅作「落的是这份文件」的身份记录。`manifest_tool.py --check` 只比整文件 `bytes` / `rows` / `sha256` / `columns`，属文件身份校验，不能替代内容等价。

反例：`docs/evidence/data_lineage_governance_20261113/b2_slice4_check.md` 记 `name_history.parquet` 字节数与改前相同、仅 `fetched_at` 变化，SHA 由 `7e29fdaa…` 变为 `fd13515e…`，按 SHA 判会误判「内容变了」；反向地，为对齐 `fetched_at` 把它置空或回填后再比 SHA，也不代表口径一致——G-080 方案记录按生产 merge 语义取「最后非空」会把 17.97M 行的抓取时间整体改成后片时间，等于伪造来源时间。
