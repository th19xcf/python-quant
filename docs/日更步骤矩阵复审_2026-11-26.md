## 0. 观测基线（先说明为什么"优化"很难定量）

- 统一日志 `work/logs/daily_update.log` 的 `run_end` 只记**整轮** `seconds`，不记每步耗时；
  控制台日志 `logs/daily_YYYYMMDD_console.log` 只有两轮、共 646/549 字节，也无线程内步骤时间。
- 现存实测：2026-11-25 18:16 全量 `seconds=6746.31`（failed=manifest）；2026-11-24 23:54 部分
  `seconds=1548.81`（只跑 4 步，failed=manifest）；其余都是 3~110s 的 `--only` 小跑。
- 结论：**当前没有任何一步的实测耗时数据**。下面的优化建议只保留"不依赖耗时也能判定收益"的项，
  并把"先建立每步耗时"排第一，否则后续所有优化都是猜。

## 2. 今天新加/新改路径的失败分支（上一轮漏掉的部分）

### 2.1 `--detach`：`_spawn_detached` / `_verify_detach`（L873-L955，main L3081-L3100）

成功分支怎么验：`test_detach_passes_when_run_start_seen`（日志预置 run_start + 存活）、
`test_detach_not_misjudged_when_child_finished_within_window`（预置 run_start+run_end + 已退出）、
以及 `test_detach_without_pid_returns_nonzero`、`test_detach_start_check_waits_ten_seconds_and_fails`。
另有 `work/verify_detach_20261126.ps1` 做过父终端 `taskkill /F /T` 的真实存活验证。

失败分支**未覆盖或已发现的问题**：
- **`--detach` + dry-run 必判失败**：detach 分支在 `args.apply` 计算之前（L3081 vs L3114），子进程按默认
  dry-run 走完 `_print_dry_plan` 直接 `return 0`，全程不写 `run_start`（`run_start` 只在 `_run_apply` L2945）。
  父进程 `_verify_detach` 只会看到"子进程已退出且日志无 run_start"→ `detach_failed` + **exit 3**，
  而这次 dry-run 其实成功。dry-run 是默认行为，等于 `--detach` 单独使用必红。**这是上一轮引入的新问题。**
- **子进程在 run_start 之前正常失败会被伪装成"启动失败"**：`--only nosuchstep`（L3111 直接 return 2）、
  被 `lock_blocked` 挡下（`_acquire_lock` L2896 SystemExit）、`_write_staging` 的 `batch_rejected`（L711/L723）
  都发生在 run_start 之前 → 父进程统一报 `detach_failed: 子进程已退出且日志无 run_start`，**真实原因
  （锁被挡/批次被拒/未知键）全部丢失**，且退出码从子进程的 1/2 变成 3。证据：`docs/日更无声失败修复_2026-11-26.md`
  记录的冒烟 `--detach --only nosuchstep` 打印了"已脱离终端拉起"，与该代码路径矛盾——说明那次冒烟并未真正
  过 `_verify_detach`，测试证据不可信。
- **pid 复用**：`_pid_alive` 只查 pid 存在（L2806 OpenProcess），不核对进程启动时间/命令行。10s 窗口内
  pid 被复用概率极低，但 `_detach_started` 是"pid 匹配 + run_start"，复用后如果恰好有同 pid 的 run_start
  （日志里历史 pid 相同）会被误判成功。缺用例：预置一条**旧日期**同 pid 的 run_start，应判失败而非成功。
- **日志窗口**：`_read_log_tail` 固定末尾 400 行（L2820）。当前 `work/logs/daily_update.log` 仅 97 行，
  暂安全；但按事件增长后，run_start 可能被挤出窗口 → 子进程明明起来了却报"10s 内日志未出现 run_start"。
  缺用例：日志 >400 行且 run_start 在窗口外。
- **中继超时**：`_spawn_detached` 用 `communicate(timeout=20)`（L924），超时只 `proc.kill()` 返回 0，
  对**已经 breakaway 拉起的子进程不做任何处理**——可能出现"父进程报 detach 失败，但子进程实际在跑并写数据"。
  这种情况没有任何事件记录（只有 no_pid），运维会重跑 → 撞锁。

### 2.2 通达信落地守卫 `_await_tdx_landing`（L504-L542，`_tdx_lday_end` L471-L501）

成功分支怎么验：`test_tdx_landing_guard_passes_without_wait_when_landed`、`.._retries_every_5min_then_passes`、

覆盖的是"末根已到/需要重试/超时/关闭守卫/解析正常"。

失败分支缺口：
- **路径不存在**（L519 `not tdx_path.is_dir()`）→ warning + `return True`，**单测没有**。而且这是"配置写错
  也继续跑"的口径：`tdx_data_path` 填错时 build 会用旧 .day 构建，只在别处报末日不符。
- **路径存在但为空 / 无 lday 子目录**（L489-L501 三层循环全空）→ `last is None` → 空转满 2400s 才失败。
  无单测；且**等待期间零落盘**：轮询用 `logger.info`（L540），而 main 把 logger 设到 WARNING（L3105），
  默认不落盘 → 外部看到的是"40 分钟完全静默"，只能靠锁 mtime 判断它还活着。
- **lday 存在但没有目标日**：被 `timeout_fails_build_step` 覆盖（同一分支），可接受。
- **等待期间目录被外部删除/改名**：`_tdx_lday_end` 里 `lday.glob` 在目录消失后返回空、probing 读不到文件
  返回 None → 继续等到超时，报"末根 缺失 < 目标"，**无法区分"源端没发布"与"路径没了"**。无单测。

### 2.3 锁：`lock_blocked` / `stale_lock_unfinished_run` / 陈旧锁归档 `os.replace`（L2862-L2933）

- 已覆盖：`test_acquire_lock_blocked_logs_event`、`test_acquire_lock_alerts_unfinished_run`。
- **并发归档没有任何互斥或二次校验（高风险）**：进入 `FileExistsError` 分支后，"读锁内容 → 判断陈旧 →
  `os.replace(LOCK_PATH, archived)`"（L2875-L2912）之间没有重新读取/比对。窗口内另一进程完全可能已经
  归档旧锁并**写入了自己的新锁**，本进程随后把**那把活跃锁** rename 走，再 `continue` 去创建自己的锁
  → **两个写数据进程同时跑**，共享 quotes/ 与 meta/。这类竞态不会被现有单测发现。
- **归档名只到秒**（L2910-L2911 `%Y%m%d%H%M%S`）：两个进程在同一秒归档 → 同名目标；Windows 上
  `os.replace` 会直接覆盖，**先归档的文件被悄悄吞掉**，事后无法追溯上一轮的锁内容。
- **`os.replace` 的异常未捕获**：源文件在 stat 之后、replace 之前被另一进程移走 → Windows 抛
  `FileNotFoundError`/`PermissionError`，此处无 try → 整个进程带着 traceback 退出（不走 SystemExit、
  不写 `run_end`，但已经写过 `stale_lock` 事件）。归到"未捕获异常"。
- `_release_lock`（L2925）在锁被外部替换的情况下会 unlink **别人的锁**（没有校验 pid）；概率低，但和上面
  同属"锁身份未校验"的问题族。

### 2.4 `batch_rejected`（L700-L724）

- 两个分支都在：`already_applied`（L702-L711）与 `input_hash_mismatch`（L712-L723），单测各一条
  （`test_batch_rejected_already_applied_logs_event`、`.._input_hash_mismatch_logs_event`）。
- 字段够不够定位：
  - hash 不符分支有 `existing_input_hash` + `input_hash` + `detail`，**能证明"变了"，但定位不到"变在哪"**

  - `already_applied` 分支**缺两个 hash 字段**，只有 `applied_at`，无法判断复跑时输入是否也变了。
- 位置语义没问题：`_write_staging` 在 `run_start` 之前，因此被拒时日志里没有 run_start/run_end，但

### 2.5 `failed_noncritical`（L1756-L1783，渲染 L2436-L2443，落盘 L2966-L2969）

- rc 解析：`_step_exit_code`（L1756）正则 `\brc=(-?\d+)\b`。解析失败 → `exit=None` → 体检行显示
  `exit=?`、run_end 里是 `null`。**不会抛异常，也不会误填**，但"哪一步、什么错"只剩 steps 名，定位弱。
  典型无 rc 的失败：`_step_factors` 的"行情内嵌因子副本与快照不一致"（L2125）、`_step_build` 的末日断言
  （L1962 有 rc=0 但判 False，会被 `\brc=0` 抓成"exit=0 却失败"的误导值——**这是一个真实的解析缺陷**：
  明细里 `rc=0 | 末日不符` 时 `failed_noncritical.exit` 会写 0，看日志的人会以为子进程没报错）。
- 字段错位：**不会**。`step`/`name`/`exit` 是三个独立 JSON 字段，name 含空格（如"停复牌日表（交易日历 − …）"）
  不参与解析；run_end 只投影 step/name/exit，不写 detail，长度可控。
- 未覆盖：非致命步骤"抛异常"（`_run_steps` L1774 捕获）时的 detail 形如 `ValueError: ...`，无 rc → exit=null，
  没有单测断言这种形态。

### 2.6 哈希复用 `src/data/hash_cache.py`

- 判据是 `size` + `mtime_ns` 同时相等（L81-L82），三项全一致才复用。
- **size+mtime 不变但内容被改写会漏检**。定性：这是**已知取舍**，不是随手写的缺陷——当前所有写入器都走
  原子替换（临时文件 + `os.replace`），替换后 inode/mtime 必变；缓存文件本身也用同一模式（L100-L108）。
  真正会漏的场景是"原地改写且把 mtime 改回原值"或"网络盘 mtime 精度粗"，本仓库没有这种写入器。
- 是否值得加"抽样校验"：**现在不值得**。理由是可量化的——抽样校验只能降低"已知不会发生"的风险，代价是
  每次 manifest 步多读 N 个文件；而 manifest 步的实测耗时**目前没有数据**（见 §0），无法证明它值得优化。
  正确顺序是先在 `run_end` 里记下 manifest 的秒数与 `FactsCache.hits/misses`（这两个计数已经在对象上，
  L50-L51，只是没落盘），拿到数据再决定。

### 2.7 估值"按末日跳过"（`daily_update.py` L1139-L1157；`collect_financials.py` L73-L94、L607-L622）

- **不会**把"停牌/源端没发数据"误判成已最新：`--since auto` 在全局末日追平时不是直接退出，而是
  `return until, until`（L89-L93）改走逐码；逐码判据是 `last_dates.get(code) == until`（L618），
  严格等于目标日才跳过。停牌股没有目标日那行 → 末根 < until → **照常抓取**（L613-L614 注释也写明这条纪律）。
- 反向问题有两个，都是"看不见"而不是"判错"：
  1. `daily_update._run_valuation` 的成败只看 `after >= plan.latest`（L1156，全局 max），逐码落后多少完全
     不进 detail/run_end；上一轮修了"全局末日被少数新码撑起来"，但只修到了 collector 内部，**日更层的判据
     还是全局 max**。
  2. 因为判据是 `== until`，停牌股永远不满足 → **每天都被重抓**，`progress.json` 的该区间永远不完成。
     代价是每日重复请求数，目前没有量化数据；修法应是"末根 < until 且源端返回空 ⇒ 记 `no_data_asof` 侧车"，
     而不是放宽成"最近 N 天"（那会真的把缺口永久标完成）。

## 3. 上一轮改动引入的新问题

1. `--detach` 与默认 dry-run 互斥失败（§2.1 第 1 条），exit 3 会造成"启动失败"的错误结论。
2. `--detach` 把"子进程在 run_start 之前就正常失败"统一掩盖为 `no run_start`，丢失 `lock_blocked`/
   `batch_rejected`/未知步骤键的真实原因与退出码（§2.1 第 2 条）；上一轮文档里的冒烟证据与此矛盾。
3. `lock_blocked` 事件本身是好的；但上一轮没动归档路径，`os.replace` 的无校验竞态依旧（§2.3），
   而 detach 让"拉起失败后重跑"更容易发生，撞上该竞态的概率被放大。

## 4. 优化建议（只保留有收益的）

按优先级，前两条建议先做：

1. **把"每步耗时 + 等待状态"落盘（≈0 成本，是所有优化的前提）**
   `_run_apply` 已经有 `_StepOutcome.seconds`（L1753），`run_end` 里只写了整轮 `seconds`（L2964）。
   改成 `steps: [{key, ok, seconds}]` 即可；同时 `FactsCache` 的 `hits/misses/recomputed` 一并写进去。
   另外 `_await_tdx_landing` 的等待改用 `logger.warning` 或直接 `_log_event('tdx_landing_wait')`——现在是
   40 分钟静默（§2.2），这条不是性能优化而是可观测性缺口。
2. **修 detach 的失败语义 + 陈旧锁归档加二次校验**
   - detach 子进程不支持 run_start 前的场景：`--detach` 时若是 dry-run 直接前台执行并说明；否则让子进程
     在 `main` 入口就写一条 `bootstrap` 事件（或把 `run_start` 提前到取锁之后），`_verify_detach` 依据
     "bootstrap/run_start/子进程退出码"三条判，失败时把子进程真实退出码透传，而不是恒 3。
   - `os.replace` 前重读锁内容（pid + started_at 必须仍等于 stat 时读到的值），归档名加 pid/uuid 后缀，
     `os.replace` 包 try 处理 `FileNotFoundError` 后重试整轮。这是唯一可能造成"双写数据"的项。
3. **致命步补硬超时**：`fill`/`build`/`fund_quote`/`factor`/`manifest`/`backup`/`gate`/`dataset_health` 无超时，
   而 11-25 全量 6746s 且 manifest 失败是现成证据。建议给 build(含 TDX 等待) 显式上限
   （2400 + 构建预算）、manifest/backup/gate 各给一个宽上限（超时按失败记，不污染数据）。
4. **`failed_noncritical.exit` 的 `rc=0 但判 False` 解析缺陷**（§2.5）：末日断言这类"rc=0 + 判据失败"应写
   `exit=None` 而不是 0，否则告警行等于在说"退出码 0 却失败了"。
5. **估值日更层加逐码可见性**：detail 追加 `落后 N 只`（collector 已有逐码末根，只差透传）。属观察项，
   不改判据、不放宽阈值。
6. **不做的事**：不给 hash_cache 加抽样校验（无耗时数据支撑）、不缩短 TDX 轮询间隔（会放大全目录扫描）、
   不改任何静默跳过为失败（会改变既有口径与退出码语义，需单独议题）。

## 5. 待补用例清单（供后续实现）

- detach：dry-run + detach（应成功）／run_start 前失败（应透传真实原因）／旧日期同 pid run_start（应判失败）／
  日志 >400 行时 run_start 在窗口外／中继 20s 超时但子进程已 breakaway。
- TDX 守卫：路径不存在、目录存在但无 lday、等待中目录被删除（应区分"缺失"与"未发布"）。
- 锁：两进程同时归档陈旧锁（不得双写、不得抛未捕获异常）／`_release_lock` 遇到被替换的锁。
- `failed_noncritical`：`rc=0 + 判据失败` 的 exit 必须是 null；抛异常形态的 detail。
- 估值：停牌股（末根 < until）应被重抓且计入"落后码"，不得被全局 max 掩盖。
