## 2. 谁事实上作准（按证据，不看命名）

### 2.1 调用点数量与性质

| 支 | 生产调用点 |
|---|---|
| 配置支 `freshness` | `src/data/local_store/build.py:1213-1241`（补数收尾，唯一写审计产物）、`tools/daily_data_gate.py:78`、`tools/daily_advice.py:159`、`tools/data_freshness_check.py:29`（CLI，支持 `--fail-on`） |
| 硬编码支 `freshness_check` | `tools/daily_update.py:1212`（步骤 22「保鲜体检」，`daily_update.py:340` 标注 **critical=False**）、`src/main.py:221`、`tools/daily_data_gate.py:96`、自身 CLI |

数量上两支接近（4 个生产入口 vs 3 个），但**性质不同**：配置支占住了"写产物"和"可 `--fail-on`"两个可审计位；硬编码支占住了日更步骤和主入口，但该步骤非致命。

### 2.2 谁决定退出码

- `tools/daily_data_gate.py:218-219` 同时计算 `freshness` 与 `freshness_summary`，`:233` `passed = all(item['passed'] ...)` → **两支都能单独否决 gate，属联合作准**。
- `daily_update.py:340` 的 `('freshness','保鲜体检', False)` → 该步骤失败**不**让日更失败（第三位是 critical 标志）。
- `build.py:1209-1210` 注释自述"非致命：需要卡口时用 `tools/data_freshness_check.py --fail-on`"。
- 结论：**两支都只在 gate 一个点上真正具备否决权**，日更与补数链路都只是告警。

### 2.3 最近一次实际判红/判绿（决定性证据）

`artifacts/data_gate/gate_20261110..20261125`，共 12 份：

| 报告 | gate | 配置支 critical / warn | 硬编码支 error / warning |
|---|---|---|---|
| 11-10 | 通过 | 0 / 7 | 0 / 0 |
| **11-11** | **失败** | 0 / 9 | 0 / 0 |
| 11-12~20 | 通过 | 0 / 0~7 | 0 / 0~5 |
| 11-24 | 通过 | 0 / 1 | 0 / 0 |
| **11-25** | 通过 | 0 / **11** | 0 / **0** |

- 唯一一次 gate 失败（11-11）的失败项是 `factor_consistency`（fund 633 只不一致），**两支保鲜都不是否决者**（`freshness.passed=True`）。
- 12 份报告里两支的 critical/error **恒为 0**，从无一次靠保鲜判红。
- 11-25 同一天两支给出**相反结论**：配置支 11 条 warn（A股日线、指数日线、基金日线、估值、换手、复权、广度、ST 快照、ST 面板、涨跌停、两融），硬编码支 0 条。差异随时间只增不减（11-25 的 warn 就是"盘中 today 锚点"造成的假警报）。
- 硬编码支在 11-17/18/19 分别报过 5/2/3 条 warning，配置支同期 0 —— 说明硬编码支在"相对锚点 + 相对宽阈值"下确实会独立报警，**不是死代码**。

**结论（作准判定）**：现状没有单一作准支，而是「双轨并列、只有 gate 一处联合否决」。从信号质量看，**配置支是事实上的主口径**（24 个数据集、覆盖占比、声明校验、唯一产物），但它带 today 锚点导致每日误报；硬编码支是**事实上的降噪/补充层**（相对锚点 + 停更登记 + 文档守卫），但它覆盖面窄且不落盘。归一应"以配置支为引擎，吸收硬编码支的三项独有能力"，而不是二选一删掉。

## 5. 验证方式（不跑整轮日更）

1. **双跑对照（核心）**：新增只读脚本 `tools/freshness_parity.py`，对同一 `store_root`、同一 `as_of=quotes_end` 分别调 `freshness.check_all(root, today=as_of)` 与 `freshness_check.run_check(root)`，按 `rel_path ↔ config.source.path` 映射成 37 行（24+13，去重后按路径对齐），输出三态差分：`ok/warn/critical ↔ ok/warning/error/known_exception`。验收线：**红绿一致率 100%**，黄级差异逐条列原因（锚点/阈值/覆盖面）。
2. **历史回归（零成本）**：把 `artifacts/data_gate/gate_*.json` 近 12 份里两支的字段提取出来做基线（本次已提取，见 §2.3），归一后对同样日期重算，要求：11-25 的 11 条 warn 归零；11-17/18/19 的 5/2/3 条 warning 至少在归一后的 known_exception 明细里可见。
3. **单测**：`tests/test_freshness_parity.py`，用固定 fixture store，断言（a）24 个 config key 与 13 行视图双向覆盖；（b）`stale_status` 命中项在两支里都是"不计缺口"；（c）指数末根断裂在两支里都判红。
4. **命令级 diff**：`python -m src.data.quality.freshness --json` 与 `python -m src.data.quality.freshness_check --json` 输出按 key 排序后 diff（归一后应可互相推导）。
5. **计数先对齐**：任务里说的"47 个数据集"与现状不符（配置 24、硬编码 13）。归一前必须先确认 47 的出处——若指 `docs/数据权威路径清单.md` 的固定路径总数，则需在 config 中建立"路径 → 数据集"映射后再谈覆盖率；否则"对 47 个数据集跑两支"这一步无法直接实现。

## 6. 建议实施顺序

1. 先在 config 建 `rel_path` 映射与 `anchor` 字段（不改判据，只加元数据），跑双跑脚本拿基线差分。
2. 引入 `known_exception` + `stale_registry`，验证 5921/2646/1366 全集判定不变（这一步是"绿不变红"的守门）。
3. 切换锚点到 `quotes_end`，验证 11-25 的 11 条 warn 归零、11-17~19 的 warning 仍能被解释。
4. 把 `freshness_check` 改成薄封装，跑 5 个相关测试文件。
5. 最后把文档登记守卫迁进测试并在 gate 保留一次调用。

不要在同一个提交里同时做"加能力"和"切锚点"，否则差分无法归因。
