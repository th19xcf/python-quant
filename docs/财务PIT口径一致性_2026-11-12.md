## 结论先行

1. **三套口径的分歧在当前数据上为 0 条**：正式三表里每个 `(ts_code, end_date)` 只有 1 行
   （income 344,703 行 = 344,703 个报告期；balance 330,299 = 330,299；cashflow 328,708 = 328,708），
   分片层同样 0 个多公告报告期。三条路径取到的 `ann_date` 与因子值逐值相同。
   「更正导致三套结果不同」是**代码层潜在风险**，不是今天的数值事实。
2. **真正的现存分歧在 TTM 守卫**：`fundamental_factors.ttm_from_cumulative` 没有
   「上年年报/上年同期公告日 ≤ 本期公告日」守卫，`build_new_factors.ttm` 有。
   净利润 **7,977 期（3.258%）**、营收 **7,997 期（3.267%）**、经营现金流 **7,312 期（3.085%）**
   在两条路径上一个有值、一个为 null；2015 年后仍各有 864 / 863 / 1,047 期。
   落到 `ff_value_ep` 的 142 个月面板上：**2,366 / 567,541 格不同，108 / 142 个月排名发生变动**，
   最大位移 3,326 位（2023-08-31），最大 TTM 差 55.82 亿元。
3. **静默前视（第 3 项）**：新浪旧报表段 1,376 行占位（income 720 / balance 649 / cashflow 7）
   **结构上会被三套实现当作 `ann_date` 使用**（三条路径都只校验 `ann_date` 非空，全仓没有一处按
   `ann_date_source` 过滤），但 1,376 行**全部早于 2010-01-01**、且**没有一行是所在股票的最后一期**，
   当前 142 个月面板（2015-01-30 起）**实际受影响月份 = 0**。若面板前移到 2010 年前，
   暴露量为 income 10,868 / balance 9,617 / cashflow 89 个月格。
4. **附带发现（比占位行更值得处理）**：income 有 **73,450 行（21.308%）`ann_date` 晚于法定披露截止日**
   （`sina_publish` 52,150 / `em_notice` 21,300），balance 27,270 行（8.256%）、cashflow 47,984 行（14.598%）。
   方向保守（晚可见不会前视），但它正是第 2 条守卫冲突的根因：该列不能单独当可信边界。
5. **建议统一口径**：版本选择用 `store` 的「截至 t 已公告的最新一版」，TTM 用 `build_new_factors` 的
   `usable` 守卫，读取侧增加 `ann_date_source` 白名单。依据见第五节。

- 三条路径**都没有**按 `ann_date_source` 过滤（全仓 `src/` 内 `ann_date_source` 只出现在

**一个容易漏掉的 B 侧行为**：因为 B 先把每期折叠成「全局最新版」再按 `ann_date <= t` 截断，
若某期的更正公告发生在 t 之后，该期在 t 时刻会**整期消失**（而不是退回更早版本）。
这与 A 的「按 t 取最新可见版」并不等价——A 在 t 时刻仍能看到旧版。该差异在今天的单版本数据下为 0，
但一旦恢复多版本就会立刻显形。

## 五、建议：三套口径统一成哪一套

**建议的统一口径 = A 的版本选择 + C 的 TTM 守卫 + 新增 `ann_date_source` 白名单。**
即：「截至 t 已公告的**最新一版**报告期」+ 「上年年报与上年同期的公告日都必须 ≤ 本期公告日」+
「占位行与超期行按来源标记降级」。

为什么不是直接选现有三套中的一套：

1. **版本选择取 A（最新可见版），不取 C（最早版）。**
   今天是 0 条多版本记录，换口径的历史重算成本为 0，风险最低；
   而「最早版」在发生追溯调整后会长期停留在旧值上，与「PIT = 截至 t 可得的最新信息」的定义不符。
   代价是：一旦恢复多版本，A 的读取顺序（读 → 过滤 → 排序）比 C 的「先折叠再截断」更安全，因为 C 的写法在
   更正日期晚于 t 时会**整期丢失**（见第一节末尾）。
2. **TTM 必须采用 C 的 `usable` 守卫。** 这是当前唯一有实测差异的一环：
   7,977 / 7,997 / 7,312 期在无守卫时会把「尚未公告的上年年报」计入 TTM，
   在 `ff_value_ep` 上造成 2,366 格取值不同、108 个月的横截面排名变动、最大 55.82 亿元的 TTM 差。
   这是本次核查中**唯一会实际改变今日因子值**的缺陷。
3. **占位行与超期行必须按来源过滤，而不是按日期条件绕过。**
   1,376 行占位当前暴露 0 个月纯属窗口巧合（面板 2015 起、占位全部 ≤ 2009）；
   73,450 行超期则已经在制造守卫冲突（2010 年集中 5,053 期）。
   建议在采集侧给这两类行加独立标记（现有 schema 只有 `ann_date_source` 三值，
   需新增如 `report_period_placeholder` / `late_filing` 或独立的 `ann_quality` 列），
   读取侧统一按白名单取，避免下游各自写条件。
4. **不建议按「最大值/最小值」这种列级聚合统一**：它会掩盖同日多期（年报与一季报）场景，
   而 A 与 B 都已经用 `end_date` 做了正确的二次排序，这部分应保留。

落地顺序建议（均需单独立项、改 `src/` 时另走提交）：① 补 TTM 与同比守卫（唯一影响今日数值）；
② 采集侧标记占位/超期；③ 读取侧白名单 + 用本文件的 4 个 xfail 用例转为正常断言作为验收。
另注：C 与 D（`research_candidates.py`）是同一套逻辑的两份代码，①必须同步改，
否则研究候选因子与正式因子会在守卫上分叉。
