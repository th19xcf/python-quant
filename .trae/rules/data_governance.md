# 数据处理红线（always-on）

本文件是数据治理的**判定层**：只写「必须做什么 / 不许做什么」，每条都能用「是 / 否」核对。
怎么做（六阶段流程、每阶段证据清单）见技能 `.trae/skills/data-curation/SKILL.md`，本文件不复述步骤。

## 与 project_rules.md 的关系

本文只写增量判定，不复制既有规则。以下内容一律以 `project_rules.md` 为准：

| 主题 | 见 `project_rules.md` 哪一节 |
|---|---|
| 提交格式、5 块报告、commit message 无空行无 BOM | 「Git 提交规则」「备份仓库提交规范」 |
| 备份范围四类、增量同步命令、集合求差镜像 | 「备份同步规则」 |
| 并行边界、网络采集限流、超时催办、提交串行、验证不通过先停 | 「任务调度与超时处理规则」 |
| 删除 `data/`、重写历史、清空备份、批量清理工作区 | 「数据与历史安全规则（红线）」 |
| 什么情况下必须先停手请示 | 「决策授权规则（带建议即执行）」 |

本文与 `project_rules.md` 出现冲突时，以 `project_rules.md` 为准，并回头修本文，不允许两处并存不同说法。

## 一、唯一正式数据

- **DG-1** 每类语义只允许存在一个正式路径。新旧两套并存即判定为缺陷，不是「兼容期」。
  依据：项目记忆「校验通过的正式数据只保留一份，代码中只允许出现该路径」。
- **DG-2** 代码里只允许出现那一个正式路径，禁止「新路径不存在就回落旧路径」之类的兼容分支。
  反例：两套派生数据并行，会让同一份回测在不同入口得出不同结论。
- **DG-3** 权威路径的唯一清单是 `docs/数据权威路径清单.md`。新增或迁移正式路径必须在该文档登记（语义 / 唯一正式路径 / 消费者 / 为什么是它），并把被取代的旧路径写进「已废弃路径」表；未登记即视为没有正式路径。不可重建资产另需进入 `CRITICAL_FILES` / `CRITICAL_DIRS`，派生数据另需写同目录 `manifest.json`。
- **DG-4** 正式路径不得带版本号；版本、口径哈希、上游 mtime、行数、只数写进同目录 `manifest.json`。
  依据：项目记忆「路径固定不带版本号」；反例 `meta/industry/industry_20261105_v2.parquet` 因 `_v2` 后缀无法解析成日期、永不被自动选中，已移入 `_backup` 退役。
- **DG-32** `data/local_store/` 只存放「运行时被消费、语义唯一」的正式数据；「需要备份」「怕丢」「暂时没处放」一律不得作为进入该层的理由。
  三层归属唯一：正式数据 → `data/local_store/`（配 `manifest.json` 并登记权威路径清单）；体积小且需长期可追溯的证据与小输入 → 进 Git（`docs/evidence/<主题>/`，该目录随 `docs/**` 由 Git 跟踪与镜像，不另行登记权威路径清单）；可重算的中间产物与断点 → `_staging/<任务>_<日期>/`。
  入层三问，任一为否即不得入：① `src/` 或 `tools/` 中存在真实消费者；② 同语义不存在第二份；③ 丢了能说清重建路径，或本身不可重建且必须长期保留（不可重建且需长期保留的，另按 DG-3 登记 `CRITICAL_FILES` / `CRITICAL_DIRS`）。
  采集与构建的中间态不得落在 `data/local_store/` 正式目录内：财务采集分片、重建断点、临时研究面板一律走 `_staging/`。
  依据：2026-11-12 审计实测——`meta/financials/parts/` 下 1,285 个采集分片 / 1.38 GB 落在正式目录；`factors/_bench_last.parquet` 96 MB 零代码引用；`factors` 整层无 `manifest.json`；同期 14 类在用数据未登记权威路径清单。该层同时存在「该进的没进」与「不该进的进了」两类缺陷。
  反例：把 15 KB 的审计输入 CSV 放进 `data/local_store/meta/anomalies/inputs/`，理由是「它需要备份」——备份需求不构成数据语义，该件应进 `docs/evidence/` 由 Git 承担留存。

## 二、候选隔离与原子替换

- **DG-5** 候选数据只能存在于 `_staging/<任务>_<日期>/`（仓库根，**不在** `data/` 之下；权威定义见 `src/data/staging.py`），不得写在正式文件同目录。
  依据：该根已在 `.gitignore` 中、不进入任何取数/回测/展示链路；`_staging/` 下已有 `backfill_20190917`、`research_rebuild_20261109`、`delisted_backfill_20261109`、`turnover_local_parts` 等按任务命名的先例。
  反例（已退役）：曾用 `data/local_store/_staging/`，因长在 `data/` 底下，不得不为它单开一条删除例外，等于削弱「`data/` 一律不删」。2026-11-10 已整体迁至仓库根，原路径不再使用，也不要再往里写。
- **DG-6** 禁止在正式目录留下 `*_candidate.parquet`、`*.new`、`*.bak` 这类过渡文件。
  反例：过渡文件会被下一次取数按通配命中，半成品直接进入正式结论。
- **DG-7** staging 内必须有可断点记录的进度文件（`progress.csv` / `progress.json` 或等价物）与失败清单（`failed.csv`）；中断后必须从断点续跑，禁止从零重跑。
  说明：DG-8 已于 2026-11-10 随 staging 根目录迁出 `data/` 而**整条取消**——当时那条「`_staging/<本次任务>/` 是 `data/` 禁止删除的唯一窄例外」的条款已无存在必要。现在 `data/` 恢复为真正一律不删（与「数据与历史安全规则（红线）」一致，无任何例外）；本次任务候选目录的清理仍照做，但按 `_staging/` 归属处理，不再借用 `data/` 的例外条款。
- **DG-9** 覆盖正式文件必须走 `src/data/atomic_write.py` 的 `write_parquet_atomic` / `write_text_atomic`（临时文件 → fsync → `os.replace`），禁止直接 `write_parquet` 覆盖。
  依据：该模块文档写明「写一半失败时目标文件保持原样」。
- **DG-10** 不得把多个文件的替换当成一个事务。`os.replace` 只保证单文件原子；跨文件更新必须显式说明顺序、失败残留状态与回滚方式。
  依据：`src/data/atomic_write.py` 第 9-11 行「单文件原子，不等于多文件事务」。
- **DG-11** 派生数据替换前，必须把现有正式目录整体移到 `_backup/`，不得直接删除或用新内容就地覆盖。`_backup/` 位于**仓库根**（与 `_staging/` 同级），不在 `data/` 之下；`data/` 恢复为一律不删、无任何例外。
  依据：项目记忆「替换时先将现有正式目录整体移动到备份目录，保留完整回滚能力」。
  `data/` 下不再允许出现任何 `_backup`；写快照一律写仓库根 `_backup/`，并按原数据层分子目录，这是 DG-11 / DG-13 的路径口径。

## 三、`_backup/` 边界与旧表退役

- **DG-12** `_backup/` 只承担回滚快照职责，禁止进入任何取数、缓存、回测、展示链路。
  依据：`src/` 全目录没有任何 `_backup` 读取；仓库内唯一把 `_backup` 当数据对照输入的是 `tools/fill_internal_gaps.py:472-480` 的 `_backup_dir_for`，用途只是证明补数前后的行差异（`tools/cleanup_archives.py` 仅扫描目录评估去重，不把内容送进任何数据链路）。
- **DG-13** 被取代的旧表移入仓库根 `_backup/<语义>_<日期>/`（`data/local_store/` 层快照直接落 `_backup/<语义>_<日期>/`，`meta/` 层落 `_backup/meta/<语义>_<日期>/`）并从正式目录移除；是移动而不是删除，且必须给出移动前后 SHA256 一致证明。
  先例：`docs/数据权威路径清单.md` 的「已废弃路径」表逐条记录原路径、移入位置、SHA256 与废弃原因。
- **DG-14** 不得新增任何「默认读 `_backup`」的路径常量、配置项或 fallback。出现即为把快照当数据源。

## 四、外部库与本地推导

- **DG-15** MySQL 数据未经校验，不得作为「哪个值对」的标尺；它只能解释「差异从哪来」。
- **DG-16** 正式字段必须由已验证来源推导：本地行情首末行、名称快照、公告与退市证据、通达信 `.day`。推不出的字段宁可留空，并逐列写明依据，禁止从库里抄。
- **DG-17** 「以库为准修正本地」一律判定为违规，除非该库值已由独立第二源对拍通过并留下证据。
  反例：2026-11-05 分红表漂移中，2 只标的是被接口改写错误金额，按库改会改错。
- **DG-18** 两源冲突且无第三证据时，必须登记 unresolved 并保留本地存量，不得择一覆盖。
- **DG-19** 混源字段必须逐字段可追溯，禁止整行打一个来源标记掩盖混源。
  依据：`valuation_daily` 的 `source` 列采用 `pe=<来源>|pb=<来源>|dv=<来源>|mv=<来源>` 字段级语法的先例。

## 五、完成与留证

- **DG-20** 声称完成时必须同时给出四项：行数守恒、逐值对拍（含「既有非空值改动数为 0」）、受影响文件 SHA256、抽样断言。缺任意一项即为未完成。
- **DG-21** 禁止用「基本一致」「应该没问题」「与预期相符」作为结论；结论必须带数字与可复现命令。
  依据：项目记忆「不得使用模糊结论，归档后冒烟验证需与既有产物逐值比对完全一致」。
- **DG-22** 改数据前必须 `copy2` 备份并记录新旧 SHA256；改完必须自证影响面：改了哪些文件、哪些行、哪些标的。
- **DG-23** 必须验证下游一致性：至少用一条真实读路径端到端跑通，证明新文件确实被读到；只验证文件本身不算通过。
  依据：`extended_contracts.py` 记录过「没数据 ⇒ 约束不生效，结论看起来正常但存在系统性偏差」。
- **DG-30** 对拍与逐值校验必须比对消费方实际读取的字段，不得只比原始列。字段存在 `fill_null`、覆盖层、有效层派生时，先确认消费方读的是哪一层，再确定对拍对象。
  同一字段有「原始 + 修正」两层时，两层必须分别给出结论；只比原始列得出的差异，一律不得直接判定「哪边错」。
  反例：2026-11-10 分红表全量对拍只比 `cash_div`，判出 14 条「本地错」；因子实际读 `cash_div_fix.fill_null(cash_div)`，14 条在有效层全部正确、除权参考价残差 0.000000。按第一轮结论改原始列会把已修好的值改回去，并抹掉 raw+fix 追溯设计。
- **DG-31** 写回正式数据的映射 / 更新操作必须有显式兜底分支：未命中任何分支时必须写回原值或直接报错，禁止用 `pl.coalesce([when/then...])` 这类无兜底表达式让未命中行默认变成 null。
  行数守恒、改动行数、逐值对拍这类断言，必须同时校验空值计数：改动前后各自的 null 数、未命中行是否被写成 null；禁止只用 `!=` / `==` 与 null 组合这类会静默为假的比较作为通过条件。
  断言必须能对「空值从 0 变成 N」这一情形失败，即断言本身要有自测或反例验证。
  反例：2026-11-10 ST coverage 写回 64 行裁定时 `pl.coalesce` 无兜底，5,824 行 `coverage_start` 被写成 null；断言用「改动行数 `!=` 裁定行数」比较，null 参与比较得 null 被过滤，断言空过，含 5,824 个空值的表被当作合格产物落盘，并对外报了「行数守恒、改动行数恰等于目标」。

## 六、范围与采集

- **DG-24** 只改本次任务范围内的文件。他人未提交的 `M` / `??` 一律不修、不清、不顺手带进提交。
  依据：「任务调度与超时处理规则」中「工作区里的 M/?? 可能是在途成果」。
- **DG-25** 外部采集同时最多 2 条任务、单连接串行 + 节流；遇限速、封禁、连续超时、返回空立即停压并如实报告。具体执行口径见 `project_rules.md`「任务调度与超时处理规则」的「网络采集限流」条。
  数据侧补充判定：返回空必须先区分「源端确实没有」与「链路未接线 / 开关未开 / 时间范围错」，再决定是否换源。
- **DG-26** 不得为推进而放宽断言、下调阈值、删除用例、忽略失败项。判定见 `project_rules.md`「任务调度与超时处理规则」的「验证不通过先停后报」条。
- **DG-27** 不得把「未接线」当成「无数据」下结论。取数为空时先查路径常量、数据源开关、时间范围与表清单，再判定缺失。
  反例：`data.allow_remote_sources` 默认关闭时返回空，曾被误读为「该标的无数据」。

## 七、备份镜像

- **DG-28** 交付与收口时的备份范围、镜像口径、增量同步命令一律见 `project_rules.md`「备份同步规则」，本文只加一条判定：镜像前后各做一次相对路径集合差，差额必须为 0。
  反例：曾按 mtime 筛选备份，实测缺 1,591 个文件（13.9%），其中含 `_backup/` 回滚快照。

## 八、决策与停手

- **DG-29** 只有三类必须停手请示：不可逆操作（删除 `data/`、重写 Git 历史、清空备份）、外部条件不具备（源端无数据、限流封禁、无权限）、改变既定口径且无实测证据。其余自行决策并事后记账。判定与记账格式见 `project_rules.md`「决策授权规则（带建议即执行）」。
  数据侧对「改变口径」的补充枚举：把推导管径改为外部源、调整 `strict` 名单、改前复权 / 后复权口径、放宽对拍容差、变更准入阈值。以上任一发生且无实测证据，即落入必须停手的一类。
