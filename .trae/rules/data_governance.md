# 数据处理红线（always-on）

本文件是数据治理的**判定层**：只写「必须做什么 / 不许做什么」，每条都能用「是 / 否」核对。怎么做（六阶段流程、每阶段证据清单）见技能 `.trae/skills/data-curation/SKILL.md`，本文件不复述步骤。历史实测反例、事故经过与数字基线见 `docs/数据治理判例与基线_2026-11-13.md`（下称「判例」，锚点为 §7.x），判定语义与迁出前等价，逐条对照见判例 §8.2。

## 一、唯一正式数据

- **DG-1** 每类语义只允许存在一个正式路径。新旧两套并存即判定为缺陷，不是「兼容期」。依据见判例 §7.13。
- **DG-2** 代码里只允许出现那一个正式路径，禁止「新路径不存在就回落旧路径」之类的兼容分支。依据：两套派生数据并行会让同一份回测在不同入口得出不同结论。
- **DG-3** 权威路径的唯一清单是 `docs/数据权威路径清单.md`。新增或迁移正式路径必须在该文档登记（语义 / 唯一正式路径 / 消费者 / 为什么是它），并把被取代的旧路径写进「已废弃路径」表；未登记即视为没有正式路径。不可重建资产另需进入 `CRITICAL_FILES` / `CRITICAL_DIRS`，派生数据另需写同目录 `manifest.json`。
- **DG-4** 正式路径不得带版本号；版本、口径哈希、上游 mtime、行数、只数写进同目录 `manifest.json`。依据与反例见判例 §7.1、§7.13。
- **DG-32** `data/local_store/` 只存放「运行时被消费、语义唯一」的正式数据；「需要备份」「怕丢」「暂时没处放」一律不得作为进入该层的理由。
  - 三层归属唯一：正式数据 → `data/local_store/`（配 `manifest.json` 并登记权威路径清单）；体积小且需长期可追溯的证据与小输入 → 进 Git（`docs/evidence/<主题>/`，随 `docs/**` 由 Git 跟踪与镜像，不另行登记权威路径清单）；可重算的中间产物与断点 → `_staging/<任务>_<日期>/`。
  - 入层三问，任一为否即不得入：① `src/` 或 `tools/` 中存在真实消费者；② 同语义不存在第二份；③ 丢了能说清重建路径，或本身不可重建且必须长期保留（不可重建且需长期保留的，另按 DG-3 登记 `CRITICAL_FILES` / `CRITICAL_DIRS`）。
  - 采集与构建的中间态不得落在 `data/local_store/` 正式目录内：财务采集分片、重建断点、临时研究面板一律走 `_staging/`。实测与反例见判例 §7.10。

## 二、候选隔离与原子替换

- **DG-5** 候选数据只能存在于 `_staging/<任务>_<日期>/`（仓库根，**不在** `data/` 之下；权威定义见 `src/data/staging.py`），不得写在正式文件同目录。
  - 依据：该根已在 `.gitignore` 中、不进入任何取数/回测/展示链路。旧路径 `data/local_store/_staging/` 已于 2026-11-10 整体迁至仓库根，原路径不再使用、也不要再往里写。续跑口径：可续跑任务的分块缓存落点必须**跨运行稳定**——代码内只留任务名、由 `staging_dir_for_store()` 运行时推导，不得带运行日或版本号；只有一次性产物才允许带日期。详见判例 §7.2。
- **DG-6** 禁止在正式目录留下 `*_candidate.parquet`、`*.new`、`*.bak` 这类过渡文件。依据：过渡文件会被下一次取数按通配命中，半成品直接进入正式结论。
- **DG-7** staging 内必须有可断点记录的进度文件（`progress.csv` / `progress.json` 或等价物）与失败清单（`failed.csv`）；中断后必须从断点续跑，禁止从零重跑。
  - 说明：DG-8 已于 2026-11-10 随 staging 根迁出 `data/` 而**整条取消**；`data/` 恢复为真正一律不删（与「数据与历史安全规则（红线）」一致，无任何例外），本次任务候选目录的清理仍照做，但按 `_staging/` 归属处理，不再借用 `data/` 的例外条款。
- **DG-9** 覆盖正式文件必须走 `src/data/atomic_write.py` 的 `write_parquet_atomic` / `write_text_atomic`（临时文件 → fsync → `os.replace`），禁止直接 `write_parquet` 覆盖。依据：该模块文档写明「写一半失败时目标文件保持原样」。
- **DG-10** 不得把多个文件的替换当成一个事务。`os.replace` 只保证单文件原子；跨文件更新必须显式说明顺序、失败残留状态与回滚方式（见 `src/data/atomic_write.py` 第 9-11 行）。
- **DG-11** 派生数据替换前，必须把现有正式目录整体移到 `_backup/`，不得直接删除或用新内容就地覆盖。`_backup/` 位于**仓库根**（与 `_staging/` 同级），不在 `data/` 之下；`data/` 恢复为一律不删、无任何例外。
  - `data/` 下不再允许出现任何 `_backup`；写快照一律写仓库根 `_backup/`，并按原数据层分子目录，这是 DG-11 / DG-13 的路径口径。
- **DG-35** **基础表必须一次改完**：行情、名录、财报、估值、因子、日历、事件这七类基础表的任何改动，必须先穷举该表全部已知待修项，再一次性执行「改动 → 逐值对拍 → 回填索引与 manifest → 重建受影响的下游派生表」；禁止「改几行 → 重建派生 → 再改几行 → 再重建」的反复循环（每轮重建都会把上一轮的派生结果覆盖并漂移）；同一张基础表禁止两路任务并行写。
  - 改动前必须先列出该表的下游派生清单（哪些表 / 哪些列由它派生），确认范围后按「源表 → 派生 → 索引与 manifest → 验证」单向推进，禁止边改边重建。
  - 与 DG-10、DG-11 的关系：三条并列不冲突时同时适用——DG-10 管「跨文件替换不构成一个事务」，DG-11 管「派生替换前先备份」；冲突时以本条为准，即不得用「分批提交 = 多次事务」绕过本条的一次性要求。依据：用户 2026-11-13 判定「对数据的处理，尤其是基础表，要一次处理完毕，不要出现反复互相影响的情况」。

## 三、`_backup/` 边界与旧表退役

- **DG-12** `_backup/` 只承担回滚快照职责，禁止进入任何取数、缓存、回测、展示链路。依据与唯一例外见判例 §7.3。
- **DG-13** 被取代的旧表移入仓库根 `_backup/<语义>_<日期>/`（`data/local_store/` 层快照直接落 `_backup/<语义>_<日期>/`，`meta/` 层落 `_backup/meta/<语义>_<日期>/`）并从正式目录移除；是移动而不是删除，且必须给出移动前后 SHA256 一致证明。先例：`docs/数据权威路径清单.md` 的「已废弃路径」表逐条记录原路径、移入位置、SHA256 与废弃原因。
- **DG-14** 不得新增任何「默认读 `_backup`」的路径常量、配置项或 fallback。出现即为把快照当数据源。

## 四、外部库与本地推导

- **DG-15** MySQL 数据未经校验，不得作为「哪个值对」的标尺；它只能解释「差异从哪来」。
- **DG-16** 正式字段必须由已验证来源推导：本地行情首末行、名称快照、公告与退市证据、通达信 `.day`。推不出的字段宁可留空，并逐列写明依据，禁止从库里抄。
- **DG-17** 「以库为准修正本地」一律判定为违规，除非该库值已由独立第二源对拍通过并留下证据。反例见判例 §7.4。
- **DG-18** 两源冲突且无第三证据时，必须登记 unresolved 并保留本地存量，不得择一覆盖。
- **DG-19** 混源字段必须逐字段可追溯，禁止整行打一个来源标记掩盖混源。先例：`valuation_daily` 的 `source` 列采用 `pe=<来源>|pb=<来源>|dv=<来源>|mv=<来源>` 字段级语法。

## 五、完成与留证

- **DG-20** 声称完成时必须同时给出四项：行数守恒、逐值对拍（含「既有非空值改动数为 0」）、受影响文件 SHA256、抽样断言。缺任意一项即为未完成。
- **DG-21** 禁止用「基本一致」「应该没问题」「与预期相符」作为结论；结论必须带数字与可复现命令。依据见判例 §7.13。
- **DG-22** 改数据前必须 `copy2` 备份并记录新旧 SHA256；改完必须自证影响面：改了哪些文件、哪些行、哪些标的。
- **DG-23** 必须验证下游一致性：至少用一条真实读路径端到端跑通，证明新文件确实被读到；只验证文件本身不算通过。依据见判例 §7.5。
- **DG-30** 对拍与逐值校验必须比对消费方实际读取的字段，不得只比原始列。字段存在 `fill_null`、覆盖层、有效层派生时，先确认消费方读的是哪一层，再确定对拍对象。
  - 同一字段有「原始 + 修正」两层时，两层必须分别给出结论；只比原始列得出的差异，一律不得直接判定「哪边错」。反例见判例 §7.6。
- **DG-31** 写回正式数据的映射 / 更新操作必须有显式兜底分支：未命中任何分支时必须写回原值或直接报错，禁止用 `pl.coalesce([when/then...])` 这类无兜底表达式让未命中行默认变成 null。
  - 行数守恒、改动行数、逐值对拍这类断言，必须同时校验空值计数：改动前后各自的 null 数、未命中行是否被写成 null；禁止只用 `!=` / `==` 与 null 组合这类会静默为假的比较作为通过条件。
  - 断言必须能对「空值从 0 变成 N」这一情形失败，即断言本身要有自测或反例验证。反例见判例 §7.7。
- **DG-33** 绕过 `write_parquet_atomic` + `flush_meta` 的旁路改写（回滚 `copy2`、按行 prune、就地修数）落盘后，必须在同一轮把索引与 manifest 回写到位（该文件的 `rows` / `bytes` / `sha256` / `file_size`）；缺这一步即判该次修数未完成。依据与存量反例见判例 §7.8。
- **DG-34** 含运行时字段的表，SHA256 不能证明内容等价：manifest 的 `generated_at`、表内的 `built_at` / `fetched_at` / `source_mtime_ns` 每次重算都会变，SHA 不等不得推出内容有变，SHA 相等也不得推出同口径一致。
  - 判等价必须按 `(ts_code, date)` 这类业务主键 join 逐列对比，并单独报改动前后空值计数与「既有非空值被改动数」（须为 0，与 DG-31 同源）。两条可用绕开方式与反例见判例 §7.9。

## 六、范围与采集

- **DG-24** 只改本次任务范围内的文件。他人未提交的 `M` / `??` 一律不修、不清、不顺手带进提交。依据：`project_rules.md`「任务调度与超时处理规则」中「工作区里的 M/?? 可能是在途成果」。
- **DG-25** 外部采集同时最多 2 条任务、单连接串行 + 节流；遇限速、封禁、连续超时、返回空立即停压并如实报告。执行口径见 `project_rules.md`「任务调度与超时处理规则」的「网络采集限流」条。
  - 数据侧补充判定：返回空必须先区分「源端确实没有」与「链路未接线 / 开关未开 / 时间范围错」，再决定是否换源。
- **DG-26** 不得为推进而放宽断言、下调阈值、删除用例、忽略失败项。判定见 `project_rules.md`「任务调度与超时处理规则」的「验证不通过先停后报」条。
- **DG-27** 不得把「未接线」当成「无数据」下结论。取数为空时先查路径常量、数据源开关、时间范围与表清单，再判定缺失。反例见判例 §7.11。

## 七、备份镜像

- **DG-28** 交付与收口时的备份范围、镜像口径、增量同步命令一律见 `project_rules.md`「备份同步规则」，本文只加一条判定：镜像前后各做一次相对路径集合差，差额必须为 0。反例见判例 §7.12。

## 八、决策与停手

- **DG-29** 只有三类必须停手请示：不可逆操作（删除 `data/`、重写 Git 历史、清空备份）、外部条件不具备（源端无数据、限流封禁、无权限）、改变既定口径且无实测证据。其余自行决策并事后记账。判定与记账格式见 `project_rules.md`「决策授权规则（带建议即执行）」。
  - 数据侧对「改变口径」的补充枚举：把推导管径改为外部源、调整 `strict` 名单、改前复权 / 后复权口径、放宽对拍容差、变更准入阈值。以上任一发生且无实测证据，即落入必须停手的一类。
