# token 效率规则（按需）

配套文件：固定约束与最小派单样例见 `dispatch-template.md`；计量脚本见 `tools/dispatch_cost_report.py`。
上下文的硬闸门（15 轮 / 约 150 KB / 60 次 / 100 次）仍以 `task-scheduling.md` 为准，本文件只管「同样的活少花 token」。

每条固定三段：**规则 / 为什么 / 违反时的识别信号**。识别信号要能被别人在上一条消息里直接看出，不靠回忆。

## 一、十条规则

### R1 派单固定约束引用化
- **规则**：每单都一样的约束（只读白名单、工作目录锁、提交串行、备份仓惯例、不贴 CSV 与大表正文、回报 ≤5 行、预算与硬停、同主题不重复开单）只写在 `dispatch-template.md` A 段，任务书里用一句引用代替整段复写，只补「本单增量」至多三行。
- **为什么**：这批约束与任务无关，每单重写一遍纯属重复付费；复写还会漂移，同一约束在不同单里出现不同措辞，子会话按哪版执行不可控。
- **违反时的识别信号**：任务书里出现与模板逐字重复的「备份仓 / 不贴 CSV / 回报行数」段落；或模板已改而任务书仍贴旧段；或同一约束在同一单里出现两种说法。

### R2 同主题探查只开一单
- **规则**：同一主题（同一批表、同一份登记表、同一组源接口）的探查只开一单，拿到结论文件后再按结论分头派执行单；执行单只读结论，不重读原始文件。
- **为什么**：定位类工作的成本几乎全在「读同一批文件」，多单并行的边际收益为零，只有重复付费。
- **违反时的识别信号**：两个在跑会话的读取白名单有交集；同一主题出现两份 `work/handoff.md` 且结论重复；第二单的开工动作是重读第一单已读过的表。

### R3 单个结果一条回执
- **规则**：一个任务只回一条结果回执（做了什么 / 关键数字 / 下一步 / 阻塞），过程明细写文件；不得拆成「采集一轮 / 入库一轮 / 校验一轮」多条回报。**单结果单消息**：同一结果只有一条消息，禁止先发半条结论、再补一条修正，也禁止把同一条回执拆成「摘要 + 明细」两条。
- **为什么**：每条回执都要带上下文重述，条数直接放大 token；多段回报里通常只有最后一段含新结论。
- **违反时的识别信号**：同一任务连续 ≥3 条回报且各自不含新结论；某条回报的正文只是过程日志；同一结论在不同回报里重复出现；同一结果出现「先发再补」的两条消息。
- **写回位置**：本节 R3；派单模板 A 段「回报 ≤5 行」处。

### R4 不确定可得的数据先只探源
- **规则**：能否拿到还不确定的数据，先开只探源的小单：预算 ≤10 次调用，产出只有「可得 / 不可得 + 证据路径（接口返回片段、表名、行数）」，明确不写入库；确认可得后再授权落地单。
- **为什么**：探源失败时，落地单的预算已经花在读表、拼字段、写脚本上，是最典型的预算超支来源。
- **违反时的识别信号**：探源单调用明显超过 10 次且已开始写入库 / 回填脚本；或该单没有产物路径、只有口头结论；或源端返回空后立刻加压重试而不是先判定「确无 / 未接线 / 被限流」。

### R5 每单写明预算与回报上限，超支须说明原因
- **规则**：任务书首行固定写「预算 ≤N 次调用 / 回报 ≤M 行 / 只读范围」；回报必带「本段调用数 + 本段耗时（分钟）」；实际超预算时，在回报里单列一行写超支原因与已获得的部分产出，不静默继续。
- **为什么**：没有预算的单无法判断该不该停；没有超支原因的账无法区分「任务本身贵」与「路径选错」。
- **违反时的识别信号**：任务书找不到预算行；回报缺两个成本数；账本里实际调用数大于派单预算而回报没有任何说明。

### R6 大文件只 grep 不整读
- **规则**：登记表、审计报告、日志、清单类大文件先检索定位，只读命中行前后各 30 行；单次读取 ≤300 行且 ≤16 KB；确需整份读必须先报路径 / 字节数 / 行数并取得确认。日志只看尾部约 50 行。
- **为什么**：整份读一次就可能吃掉单会话上下文的一半，且读进来的大部分内容与当前判断无关，后续每轮还要重复付费。
- **违反时的识别信号**：出现整份 Read 登记表 / 日志；同一文件在同一会话里被整份读 ≥2 次；回报里出现「为核对完整通读了……」这类表述。

### R7 提交只回一句
- **规则**：提交与备份同步完成后只回一句「提交成功 + 短哈希」，不贴 5 块模板、文件清单、`git status` 全文；用户点名要明细时才展开。
- **为什么**：提交结果可以用一个哈希定位，清单与状态对用户没有新增判断价值，却固定占用一段上下文。
- **违反时的识别信号**：提交回复出现 5 块、逐文件变更清单、工作区状态全文；同一提交被拆成「提交」「推送」「校验」多条回复。

### R8 超预算 20% 必须硬停
- **规则**：实际调用数达到派单预算的 120% 时立即停手，只回一条：「已用 X/N（超 R8）、已完成部分、剩余步骤、建议」，在该消息发出前不得再发起任何试探性调用（换接口、换路径、加一次核对都算继续试）。允许继续的唯一情形是用户当轮明确放行并给出新上限。
- **为什么**：本轮超支全部集中在收尾核对（ST 面板 73/50、两单 12/10），说明超支不是任务贵，而是「再多试一次」的惯性；不设硬停线，预算只是建议值。
- **违反时的识别信号**：台账 `tool_calls / budget_calls > 1.2` 且 note 无「超支」说明；单条会话在超线后仍出现新工具调用；回报只写「还在处理」而不写超支与剩余步骤。
- **写回位置**：本节 R8；台账 `budget_calls` 列（`tools/task_ledger.py add --budget-calls`）；复核用 `tools/dispatch_cost_report.py --overrun-pct 20`（命中标 `R8 超预算超20%`）。

### R9 核对类任务预算起算 10 次
- **规则**：确认既有状态、备份仓核对、登记表对照、口径复核这类「核对类」任务，任务书预算不得低于 10 次调用（写死起算值）；低于 10 次的预算单视为任务书不合格，先改预算再派，不得以「顺手看一眼」压到 3~5 次。
- **为什么**：本轮两单收尾 12/10 的超支正是核对动作被低估：核对需要先定位文件、再比对、再落结论，天然比「读一眼」贵。
- **违反时的识别信号**：任务书预算 <10 且标题/描述含「核对 / 确认 / 复核 / 对拍 / 备份仓」；或用探源单预算（≤10）承接实际是收尾核对的任务。
- **写回位置**：本节 R9；派单模板预算行（低于 10 次的核对单在派单时就判不合格）。

### R10 主会话禁止零信息占位消息
- **规则**：主会话在等待子会话或长任务时，不得发送「等它回来」「稍等」「继续等待」「正在处理」这类不含新事实的消息；一轮内只发两类消息——派单说明与结果回执。确实需要长时间等待时保持静默，由结果消息触发下一轮。
- **为什么**：本轮主会话在结果未到时连发十几条零信息句子，每条都要重述上下文，纯消耗；且这些消息不改变任何执行状态。
- **违反时的识别信号**：同一轮出现 ≥2 条正文不含数字、文件路径或结论的消息；消息内容可被「仍在等待」一句完全覆盖；连续消息之间没有任何工具调用。
- **写回位置**：本节 R10；复核记录里按「轮次消息数 / 有效消息数」观测。

## 二、每周复核（闭环入口）

**看哪张表**：`python tools/dispatch_cost_report.py --days 7 --min-calls 30` 的输出表。数据来自两处，均为本地只读——
1. `logs/task_ledger.csv`：`session_id` / `title` / `phase` / `tool_calls` / `budget_calls` / `duration_min` / `rounds`；
2. `work/<任务名>_<YYYY-MM-DD>/`：产物文件数（排除 `__pycache__`）、报告字节数（`.md`）。

**什么阈值触发规则修改**（命中任一即复盘，不追求全绿）：
| 信号 | 阈值 | 对应规则 |
|---|---|---|
| 单任务调用数 | ≥ 60（硬停线） | R5 |
| 调用数 / 预算 | ≥ 1.2（达预算 120%） | R8 |
| 核对类任务派单预算 | < 10 | R9 |
| 单轮零信息消息 | ≥ 2 条 | R10 |
| 调用数 / 产物文件数 | ≥ 20 | R2 / R4 |
| 报告字节 / 调用数 | < 100 B（且调用数 ≥ 30） | R3（产出太薄，回执却很多） |
| 台账 `tool_calls=unknown` 占比 | > 30% | R5（没记账，闸门失效） |
| 无 work 目录但调用 ≥ 40 | 出现即看 | 先判是否代码类任务，再决定是否计 R5 |

**超支率怎么算**：`tools/dispatch_cost_report.py` 读台账 `budget_calls`；`tool_calls / budget_calls >= 1.2` 即命中 R8。历史行没有该列时脚本单列「预算不可得」，不得按 0 或按估算值补齐。

**改完写回哪个文件**：
- 属「已有规则没被遵守」→ 在该规则条目下追加一行实测依据（日期 + 任务 + 数字），不新增条目；
- 属「模板缺这条约束」→ 改 `dispatch-template.md` A 段，并同步本文件对应条目的措辞；
- 属「全新失效模式」→ 在第一节新增 R8 起条目，同时在 `99-index.md` 更新本文件说明；
- 每次复核在下面「复核记录」追加一行，作为下次复核的入口。

**复核记录**（append-only，一行一次）：
格式：`- YYYY-MM-DD | 命中 <任务或信号> | 改动 <R# / 模板段 / 无> | 结论 <一句话>`
- 2026-11-22 | 建立规则与脚本（首版） | 新增 R1-R7 + 模板 + 脚本 | 下一轮复核从本表开始
- 2026-11-22 | 近 2 天台账 82 单 / 有调用数 28 / 缺失 54（65.9%）/ 合计 683 次、35 个 work 产物目录；本轮实测超支 3 单（73/50=+46%、12/10=+20%、12/10=+20%），台账预算列缺失故超支率与每单回执行数均不可得 | 新增 R8/R9/R10 + 强化 R3；`task_ledger.py` 增 `budget_calls`，`dispatch_cost_report.py` 增预算维度 | 超支集中在收尾核对，已设 20% 硬停与 10 次起算；下轮起预算必须入账才能算命中率

## 三、自检三问（每次派单前，各一句话）

1. 这单的固定约束是引用模板，还是又整段复写了？
2. 这单的预算与回报上限写在哪一行，超支时谁来报？
3. 同一主题是否已有在跑会话或结论文件？有就引用，不再开单。
