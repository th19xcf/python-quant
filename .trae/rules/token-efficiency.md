# token 效率规则（按需）

配套文件：固定约束与最小派单样例见 `dispatch-template.md`；计量脚本见 `tools/dispatch_cost_report.py`。
上下文的硬闸门（15 轮 / 约 150 KB / 60 次 / 100 次）仍以 `task-scheduling.md` 为准，本文件只管「同样的活少花 token」。

每条固定三段：**规则 / 为什么 / 违反时的识别信号**。识别信号要能被别人在上一条消息里直接看出，不靠回忆。

## 一、十条规则

### R1 派单固定约束引用化
- **规则**：每单都一样的约束（只读白名单、工作目录锁、提交串行、备份仓惯例、不贴 CSV 与大表正文、回报 ≤5 行、预算与硬停、同主题不重复开单）只写在 `dispatch-template.md` A 段，任务书里用一句引用代替整段复写，只补「本单增量」至多三行。
- **为什么**：这批约束与任务无关，每单重写一遍纯属重复付费；复写还会漂移，同一约束在不同单里出现不同措辞，子会话按哪版执行不可控。
- **违反时的识别信号**：任务书里出现与模板逐字重复的「备份仓 / 不贴 CSV / 回报行数」段落；或模板已改而任务书仍贴旧段；或同一约束在同一单里出现两种说法。

### R2 同主题探查只开一单
- **规则**：同一主题（同一批表、同一份登记表、同一组源接口）的探查只开一单，拿到结论文件后再按结论分头派执行单；执行单只读结论，不重读原始文件。
- **可执行判据（派单前 30 秒做完）**：
  ① `glob` 当天目录 `work/*_<YYYY-MM-DD>/`（只取当天日期，不扫全量）；
  ② 关键词取法：任务名里的核心名词优先——先去掉动作词（分析 / 核对 / 验证 / 修复 / 回填 / 统计 / 排查 / 实现 / 接入）与日期，留 1~3 个实词；例「排除层口径核对」取「排除层」，「两融买点复核」取「两融买点」；
  ③ 任一已有目录名包含该关键词 → 只能引用该目录（结论与产物路径都指向它），不得新建同类目录；完全不命中才允许新建，并在任务书写一句「已 glob 当天 work/，无同关键词目录」。
- **为什么**：定位类工作的成本几乎全在「读同一批文件」，多单并行的边际收益为零，只有重复付费；同一天新建同名目录还会让产物分散、复核时算不出单任务成本。
- **违反时的识别信号**：两个在跑会话的读取白名单有交集；同一主题出现两份 `work/handoff.md` 且结论重复；第二单的开工动作是重读第一单已读过的表；同一关键词当天出现 ≥2 个 work 目录（反例：2026-11-22 同日出现 4 个排除层相关目录）。

### R3 单个结果一条回执
- **规则**：一个任务只回一条结果回执（做了什么 / 关键数字 / 下一步 / 阻塞），过程明细写文件；不得拆成「采集一轮 / 入库一轮 / 校验一轮」多条回报。**单结果单消息**：同一结果只有一条消息，禁止先发半条结论、再补一条修正，也禁止把同一条回执拆成「摘要 + 明细」两条。
- **为什么**：每条回执都要带上下文重述，条数直接放大 token；多段回报里通常只有最后一段含新结论。
- **违反时的识别信号**：同一任务连续 ≥3 条回报且各自不含新结论；某条回报的正文只是过程日志；同一结论在不同回报里重复出现；同一结果出现「先发再补」的两条消息。
- **写回位置**：本节 R3；派单模板 A 段「回报 ≤5 行」处。

### R4 不确定可得的数据先只探源
- **规则**：能否拿到还不确定的数据，先开只探源的小单：预算 ≤10 次调用，产出只有「可得 / 不可得 + 证据路径（接口返回片段、表名、行数）」，明确不写入库；确认可得后再授权落地单。
- **为什么**：探源失败时，落地单的预算已经花在读表、拼字段、写脚本上，是最典型的预算超支来源。
- **违反时的识别信号**：探源单调用明显超过 10 次且已开始写入库 / 回填脚本；或该单没有产物路径、只有口头结论；或源端返回空后立刻加压重试而不是先判定「确无 / 未接线 / 被限流」。

### R5 每单写明预算与回报上限，超支须说明原因
- **规则**：任务书首行固定写「预算 ≤N 次调用 / 回报 ≤M 行 / 只读范围」；回报必带「本段调用数 + 本段耗时（分钟）」；实际超预算时，在回报里单列一行写超支原因与已获得的部分产出，不静默继续。
- **为什么**：没有预算的单无法判断该不该停；没有超支原因的账无法区分「任务本身贵」与「路径选错」。
- **违反时的识别信号**：任务书找不到预算行；回报缺两个成本数；账本里实际调用数大于派单预算而回报没有任何说明。

### R6 大文件只 grep 不整读
- **规则**：登记表、审计报告、日志、清单类大文件先检索定位，只读命中行前后各 30 行；单次读取 ≤300 行且 ≤16 KB；确需整份读必须先报路径 / 字节数 / 行数并取得确认。日志只看尾部约 50 行。
- **为什么**：整份读一次就可能吃掉单会话上下文的一半，且读进来的大部分内容与当前判断无关，后续每轮还要重复付费。
- **违反时的识别信号**：出现整份 Read 登记表 / 日志；同一文件在同一会话里被整份读 ≥2 次；回报里出现「为核对完整通读了……」这类表述。

### R7 提交只回一句
- **规则**：提交与备份同步完成后只回一句「提交成功 + 短哈希」，不贴 5 块模板、文件清单、`git status` 全文；用户点名要明细时才展开。
- **为什么**：提交结果可以用一个哈希定位，清单与状态对用户没有新增判断价值，却固定占用一段上下文。
- **违反时的识别信号**：提交回复出现 5 块、逐文件变更清单、工作区状态全文；同一提交被拆成「提交」「推送」「校验」多条回复。

### R8 超预算 20% 必须硬停（核对类保留 1 次收尾调用）
- **规则**：实际调用数达到派单预算的 120% 时立即停手，只回一条：「已用 X/N（超 R8）、已完成部分、剩余步骤、建议」；在该消息发出前不得再发起任何试探性调用（换接口、换路径、加一次核对都算继续试）。允许继续的唯一情形是用户当轮明确放行并给出新上限。
- **核对类例外（仅此一类，且只用 1 次）**：若本单属于「核对类」，允许在超线后再执行 **1 次**调用，该调用只能产出收尾结论（汇总已核事实、结论、证据路径），不得取新数据、不得改动任何文件、不得新写脚本；用完即回执并注明「R8 核对例外 1 次」，不得连续申请、不得拆成多次小核对绕过。
- **「核对类」定义（写死，三条同时满足）**：①对象是**已存在**的状态 / 文件 / 数据（既有表、备份仓、登记表、已入库结果），不产生新数据；②动作是**比对或确认**（对拍、计数、查一致性、确认口径），不含「源端能不能取到」的探源；③产出是**一份对照结论**，不写正式表、不跑回测、不做回填。
- **不算核对类（不得豁免）**：探源（R4）、改码与实现、采集 / 回填 / 重建、回测与策略评估、带写入副作用的审计；这些超线即停，无例外。
- **为什么**：本轮超支集中在收尾核对（ST 面板 73/50、两单 12/10）：核对天然需要「比对 + 落结论」两步，超线时截断会丢掉已完成的工作；但放开无限次就退化成「再多试一次」，所以只给 1 次且限定为结论调用。
- **违反时的识别信号**：台账 `tool_calls / budget_calls > 1.2` 且 note 无「超支 / 核对例外」说明；超线后出现第 2 次及以上调用；用「核对类」承接探源或改码任务；回报只写「还在处理」而不写超支与剩余步骤。
- **写回位置**：本节 R8；台账 `budget_calls` 列（`tools/task_ledger.py add --budget-calls`）；复核用 `tools/dispatch_cost_report.py --overrun-pct 20`（命中标 `R8 超预算超20%`）。

### R9 核对类任务预算起算 10 次
- **规则**：确认既有状态、备份仓核对、登记表对照、口径复核这类「核对类」任务（判定见 R8 三条定义），任务书预算不得低于 10 次调用（写死起算值）；低于 10 次的预算单视为任务书不合格，先改预算再派，不得以「顺手看一眼」压到 3~5 次。
- **为什么**：本轮两单收尾 12/10 的超支正是核对动作被低估：核对需要先定位文件、再比对、再落结论，天然比「读一眼」贵。
- **违反时的识别信号**：任务书预算 <10 且标题/描述含「核对 / 确认 / 复核 / 对拍 / 备份仓」；或用探源单预算（≤10）承接实际是收尾核对的任务。
- **写回位置**：本节 R9；派单模板预算行（低于 10 次的核对单在派单时就判不合格）。

### R10 主会话禁止零信息占位消息
- **规则**：主会话在等待子会话或长任务时，不得发送「等它回来」「稍等」「继续等待」「正在处理」这类不含新事实的消息；一轮内只发两类消息——派单说明与结果回执。确实需要长时间等待时保持静默，由结果消息触发下一轮。
- **为什么**：本轮主会话在结果未到时连发十几条零信息句子，每条都要重述上下文，纯消耗；且这些消息不改变任何执行状态。
- **违反时的识别信号**：同一轮出现 ≥2 条正文不含数字、文件路径或结论的消息；消息内容可被「仍在等待」一句完全覆盖；连续消息之间没有任何工具调用。
- **写回位置**：本节 R10；复核记录里按「轮次消息数 / 有效消息数」观测。

### R11 记账与提交同源
- **规则**：任何产生 commit 或写 `work/` 产物的任务，收口时必须写一行台账，含 `budget_calls` 与实际 `tool_calls`；缺行即视为该单未收口。每日复核第一步先比对「当日 commit 数」与「当日台账行数」，不等就判未记账：补登该单并把缺口计入超支统计。这一步不新增代码，用 `git log --since=<当天 00:00> --until=<次日 00:00> --oneline` 的行数与台账同一天记录数即可。
- **为什么**：2026-11-23 有 commit 0a9a518 与 286 个 work 产物，台账同日仍是 0 行，导致 R4 / R5 / R8 全部判不出，规则只剩形式。
- **违反时的识别信号**：当天有 commit 或 `work/*_<日期>/` 目录而台账同日 0 行；`git log` 当日提交数 > 台账当日行数；收口回报带 commit 哈希但台账无对应行。
- **写回位置**：本节 R11；复核第一步固定输出「commit 数 / 台账行数 / 差额」三列。

### R12 同族回测禁止多口径全量重跑
- **规则**：同一回测族换成本口径、换参数时，先用解析换算给出量级影响（如成本变动 × 换手率 = 收益影响），再只对差异最大的单点做一次实跑校验；确需全量重跑，必须在派单里写明理由与预估耗时，并给出「只跑差异单点」的替代方案。
- **为什么**：2026-11-23 `cross_score` 三个变体（13bp / 21.9bp / 21.9bp_fixed）各产出 88 个文件，同一族重复跑 264 个产物，换来的仍是同方向的量级结论，边际信息极少。
- **违反时的识别信号**：同一工作目录出现 ≥2 个同族变体目录且文件数相近；派单正文没写「为什么不能只跑单点」；重跑产物数 > 差异点数 × 10。
- **写回位置**：本节 R12；复核时按 `work/` 下同族变体目录数观测。

### R13 进度查询合并
- **规则（触发 / 动作）**：长任务运行中要看进度时，只查一次「状态文件（`logs/patrol_status.json` 等）+ 日志尾 50 行」；同一任务两次进度查询间隔 ≥10 分钟，或等到阶段边界（读表完成、回测一轮结束、提交前）再查；台账 note 记 `poll=n`（n 为本单进度查询次数）。
- **为什么**：11-23 日更期间靠短间隔轮询进程/日志跟踪进度，每次都要重读同一段日志尾，属于纯重复付费，且状态文件本身已能给出存活与阶段。
- **违反时的识别信号（验证口径）**：同一任务 10 分钟内出现 ≥2 次进度类查询；note 无 `poll=` 或周复核里 `poll` 均值逐周上升；回报出现「再看一下进度」这类无新信息的轮询描述。
- **写回位置**：本节 R13；台账 note 的 `poll=n`；周报复核 `poll` 均值。

### R14 提交即记账
- **规则（触发 / 动作）**：每次 commit 前用 `tools/finalize_commit.py` 写 done 行，含 `budget_calls` 与实际 `tool_calls`；同一派单的多笔子提交至少首笔写全，其余共享同一 task 标识。
- **为什么**：11-23 有 11 笔 commit 而台账 0 行，R11 被违反，导致 R5 / R8 的预算与超支判据全部失效。
- **违反时的识别信号（验证口径）**：当日 `git log --since=<当天 00:00> --until=<次日 00:00> --oneline` 行数 ≠ 台账当日 done 行数；commit 存在而台账无对应 note；补录行未标 `backfill`。
- **写回位置**：本节 R14；台账 done 行；周复核第一步即该等式。
- **日粒度快照（每日收工）**：把当日一行追加进 `docs/token/ledger_daily.csv`（字段 `date,done_rows,total_tool_calls,total_budget_calls,anomaly,note`），随当天最后一次提交入库；运行时明细仍留在 `logs/task_ledger.csv`（不入库），入库的只有日粒度快照。一条命令校验：`python tools/ledger_daily_check.py --days 7`（退出码 1 即有缺口）。

### R15 同一事故单会话诊断
- **规则（触发 / 动作）**：日更失败、进程被强杀或任务中断时，先查一次进程是否存活（`Get-Process` 或 `logs/patrol_status.json`）；存活则原会话续跑（等待或补发继续指令），不新开会话；进程已死才开恢复单，并在任务书引用原会话结论。
- **为什么**：11-23 日更事故后另起会话诊断，重复读同一批日志；`qfq_degradation` 在 11-23 22:43 与 11-24 16:19 两次落盘，说明同一告警被重复处理。
- **违反时的识别信号（验证口径）**：同一告警 / 同一 commit 关联的 `session_id` 多于 1 个；新会话开局动作是重读原会话已读日志；同一事故当天出现 ≥2 份诊断结论。
- **写回位置**：本节 R15；台账 `session_id`（同一事故应唯一）；复核时按告警时间窗聚合 session。

### R16 耗时与调用双记账（超阈触发复盘）
- **规则（触发 / 动作）**：每个任务回报时同时给实际耗时与调用数（沿用派单固定后缀「本段调用数与耗时」，不另立格式）；长任务（日更、全量回测等）额外给阶段耗时 top3。收口时写一行进 `docs/ops/task_timing.csv`，字段 `date,task_id,duration_sec,tool_calls,budget_calls,phase_top1,phase_top1_sec,over_threshold,note`，`date` 与 `docs/token/ledger_daily.csv` 同口径；耗时统一按秒，回溯不到写 `unknown`，不估算。
- **为什么**：R13 / R14 只记了调用数与是否记账，没有落库实际耗时与阶段占比，慢和贵只能靠感觉，缺超阈判定与复盘入口。
- **阈值与触发**：调用数 > 预算 ×1.2，或耗时 > 同族任务（`task_id` 去掉日期后缀视为同族；样本 <5 时用全表）历史 P75，任一命中即 `over_threshold` 标 `calls_120` / `time_p75`，并触发一次复盘。
- **复盘产物**：≤3 条优化项，每条写触发条件、动作、预期收益、验证方式，落 `docs/ops/review_<YYYY-MM>.md`。
- **验证口径**：下次同类任务跑完必须给出改前 / 改后两个数字（耗时秒、调用数），不接受「已优化」。
- **周期检查**：`python tools/task_timing_report.py --weeks 8`，按周列任务数、平均耗时、平均调用、超阈数与环比恶化 top3。
- **违反时的识别信号（验证口径）**：回报只有「已完成」没有耗时 / 调用数；task_timing 缺行或 `date` 与日快照对不上；同一 task_id 连续两周进恶化 top3 却无对应复盘条目。
- **写回位置**：本节 R16；`docs/ops/task_timing.csv`；`docs/ops/review_<YYYY-MM>.md`。

### R17 阶段一单一验收，交接必带下一单输入
- **规则（触发 / 动作）**：派单或执行中出现第 2 个可独立验收的阶段（如「修根因」与「补表」、「改代码」与「重跑全量」），立即拆单，前一单收口写 `work/handoff_<任务>_<日期>.md`；中途追加的需求不并入本轮，记入 handoff 另开单。累计调用达 60 次必须停手写 handoff（与派单固定后缀一致），handoff 至少含四项：已完成且已验证的结论、当前状态与未完成项、下一单的输入（文件 / 数据 / 参数）与验收标准、已排除的死路。
- **为什么**：11-24 日更那单 108 次、超约定 80%，根因不是执行不守约，而是派单把 6 个阶段塞进同一轮，单轮天然超 60；拆单 + 带输入的 handoff 才能让下一单不重复探查。
- **验证口径**：同一任务连续两单能靠 handoff 直接开工（下一单不重复读同一批文件）；单轮调用 ≤60，超 60 按 R8 硬停。
- **违反时的识别信号**：回报里出现「顺便 / 又追加 / 继续补」；单轮调用 >100；handoff 只有一句话、没有下一单输入清单。
- **写回位置**：本节 R17；`work/handoff_<任务>_<日期>.md`。

## 二、每周复核（闭环入口）

**看哪张表**：`python tools/dispatch_cost_report.py --days 7 --min-calls 30` 的输出表。数据来自两处，均为本地只读——
0. 记账完整性（R11，复核第一步）：`git log --since=<当天 00:00> --until=<次日 00:00> --oneline` 的行数 vs 台账同日记录数，不等即判未记账，先补登再算超支。
1. `logs/task_ledger.csv`：`session_id` / `title` / `phase` / `tool_calls` / `budget_calls` / `duration_min` / `rounds`；
2. `work/<任务名>_<YYYY-MM-DD>/`：产物文件数（排除 `__pycache__`）、报告字节数（`.md`）。

**什么阈值触发规则修改**（命中任一即复盘，不追求全绿）：
| 信号 | 阈值 | 对应规则 |
|---|---|---|
| 单任务调用数 | ≥ 60（硬停线） | R5 |
| 调用数 / 预算 | ≥ 1.2（达预算 120%） | R8 |
| 核对类任务派单预算 | < 10 | R9 |
| 单轮零信息消息 | ≥ 2 条 | R10 |
| 调用数 / 产物文件数 | ≥ 20 | R2 / R4 |
| 报告字节 / 调用数 | < 100 B（且调用数 ≥ 30） | R3（产出太薄，回执却很多） |
| 台账 `tool_calls=unknown` 占比 | > 30% | R5（没记账，闸门失效） |
| 无 work 目录但调用 ≥ 40 | 出现即看 | 先判是否代码类任务，再决定是否计 R5 |

**超支率怎么算**：`tools/dispatch_cost_report.py` 读台账 `budget_calls`；`tool_calls / budget_calls >= 1.2` 即命中 R8。历史行没有该列时脚本单列「预算不可得」，不得按 0 或按估算值补齐。

**改完写回哪个文件**：
- 属「已有规则没被遵守」→ 在该规则条目下追加一行实测依据（日期 + 任务 + 数字），不新增条目；
- 属「模板缺这条约束」→ 改 `dispatch-template.md` A 段，并同步本文件对应条目的措辞；
- 属「全新失效模式」→ 在第一节新增 R8 起条目，同时在 `99-index.md` 更新本文件说明；
