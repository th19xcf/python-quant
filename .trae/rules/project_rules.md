# 项目工作规则

## Git 提交规则

- **用户已授权免确认提交**：提交前无需再向用户确认，直接完成「变更文件备份同步 → SHA256 校验 → `git commit` → 默认回一行」全流程；默认只回一行「已入库 + 短哈希 + 变更文件数」，仅当用户当次明确要求提交报告时才输出完整 5 块模板
- 提交前仍需整理待提交内容（文件清单、拟定 commit message、备份同步状态），但整理结果默认不输出，仅在点名要求提交报告时随 5 块一并给出，供用户事后复核
- 用户当场明确提出异议或要求暂缓的，以用户指令为准
- **Commit message 必须使用中文**：标题与正文描述统一使用中文，仅保留约定式提交的类型前缀（feat/fix/refactor/perf/chore 等）与 scope 为英文，格式为 `type(scope): 中文描述`
- **Commit message 不得包含空行**：标题行与正文之间、正文各条目之间均不插入空行；条目紧接标题下一行开始，逐行连续书写（不使用 `git commit -m "标题\n\n正文"` 这种带空行的写法）
- **Commit message 文件必须无 BOM**：禁止用 PowerShell 5.1 的 `Set-Content -Encoding utf8` 写消息文件（其 `utf8` 即 UTF-8 带 BOM，会写入 `EF BB BF`，且 `git commit -F` / `git stripspace` 不会自动清理）；统一用 `.venv\Scripts\python.exe` 以 `open(p, 'w', encoding='utf-8', newline='\n')` 写临时文件后 `git commit -F <文件>`，或无 Python 时用 `[System.IO.File]::WriteAllText($p, $msg, (New-Object System.Text.UTF8Encoding($false)))`；提交前可自检首 3 字节不为 `EF BB BF`
- **每次执行 git commit 后，默认只回一行**「已入库 + 短哈希 + 变更文件数」；仅当用户当次明确要求提交报告时，才按以下模板输出完整 5 块（模板保留不删，作为点名时的格式）：

### 注意事项
- **Commit message 必须原样输出**：从 `git log -1 --format="%B"` 取，不做任何二次格式化（不要加"标题""正文"标签，不要改缩进）
- **第 2 块（完整 Commit Message）输出格式固定**：只用一个 `text` 代码块（` ```text ` 起始、` ``` ` 结束）直接贴原文，块内不加任何标签或缩进；**严禁把整个 5 块模板再包进外层代码块**——嵌套围栏会让聊天窗口把消息内容渲染吞掉
- **不要伪造输出**：所有数值、哈希、文件状态都必须来自 `git` 的真实输出
- **备份方式**：只同步本次 commit 的变更文件到备份目录，**不删目录、不碰 .git**，命令为：
  ```powershell
  python -c "
import subprocess, shutil, os, sys
src=r'E:\code\python\quant'
sys.path.insert(0, src)
from tools.backup_root import resolve_backup_root
# 0. 备份仓路径唯一入口：QUANT_BACKUP_ROOT → .trae/backup.local.json → 报错（不写死盘符）
dst=str(resolve_backup_root())
# 1. 获取本次 commit 变更文件列表
r=subprocess.run(['git','-C',src,'diff','--name-only','HEAD~1','HEAD'],capture_output=True,text=True)
changed=[l for l in r.stdout.strip().split('\n') if l]
# 2. 获取被删除的文件列表
r2=subprocess.run(['git','-C',src,'diff','--name-only','--diff-filter=D','HEAD~1','HEAD'],capture_output=True,text=True)
deleted=set(l for l in r2.stdout.strip().split('\n') if l)
# 3. 同步修改/新增
for rel in changed:
    s=os.path.join(src,rel); d=os.path.join(dst,rel)
    if os.path.isfile(s):
        os.makedirs(os.path.dirname(d),exist_ok=True)
        shutil.copy2(s,d)
    elif rel in deleted and os.path.exists(d):
        os.remove(d)
print(f'synced {len(changed)} files, removed {len(deleted)} deleted')
"
  ```
  backup 目标由 `tools/backup_root.py` 的 `resolve_backup_root()` 解析并校验（`QUANT_BACKUP_ROOT` → `.trae/backup.local.json` → 报错），禁止写死盘符；备份目录有自己的 `.git`，**永远不要删整个目录**
- **核心原则：增量同步，其他不动**。只拷贝本次 commit 变更的文件过去，删除源仓库已删的文件；备份目录里的 `.git` 信息、untracked 文件、手动添加的内容全部保留
- **为什么不删整个目录**：备份目录是独立的 git 仓库（有自己的 `.git`），`shutil.rmtree` 会把备份仓库也干掉；之前的"精确匹配"方案过度设计了，用户只需要同步文件内容

- **按情况自行提交并备份**：用户已授权，无需人工确认。一组改动自洽（同一逻辑变更、测试通过）时，直接执行「备份同步 → SHA256 校验 → 中文无空行无 BOM 提交 → 回一行」全流程，默认只回一行「已入库 + 短哈希 + 变更文件数」。
- **只提交自洽的一组**：一次提交只含一个逻辑闭合的改动；在跑任务的中间态不入库；工作区有其它未完成改动时**只 `git add` 本次相关文件，禁止 `git add -A` / `git add .`**。
- **异常先报后动**：提交前若发现未预期的文件变更（比如不属于本次范围的 `M`/`??`），先如实报出，不要顺手带上。
- **提交前必须自证可用**：提交前至少跑通本次改动相关的单测与静态检查（ruff/mypy）；若存在与本改动无关的既有失败项，必须在报告中单独列出并说明归属，不得笼统写成"全部通过"。

## 备份仓库提交规范

- **提交标题格式**：`type(scope): YYYY-M-D，中文描述`，日期紧跟冒号，用中文逗号与描述分隔，月、日不补零；示例 `chore(backup): 2026-11-9，同步 2026-11-09 数据质量、研究脚本与审计文档`
- **正文每行同样以类型前缀开头**：格式 `type(scope): YYYY-M-D，中文描述`，逐行连续书写；标题与正文之间、正文各条目之间一律不插空行
- **Commit message 文件必须无 BOM**：沿用源仓库既有约定，用 `.venv\Scripts\python.exe` 以 `open(p, 'w', encoding='utf-8', newline='\n')` 写临时文件后 `git commit -F <文件>`，提交前自检首 3 字节不为 `EF BB BF`
- **职责归属**：备份仓库（路径由 `tools/backup_root.py` 解析）的维护、提交与推送由助手负责；每次备份同步完成后直接提交并推送，不需要用户再提醒
- **仓库形态与推送约定**：源仓库 `e:\code\python\quant` 仅本地、未配置任何远端，只做本地提交，不 fetch、不 push，也不要给它添加远端；备份仓库（解析并校验 origin 指向 `th19xcf/python-quant`）是唯一关联 GitHub 的仓库，其提交推送至该仓库自己的 `main`。两个仓库独立管理、互不约束，不需要跨库对齐或快进
- **红线继承**：备份仓库只做增量 `copy2` 与「源端已删文件」的对位删除；禁止 `rmtree`、禁止碰其 `.git`、禁止 force push（`--force` / `--force-with-lease`）与任何改写历史的操作（未推送的 amend 按 `00-core.md`「Git 历史只增不重写」申报）

## 备份同步规则

- **每次执行 git 提交前，必须先把本次修改的文件同步到 `resolve_backup_root()` 解析出的备份目录下对应的位置**（保持与仓库相同的相对路径结构）
- 同步范围 = 本次提交涉及的全部文件（新增/修改）；删除的文件需从备份目录对应位置一并移除
- **完整备份范围 = ① git 跟踪文件 ② `data/local_store/**` ③ `reports/**` ④ 仓库外被脚本引用的输入文件（`E:\www\tmp\` 下）**：每次交付与收口都按这四类逐一核对，缺一类即为备份不完整
- **教训**：只备份 ①、② 会让 `reports/**` 与外部输入成为盲区，最终出现「结果只能靠产物复现、产物又没备份」的双重失效；未跟踪或不在仓库内都不是跳过备份的理由
- **`data/local_store/**` 与 `reports/**` 一律按「相对路径集合求差」做全量镜像，禁止按 `mtime` 或「今天」筛选**：按日期筛选会让历史文件永久缺席（实测曾缺 1,591 个 / 13.9%，含 `_backup/` 回滚快照），每次须先求集合差补齐缺失文件，再做全量逐文件 SHA256 比对
- 备份同步完成后，再按上述 Git 提交规则请用户确认并提交

## 任务调度与超时处理规则

- **超时阈值 15 分钟**：任何在跑的任务超过 15 分钟没有任何进展更新，必须主动发一次状态询问，只问三件事，不要长篇报告：
  1. 现在卡在哪一步？
  2. 有没有外部阻塞？（数据源限速、接口返回空、账号封禁、需要 token）
  3. 还要多久？
- **先催后接管，不轻易重启**：能催活的任务不要杀掉重建。两个会话同时写同一批文件，冲突风险高于等待成本。
- **确认卡死后才接管**：确需另起会话接管时，新任务必须先盘点旧任务已完成的产物与断点（分块 parquet、`manifest.json`、`progress.csv`、`failed.csv`、临时脚本等），**从断点续跑，禁止从零重来**。
- **不声称"已杀死"**：若当前没有终止会话的能力，如实说明只能"另起接管"，且旧会话可能仍在运行、仍在写同一批文件；不得表述为已停止。
- **接管前声明文件归属**：新任务开工前先明确它要写哪些路径，避免与旧任务并发写同一文件。
- **允许直接结束占用资源的进程**：用户已授权，遇到正在运行的程序阻塞任务时可直接结束该进程，事后再说明结束了什么、为什么。
- **能拆就拆、能并行就并行**：一个目标如果可以切成互不依赖的子任务，就一次性全部派出去并行跑，不要排队等前一个完成再开始下一个。只有真正有依赖的步骤（后一步需要前一步的结果）才串行。
- **并行前先划边界**：只有彼此不写同一批文件、不争同一个 Git 工作区的子任务才能并行；会写同一路径、同一文件或同一仓库状态的，必须串行或合并到一个任务里。
- **同一产出的一轮内微调归并、多个产出必须派单即拆**：对同一份产出在同一轮内连续提出的修改、补充、修正，合并成一条消息发给原任务，不要为同一份产出另开会话；跨轮新需求、以及**多个可独立验收的产出（N 张表、多个模块）必须在派单时就拆成多个会话**，不得先归并再靠中途收口。派单判据一句话：一个会话只承接一个可独立验收的产出。
- **并行结果合并汇报**：多条任务同时跑时，按主题归并结果再汇报，不逐条罗列过程与流水账。
- **发现已知待办即刻安排**：审计、核查、报告、任务回执里发现的任何已知缺口、待办、未完成项，只要不属于"需外部条件不具备"或"用户已明确作废"两类，必须**当场安排任务落实**，并在同一条回复里说明去向（已派 / 因何排队）。禁止只在回复里罗列待办而不安排。
- **必须排队的要写明解锁条件**：因文件冲突或数据一致性必须串行的，明确写出"等哪条任务完成后立即派"，并在该条任务收口时第一时间派出去，不得遗忘。
- **加速以不出错为前提**：并行只在不冲突且可验证的前提下进行。任何用正确性换速度的做法一律禁止，包括跳过测试、跳过对账、跳过备份校验、两条任务并发写同一文件、并发压同一外部数据源。
- **每条并行任务必须自带验收**：开工前明确验收标准（单测、对账、抽样比对、守恒校验），收口时必须给出实测证据。没有证据的"完成"不算完成，不得转述为已完成。
- **网络采集限流**：外部数据源采集类任务同时不超过 2 条，单连接串行 + 节流。出现限速、封禁、连续超时等信号时立即降并发并如实报告，不得加压重试。
- **冲突优先于速度**：两条任务会写同一文件、同一目录产物或同一 Git 工作区状态时，必须串行或合并为一条，不得为提速改成并发写。
- **验证不通过先停后报**：不得为了推进而放宽断言、下调阈值、删除用例或忽略失败项。先定位原因、如实上报，再决定换源、缩范围或回滚。
- **派任务时必须写明阶段性汇报要求**：每次派单（新开会话或追加消息）末尾必须带「60 次停手 + 回报带本段调用数与耗时」两句固定后缀，并要求对方主动回阶段性进展、不等主控来问；后缀原文与里程碑格式见 `.trae/rules/task-scheduling.md` 的「派单必带的固定后缀」与「阶段性汇报节点与格式」，细则不在本文件重复。
- **用户发截图时先读图再派单**：调度侧必须先看截图确认被指对象（页头 / 图例 / 表格列 / 按钮等）再写任务书，不得凭文字描述猜测对象；猜错会造成一轮 10~20 次调用的返工。
- **遇阻塞立即报，不许硬等**：出现限速、封禁、接口为空、外部依赖缺失、口径歧义时，第一时间报告阻塞点与影响，不得静默重试或擅自放宽要求。
- **静默即视为停滞**：超过 15 分钟没有任何进展汇报的任务，主控按超时规则发状态询问；连续两次询问仍无实质进展，按「先催后接管、从断点续跑」处理。
- **同一仓库提交必须串行**：`git add` / `git commit` 天然互斥，两条任务并发提交必然撞共享 index，会把他方文件混进本次提交。提交前先确认没有其它任务正在提交；无法确认时用隔离索引（`GIT_INDEX_FILE` 指向临时文件）并在报告中写明，禁止在共享 index 上并发提交。
- **提交范围必须自证**：提交后立即用 `git show --stat HEAD` 或 `git diff-tree --no-commit-id --name-only -r HEAD` 复核本次 HEAD 的文件清单，与预期清单逐一比对；发现多出文件立即回退重做，不得事后补一句"混入了"了事。

## 大文档读取纪律

- **单次读取上限**：一次读取不超过 300 行且不超过 16 KB；超出必须拆段或改为检索。
- **整份读需确认**：任何超过 16 KB 或超过 300 行的文件，整份读之前先报「路径 / 字节数 / 行数 / 估算 token 量级 / 为什么不能分段定位」，经用户明确确认后才执行；未确认前只准 grep 定位与局部读。
- **硬红线**：超过 32 KB 或超过 500 行，不允许一次性读入上下文；即使被点名要求整份读，也须先给出按标题或编号切块的分段方案再执行。
- **默认动作**：grep 定位行号 → 只读命中行前后各 30 行；需要全貌时读目录与标题行，不读正文。
- **适用范围**：数据缺口登记表、审计报告、盘点清单、日志、规则文件本身等大文档同等适用；派子任务时要把这条写进任务书。
- **理由**：中文 UTF-8 约 3 字节/字、1 字约 1~1.5 token，16 KB 已是 5~8k token，50 KB 超过 2 万 token；且读进上下文的文件在之后每次工具调用都重新计费，代价不是一次性的。

## 上下文增长控制

- **单会话 60 次硬停（执行点，不等审批）**：工具调用达到 60 次即停止接收新工作——只跑完手上正在执行的那一条命令，不再开新的探查、编辑或收尾动作，立刻写交接文件 `work/handoff.md`（≤40 行：目标 / 口径与常量位置 / 已改已验 / 待改 / 复测怎么跑），然后回报「已停手 + 交接路径 + 剩余项」，不需要等待批准；100 次为绝对上限，达到即停，不允许再继续。判定函数 `tools/task_ledger.py::session_gate`，阈值改动必须同轮改单测。
- **一个会话只承接一个可独立验收的产出**：N 张表、多个模块、多份报告在派单时就拆成 N 个会话，不靠中途收口补救；同一产出的一轮内微调视为同段，不另开会话。
- **跨会话交接走文件**：续作必须落交接文件（`<任务目录>/work/handoff.md`，≤40 行：目标 / 已完成 / 关键路径与结论 / 下一步 / 已知坑），新会话只读交接文件与必要的最小片段，不重读历史产物、不重跑已验证步骤。
- **明细落盘、只回报标量**：明细表、逐行核对表、调仓清单、脚本日志一律只落盘，回报里只给文件路径 + 少量标量，不贴表格、不逐行复述；标量上限与单条回报格式见 `00-core.md` 第四节（明细只落盘 / 单次回报上限），不在此重复定义。
- **收口自动记账**：`tools/finalize_commit.py --apply` 成功后自动向 `logs/task_ledger.csv` 追加一行（时间 / 任务标识 / 调用数 / 耗时 / 提交短哈希，调用数取不到写 `unknown` 并告警、不阻断收口），同一提交重复收口不重复写；未走该脚本的收口才手工 `python tools/task_ledger.py add ... --phase done --apply` 补记。
- **样式与交互类微调按「同批同类一次扫全」**：用户只能看到才发现，所以不要求用户一次提全；收到一处样式反馈时，执行方须在同一轮把同类控件（列宽 / 行高 / 底色 / 对齐 / 排序 / 表头 / 空值显示）一次排查改完，并在回报里列出「同类中还发现并修了哪些」，避免下一轮再被同一类问题打回。
- 此类微调属于「同一交付物一轮内微调」，计入同一段，不因多轮往返触发换会话。
- 本节只做交叉引用；与 `00-core.md` 第四节冲突时以 `00-core.md` 为准。

## 决策授权规则（带建议即执行）

- **决策点必须自带建议**：凡是需要用户拍板的事项，必须一次写清「选项 / 我的推荐 / 推荐理由 / 不做会怎样」，不得只抛问题让用户自己挑。
- **与其他规则不冲突时，按自己的建议直接执行，不再等确认**：给出推荐即可推进，事后在汇报里写清「已按建议 X 执行，理由是 Y，可这样回滚 Z」，让用户事后复核而不是事前放行。
- **不得以「等用户确认」停在原地**：只有下列三类才必须停下来等用户。
  1. 触碰「数据与历史安全规则（红线）」的操作：删除 `data/` 内容、清空或覆盖备份目录、重写 Git 历史、批量清理工作区；
  2. 外部条件不具备：源端没有数据、接口限流或封禁、需要账号或 token、需要用户先更新本地源文件；
  3. 会改变既定口径或结论含义、且没有实测证据可自证：放宽断言、下调阈值、删除用例、改变 `strict` 口径等。
- **红线类即使给了建议也不自动执行**：仍须把影响面（路径、行数、不可恢复性、下游依赖）报给用户，并给出不丢数据的替代方案；用户点名到具体路径后才动手。
- **不滥用本条**：本授权只覆盖「可逆、有备份、可回滚、有验收证据」的操作。不可逆或无法实测验证的，仍按「不确定就停手」处理。
- **被授权执行的事项照样要记账**：在汇报中单独列一段「本次自行决定并执行的事」，写清判断依据与回滚方式，供用户事后追认或推翻。

## 数据与历史安全规则（红线）

- **数据目录禁止删除**：`data/`、`data/local_store/**`（含 parquet、meta、raw、断点缓存、`_backup`）一律不得删除、清空、或"删除后重建"。只允许追加、覆盖单文件、增量补齐。
- **备份目录禁止清空**：备份仓路径只能由 `tools/backup_root.py` 的 `resolve_backup_root()` 解析（环境变量 `QUANT_BACKUP_ROOT` → 本机配置 `.trae/backup.local.json` → 报错停止），文档与代码一律不写死盘符、不按候选盘符探测、解析失败不得新建空目录；解析后必须校验目录存在、含 `.git`、origin 指向 `th19xcf/python-quant`，任一不满足即抛错停止，不得降级为「跳过备份」。对解析出的目录只做增量同步（copy2 单文件、删除仅限源仓库已删的对应文件）。禁止 `rmtree`、禁止删整个目录、禁止碰它的 `.git`。
- **Git 历史只增不重写**：已推送提交一律禁止改写历史；完整定义与未推送 amend 的申报格式见 `00-core.md`「Git 历史只增不重写」，本节不重复。
- **禁止批量清理工作区**：禁止 `git clean -fdx`、禁止对未跟踪文件做批量删除。工作区里的 `M`/`??` 可能是其它任务的在途成果，清理等于销毁他人工作。
- **用户口头要求上述操作也不直接执行**：即使用户当次要求"删本地数据 / 覆盖备份 / 重置历史"，也必须先把影响面（涉及路径、行数、不可恢复性、下游依赖）报给用户，并给出不丢数据的替代方案；仅在用户对该次具体路径再次明确确认后才可动手，且**删除 `data/` 任何内容需用户点名到具体文件或子目录**。
- **不确定就停手**：任何会影响项目可运行性、数据完整性或历史可回溯性的操作，一律先停下来报告，不得"先做了再说"。
- **数据口径以本地 `data/local_store` 为唯一权威来源**：日常链路（采集域、构建、校验）只读本地，不再读 MySQL，也不做本地与 MySQL 的对照；MySQL 仅保留为远期归档目标，从本地一次性回灌属独立任务、不进日常链路。

## 定时唤醒与巡检规则

- **默认开启 10 分钟巡检**：项目常驻一个周期性定时任务，cron 为 `*/10 * * * *`，用于定时唤醒主控、及时发现停摆。调度最小粒度就是 10 分钟，5 分钟不支持，不要反复尝试更短的间隔。
- **巡检只做轻量动作**：列会话状态与更新时间 → 挑出「仍在进行但超过 15 分钟没更新」和「刚变成已完成/失败」的 → 只对其中的可疑者看一轮最新内容。不逐条读全部会话正文，不重复上轮结论。
- **无变化就静默**：正常时只输出一行「巡检：无异常，在跑 N 条」。有变化才写三行以内。除发现失败、需用户决策的阻塞、或「声称完成却没提交」，不主动打扰用户。
- **发现停滞按既有规则处理**：先催（只问卡在哪步、有无外部阻塞、还要多久），确认卡死才另起接管，且必须从断点续跑、先声明文件归属。
- **巡检不得越权**：不删除任何数据、不清空或覆盖备份目录、不重置 Git 历史、不批量清理工作区、不改任何代码、不自行开新任务、不替用户做决定。
- **可随时调整**：频率、开关由用户一句话决定；暂停或删除定时任务不等于终止在跑的子会话，不得表述为"已停止"。
