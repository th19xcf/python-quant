# 任务调度与超时处理规则（按需）

- **开工前成本预估（派活方义务）**：每个任务书必须含三行预估——①规模：预计处理的文件数、字节数、外部请求数 × 间隔秒数；②耗时与回报次数：预计墙钟时间、计划回报次数（默认开工一行、收工一次汇总）；③高耗动作与替代：是否含全库扫描、逐文件哈希、逐件枚举、整表写进正文或报告，有则写明替代做法。阈值：文件数 >1 万、字节 >1 GB、外部请求 >500 次、预计墙钟 >10 分钟，任一触发即先给压缩方案再开工，不得先跑后省。收工用同一三行核一次实际值；实际值超预估两倍记一行原因，不写报告、不重复复盘。
- **会话数按文件族计（量化判据）**：同一天 + 同一文件族（如 `.trae/rules`、`tools/`、`docs/`）或同一交付物 = 必须复用同一会话；会话数按文件族与交付物计，不按改动点计。与 DG-35「基础表一次改完」及「同一仓库提交必须串行」冲突时，优先级为 DG-35 > 提交串行 > 本条：先按表一次改完、提交仍逐笔串行，本条只合并会话、不合并提交。
- **规则类改动先记待改清单**：规则类改动先记进一张待改清单（一行一条、含依据），攒到 3 条或当日收工前一次性执行；单条小改动不许直接开单。清单与执行同轮提交，不另建产物文件。
- **交付物版式前置**：产出看板/报告/页面前，先写五行以内的「版式与数据源清单」（首屏放什么、有哪些区块、数据来自哪几个文件与版本），确认后再写渲染；与 `00-core.md`「同一交付物一天只允许重排版一次」配套。
- **超时阈值 15 分钟**：任何在跑的任务超过 15 分钟没有任何进展更新，必须主动发一次状态询问，只问三件事，不要长篇报告：
  1. 现在卡在哪一步？
  2. 有没有外部阻塞？（数据源限速、接口返回空、账号封禁、需要 token）
  3. 还要多久？
- **先催后接管，不轻易重启**：能催活的任务不要杀掉重建。两个会话同时写同一批文件，冲突风险高于等待成本。
- **确认卡死后才接管**：确需另起会话接管时，新任务必须先盘点旧任务已完成的产物与断点（分块 parquet、`manifest.json`、`progress.csv`、`failed.csv`、临时脚本等），**从断点续跑，禁止从零重来**。
- **不声称"已杀死"**：若当前没有终止会话的能力，如实说明只能"另起接管"，且旧会话可能仍在运行、仍在写同一批文件；不得表述为已停止。
- **接管前声明文件归属**：新任务开工前先明确它要写哪些路径，避免与旧任务并发写同一文件。
- **开工前先查代码地图**：动数据、改派生表、改采集或回填逻辑的任务，开工前先查 `docs/代码地图.md` 定位写入点与调用方，不再从 grep 找写入点。
- **派活前把链路写进任务书**：派发「改采集 / 改派生 / 补数 / 改写入点」类任务时，任务书必须写明已确认的入口文件、函数、写入点与产出路径；子任务不得以「先通读全仓找链路」开工。地图缺该链时，先用一次定向检索补进 `docs/代码地图.md` 再派活。依据：2026-11-13 日更单入口（f205ce0）会话先全库通读，被用户中途叫停后才改为按链路读。
- **允许直接结束占用资源的进程**：用户已授权，遇到正在运行的程序阻塞任务时可直接结束该进程，事后再说明结束了什么、为什么。
- **能拆就拆、能并行就并行**：一个目标如果可以切成互不依赖的子任务，就一次性全部派出去并行跑，不要排队等前一个完成再开始下一个。只有真正有依赖的步骤（后一步需要前一步的结果）才串行。
- **并行前先划边界**：只有彼此不写同一批文件、不争同一个 Git 工作区的子任务才能并行；会写同一路径、同一文件或同一仓库状态的，必须串行或合并到一个任务里。
- **同一交付物的追加要求归并到同一任务**：对同一份产出连续提出的修改、补充、修正，合并成一条消息发给原任务，不要为同一份产出另开会话——重复开工既浪费又容易互相覆盖。
- **并行结果合并汇报**：多条任务同时跑时，按主题归并结果再汇报，不逐条罗列过程与流水账。
- **发现已知待办即刻安排**：审计、核查、报告、任务回执里发现的任何已知缺口、待办、未完成项，只要不属于"需外部条件不具备"或"用户已明确作废"两类，必须**当场安排任务落实**，并在同一条回复里说明去向（已派 / 因何排队）。禁止只在回复里罗列待办而不安排。
- **必须排队的要写明解锁条件**：因文件冲突或数据一致性必须串行的，明确写出"等哪条任务完成后立即派"，并在该条任务收口时第一时间派出去，不得遗忘。
- **加速以不出错为前提**：并行只在不冲突且可验证的前提下进行。任何用正确性换速度的做法一律禁止，包括跳过测试、跳过对账、跳过备份校验、两条任务并发写同一文件、并发压同一外部数据源。
- **每条并行任务必须自带验收**：开工前明确验收标准（单测、对账、抽样比对、守恒校验），收口时必须给出实测证据。没有证据的"完成"不算完成，不得转述为已完成。
- **网络采集限流**：外部数据源采集类任务同时不超过 2 条，单连接串行 + 节流。出现限速、封禁、连续超时等信号时立即降并发并如实报告，不得加压重试。
- **冲突优先于速度**：两条任务会写同一文件、同一目录产物或同一 Git 工作区状态时，必须串行或合并为一条，不得为提速改成并发写。
- **验证不通过先停后报**：不得为了推进而放宽断言、下调阈值、删除用例或忽略失败项。先定位原因、如实上报，再决定换源、缩范围或回滚。
- **`_staging` 断点是收口硬条件（只约束新任务）**：新开的采集 / 构建类任务，`_staging/<任务>_<日期>/` 下必须**同时**存在 `progress.csv` / `progress.json`（或等价可机读进度文件）与 `failed.csv`，缺任意一个即判定该任务未完成，不得报收口；收口回执里要点明这两条路径。**历史任务一律不追溯补**——补建等于制造假进度文件，比缺断点更危险（存量见判例 §5.1）。本条只对此后新开的任务生效；适用范围按 `data-governance-detail.md` DG-7 的三条判定收窄——仅同时满足「预计 ≥10 分钟、跨运行续跑、含外部采集」才强制，其余任务可省这两份文件，但改前备份与 SHA256 台账不得省。
- **派任务时必须写明阶段性汇报要求**：每次下派任务，都要在指令里明确要求对方主动回阶段性进展，而不是等主控来问。没写这一条，就等于允许对方长时间静默。
- **阶段性汇报节点与格式**：每个明确里程碑（数据盘点完成、实现完成、验证完成、提交完成）各回一条，一句话即可：已完成什么 / 当前在哪步 / 下一步是什么 / 预计还要多久。单个步骤预计超过 10 分钟，中途必须给一次进展。
- **遇阻塞立即报，不许硬等**：出现限速、封禁、接口为空、外部依赖缺失、口径歧义时，第一时间报告阻塞点与影响，不得静默重试或擅自放宽要求。
- **静默即视为停滞**：超过 15 分钟没有任何进展汇报的任务，主控按超时规则发状态询问；连续两次询问仍无实质进展，按「先催后接管、从断点续跑」处理。
- **采集类任务对话只准两行**：开跑一行（起止范围、预计请求数、间隔）、收工一行（入库条数、区间、失败数、校验结论、短哈希）。所有进度与日志写文件（`progress.csv`、`failed.csv`、日志文件），不在对话里逐月/逐日回显。
- **采集前先去重再对拍**：候选先按同键本地去重，再拿去重后的集合做同键对拍，避免为会丢弃的行付对拍成本。
- **不适用 5 块报告**：采集与补数类默认不输出提交明细、文件变更清单、工作区状态，除非用户点名。
- **采集请求粒度按接口能力合并**：外部接口支持区间或批量取数时，必须按接口能力合并请求，先用一次探针确认可用区间参数，不许默认按最小时间片（日/月）切分逐次调用。接口硬性只接受单点参数时（如仅 `ann_date` 或单个标的）逐次调用不可避免，但开工前必须说明「请求次数 × 间隔 = 预计墙钟时间」，并明确该类耗时属墙钟时间，不靠分期回报反映进度。
- **采集日志只打桶级聚合**：采集循环 stdout 只打按时间桶聚合的单行（桶名 + 本桶新增行数 + 累计行数），逐条/逐日明细写 `progress.csv`，已完成分片记 sha256，对话里禁止回读明细。同一批采集只允许两次对话回报：开工一行、收工一次汇总（行数、区间、失败数、校验结论、短哈希），禁止「采集报一轮、入库报一轮、校验再报一轮」。
- **同一仓库提交必须串行**：`git add` / `git commit` 天然互斥，两条任务并发提交必然撞共享 index，会把他方文件混进本次提交。提交前先确认没有其它任务正在提交；无法确认时用隔离索引（`GIT_INDEX_FILE` 指向临时文件）并在报告中写明，禁止在共享 index 上并发提交。
- **同文件并行编辑三条**（提交范围自证见 `00-core.md`「提交纪律」；本条依据见判例 §5.2）：
  ① **先串行或按 hunk 暂存**：隔离索引只隔离索引文件、**不隔离工作区**，`git add <整个文件>` 会把同一文件里他路的在途 hunk 一并入账。同一路径被两路并行编辑时必须先串行（等对方提交完再改），或按 hunk 单独构造 blob（`git diff -- <file>` 摘本路 hunk → 基于 `HEAD:<file>` 应用 → `git hash-object -w` → `git update-index --cacheinfo`），禁止直接 `git add <整个文件>`。
  ② **必须做 hunk 级核对**：`git show --stat HEAD` 与 `diff-tree --name-only` 只给文件名，看不出同文件内混入；提交后必须对每个改动文件执行 `git diff HEAD~1 -- <file>`，逐个 hunk 确认属于本路。
  ③ **发现混入且已推送：不回滚、不 amend**：改写历史属红线，已推送的一律不回滚、不 amend、不 force push；如实记账并在下一笔提交正文写明"上一笔 `<hash>` 混入他路 hunk（文件 / 内容 / 来源 / 时点）"，保留可追溯链。

## 上下文与 token 成本（编排侧）

- **镜像与全库盘点只跑一轮**：镜像、集合差、全库盘点类任务等一个写入批次全部结束后只跑一次；禁止在写入过程中反复复扫，禁止为「自证」跑两轮相同校验。核对：同类校验本轮执行次数是否为 1 且发生在批次收尾之后，是 / 否。
- **同一交付目录串行推进**：一个交付目录按「全部写入完成 → 转存 `docs/` → 最后一次镜像」单向推进；缺口表同一轮的多条发现攒批一次改表、一次提交。核对：是否只做一次转存与一次镜像、缺口表是否一轮只改一次提交一次，是 / 否。
- **不复用长会话**：每个批次或新目标另开新会话，任务书只带必要上下文、文件路径与验收口径，做完即结束；同一交付物的后续修正可以留在原会话。
- **输入精简**：不整份读入大文档（缺口表、权威清单、审计报告等），先用检索定位行段再读；不重复粘贴 `git status` 全文，只报与本次相关的条目数；批量信息脚本汇总后只读汇总结果。

## 审计、迁移与周期任务编排

- **N3 同一对象 24 小时一次性**：同一审计对象 24 小时内只允许一个会话定性；后续会话只引用前一会话的结论与哈希，不重做取证（与 `data-governance-detail.md` DG-36 ④ 同一口径）。
- **N5 迁移先建映射表**：先落 old→new 路径映射表再批量执行；引用扫描按 basename 一次 `grep` 完成，禁止逐件全仓搜索。
- **N7 周期任务模板化**：日更 / 巡检 / 镜像各一条固定命令入口，输出单行状态；禁止拆成多会话逐步执行。
- **N9 规则类任务执行口径**：规则文件改动一次给全量条文、按整节覆盖写；判定覆盖用脚本做差集（改前抽编号与关键词，改后逐条命中检查，只报未命中项）；末尾一次核对字节数；机制验证用两个最小探针，禁止逐条 Edit 后紧跟校验。
- **N9 附：差集粒度**：按「动词 + 对象」关键词比对，禁用 4-gram 等字符 n-gram——压缩后的同义句会被成批判为未命中（2026-11-13 规则拆分 9a9526c，163 条中初筛 11 条误报、又花一轮逐条断言）；未命中项一次锚点断言即收口，不再开二轮复核。
