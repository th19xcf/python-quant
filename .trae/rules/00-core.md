# 00 核心规则（常驻）

> 本文件与 `99-index.md` 常驻；其余按索引开工前 Read，冲突以本文件为准。判例见 `docs/数据治理判例与基线_2026-11-13.md`。

## 一、数据与历史安全规则（红线，原文逐字）

- **数据目录禁止删除**：`data/`、`data/local_store/**`（含 parquet、meta、raw、断点缓存、`_backup`）一律不得删除、清空、或"删除后重建"。只允许追加、覆盖单文件、增量补齐。
- **备份目录禁止清空**：`G:\git\python-quant` 只做增量同步（copy2 单文件、删除仅限源仓库已删的对应文件）。禁止 `rmtree`、禁止删整个目录、禁止碰它的 `.git`。
- **Git 历史只增不重写**：禁止 `git reset --hard`、`git filter-branch`、`git rebase` 改写已提交历史、`git push --force`。需要"收拢历史"时，必须保留旧历史（tag 或备份分支）并把方案先报给用户。
- **禁止批量清理工作区**：禁止 `git clean -fdx`、禁止对未跟踪文件做批量删除。工作区里的 `M`/`??` 可能是其它任务的在途成果，清理等于销毁他人工作。
- **用户口头要求上述操作也不直接执行**：即使用户当次要求"删本地数据 / 覆盖备份 / 重置历史"，也必须先把影响面（涉及路径、行数、不可恢复性、下游依赖）报给用户，并给出不丢数据的替代方案；仅在用户对该次具体路径再次明确确认后才可动手，且**删除 `data/` 任何内容需用户点名到具体文件或子目录**。
- **不确定就停手**：任何会影响项目可运行性、数据完整性或历史可回溯性的操作，一律先停下来报告，不得"先做了再说"。

## 二、决策授权规则（带建议即执行）

- **决策点必须自带建议（硬判定）**：待决定事项必须同时给出「选项 / 我的推荐 / 推荐理由 / 不做会怎样」四项，缺一项即视为未完成沟通，不得只抛问题；极简汇报可省过程与证据，但不能省「我建议选哪个」；判不出推荐时必须写明缺哪条证据、补它要做什么，不得以「请你决定」收尾。
- **按建议直接执行，不等确认**（用户已给结论时按结论执行、不重复劝说）：事后写清「已按建议 X 执行、理由 Y、可回滚 Z」，供事后复核而非事前放行。三类必须停下等用户：① 红线——删除 `data/` 内容、清空或覆盖备份目录、重写 Git 历史、批量清理工作区；② 外部条件不具备——源端无数据、限流封禁、需账号 / token、需用户先更新本地源文件；③ 改既定口径或结论含义且无实测证据——放宽断言、下调阈值、删除用例、改 `strict` 口径等。
- **红线类即使给了建议也不自动执行**：红线操作仍须报影响面（路径、行数、不可恢复性、下游依赖）与不丢数据替代方案，用户点名到具体路径后才动手；只覆盖可逆、有备份、可回滚、有验收证据的操作，不可逆或无法实测的按「不确定就停手」。
- **被授权事项照样记账**：汇报单列「本次自行决定并执行的事」，写清依据与回滚方式，供事后追认或推翻。
- **派活前必看三行**：① 今天同一文件族（`.trae/rules`、`tools/`、`docs/`、`data/` 等）是否已有会话？有则发进该会话，不新开；② 同一交付物今天是否已产出过？有则就地更新，不另起文件；③ 跨天不合并。

## 三、提交纪律

- **提交流程与报告格式**：提交前必读 `git-backup.md`（免确认、5 块报告、备份、备份仓）。
- **Commit message 必须中文**：标题与正文统一中文，仅类型前缀（feat/fix/refactor/perf/chore 等）与 scope 为英文，格式 `type(scope): 中文描述`；标题与正文之间、正文各条目之间不得有空行，条目紧接标题下一行连续书写，禁止 `git commit -m "标题\n\n正文"`。
- **Commit message 文件必须无 BOM**：禁用 PowerShell 5.1 `Set-Content -Encoding utf8`（带 BOM，`git commit -F` / `stripspace` 不清理）；用 `.venv\Scripts\python.exe` 以 `open(p,'w',encoding='utf-8',newline='\n')` 写临时文件后 `git commit -F`，无 Python 时用 `UTF8Encoding($false)`；提交前自检首 3 字节不为 `EF BB BF`。
- **提交范围必须自证**：多出文件立即回退重做，不得事后补「混入了」了事；同文件并行编辑按 `task-scheduling.md` 三条。
- **隔离索引回填**（`GIT_INDEX_FILE` 提交的同一轮必须执行 `git read-tree HEAD`，缺此步即判该次提交未完成）：① 在**新的一条** shell 命令里执行（`GIT_INDEX_FILE` 是同进程环境变量，同命令里回填的是临时索引）；② `git status --short` 不再出现与本次提交无关的 `MM`。`ls-files` + `rev-parse` 双查已取消。见判例 §2.1。
- **隔离索引五步**（种子化、基准取提交时刻父提交、变更文件数核对、`before != after` 整体重做、提交后清单自证）：细则见 `git-backup.md`；打断即整体重做，不得续跑。
- **提交前清点共享暂存、提交后复核清单**：细则见 `git-backup.md`。

## 四、上下文与 token 成本规则

- **汇报只回结果**：只给结论与必要数字，不展开过程、不复述全文，细节留在文件里。
- **子会话回报上限**（冲突以本条为准）：单条只写「做了什么 / 关键数字 / 下一步 / 阻塞」四项、≤5 行；提交后只回一行「已入库推送 + 短哈希」。**5 块模板与提交明细表默认不输出**（不写 `docs/evidence/<主题>/commits.md`），仅点名时生成。核对：是否只在点名时产出 5 块（两侧皆无默认产出），是 / 否。
- **同一环境异常只上报一次**：同一环境异常（锁文件被回收、权限被拒等）全程只报一次并在汇报同处登记为已知现象。核对：是否只报一次且已登记，是 / 否。
- **报告与附带产物默认不产出**：默认不写报告与 CSV/明细表/样本清单；确需写时每任务 ≤1 份、≤200 行，仅限「改正式数据」「改既定口径」；数值证据用条数 + 极值/分位 + 可复现命令代替落盘；同类文件就地更新；单一交付报告就地改原段落，禁止「更正小节 / 追加说明 / 补遗」二次成文。同一交付物（看板、报告、页面）一天内只允许重排版一次，版式与数据源版本清单先定再写渲染。核对：本轮是否零产物或符合上限，是 / 否。
- **编排 4 条**：见 `task-scheduling.md`。
- **校验与盘点的默认做法**：
  1. **收尾校验不抽样**（取代「全库 check + 抽样 50 件」）：本次改动逐件核 `rows`/`bytes`/`sha256` 与 manifest 一致；同级 manifest 汇总对账（顶层 `rows`/`bytes` = 各侧车之和，差额 0）；mtime 反查只能挑候选，判「缺失」须同时满足「源侧存在 + 目标侧不存在」；多出须为 0，不为 0 只报不修。
  2. **镜像与备份比对用 rsync 式增量**：大小 + mtime 相同即跳过哈希；集合差与哈希必须绑定同一份相对路径快照；禁止整树逐文件 SHA256 双向比对。
  3. **全库盘点用「上次基线 + 增量」**：基线文件须记录生成时的 HEAD 与输入集合哈希；禁止每轮重扫全库。
  4. **同一批数据只跑一次**：dry-run 一次 + apply 一次；「补一批 → 复跑 → 再补」仍属违规，禁止 sync / verify 两轮互证。
  5. **端到端读取只抽 1~2 条真实路径**：禁止每层都验；迁移 / 归位类必须做全量路径级集合差，只有内容对拍可抽。
  6. **同一逻辑闭合的改动合并为一次提交 + 一次备份**，禁用每步一提交（红线与不可逆仍即时处理）；DG-35 基础表仍单独成一次提交，但内部「改 → 对拍 → 回填 → 重建」一次走完。
- **长任务必审**：预计 ≥10 分钟或 token 高的子任务（采集、盘点、整表重建、批量对拍、镜像），完成后必须审计一次，产出「token 花在哪 + 可复用的压缩规则」。审计低成本：不读工具输出、不读代码、不重跑命令，只用回合数与工具调用计数、每会话 ≤2 轮；结论 ≤15 行、不写报告文件。同类开销第二次出现即落成规则条目，不再复盘。
- **压缩不降证据**：以上六条与长任务必审只替换校验与盘点方法；压缩只作用于汇报文本与附带产物，DG-20 四项与 DG-31 兜底一条不减。核对：四项与兜底是否全量存在，是 / 否。

## 五、DG-35 基础表必须一次改完

- **DG-35** **基础表必须一次改完**：行情、名录、财报、估值、因子、日历、事件这七类基础表的任何改动，必须先穷举该表全部已知待修项，再一次性执行「改动 → 逐值对拍 → 回填索引与 manifest → 重建受影响的下游派生表」；禁止「改几行 → 重建派生 → 再改几行 → 再重建」的反复循环（多轮重建互相覆盖漂移）；同一张基础表禁止两路任务并行写。
  - 改动前列出下游派生清单（表 / 列级），按「源表 → 派生 → 索引与 manifest → 验证」单向推进，禁止边改边重建。
  - 与 DG-10 / DG-11 不冲突时同时适用（分别管跨文件非事务、替换前备份）；冲突时以本条为准，不得用「分批提交 = 多次事务」绕过一次性要求。依据：用户 2026-11-13「基础表要一次处理完毕，不要反复互相影响」。
