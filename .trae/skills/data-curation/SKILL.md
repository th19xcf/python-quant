# data-curation：数据治理六阶段

本技能只写**怎么做**。判定红线（禁止项、必须项、证据门槛）见 `.trae/rules/00-core.md` 与 `.trae/rules/data-governance-detail.md`，出现冲突以规则层为准。
涉及提交、备份同步、并发调度、超时处理时，按 `.trae/rules/00-core.md`、`.trae/rules/git-backup.md`、`.trae/rules/task-scheduling.md` 对应章节执行，本技能不重复。

## 适用场景

- 某类数据有缺口、有脏值、有重复键，需要补齐或修正
- 派生表重建（因子、估值、财务、事件、指数成分等），需要从 staging 换到正式路径
- 发现新旧两套数据并存，需要收敛为唯一正式路径
- 被问到「这份数据能不能用」「和库里差异怎么解释」

## 不适用场景

- 只读核查、只出报告、不动数据 → 直接按规则层做只读核查，不要进第五、六阶段
- 纯取数、画图、回测、推荐生成 → 走业务链路，本技能不介入
- 修改代码逻辑而非数据内容 → 走普通开发流程；但若改动会影响取数路径（正式路径常量、开关默认值），必须先回到本技能第一阶段确认影响面

## 第零步：先定档（30 秒判断）

| 现状 | 走哪条路 |
|---|---|
| 缺口在正式路径、有已验证本地源 | 完整六阶段 |
| 只有候选数据在 `_staging/`，未验收 | 从第五阶段开始，禁止跳步直接替换 |
| 正式文件已是新内容，但没证据 | 补第五阶段对拍，对拍不通过则按第六阶段回滚 |
| 两套路径并存、不知道谁在用 | 回第一阶段，先把读取方列全，禁止猜 |
| 只是想知道差异原因 | 只做第二、三阶段，产出「差异归因」，不写盘 |

## 第一阶段：缺口定位

先回答三个问题，答案必须落到文件与行号。

1. **谁在读**：先看 `docs/数据权威路径清单.md` 是否已登记该语义及其消费者；再用 `Grep` 查路径常量与调用方（如 `data/local_store/`、`local_store.paths`、`default_store_root`）；契约类缺口跑 `python -m src.data.quality.extended_contracts --json`，看 `ready` / `missing` / `partial`。
2. **缺什么**：按 (数据集, 字段, 时间区间, 标的) 量化，给出缺失行数、缺失只数、null 率，而不是「有一部分缺」。
3. **影响面**：列出会被这批数据影响的结论（回测区间、因子、推荐、报告数字），并写明「若不补，哪个结论不能下」。

**验收证据**

- [ ] 缺口统计表：数据集 / 字段 / 区间 / 缺失行数 / 缺失只数 / null 率
- [ ] 读取方清单：`文件:行号` 逐条列出，包含间接读取（缓存层、派生表、UI）
- [ ] 影响面一句话结论：不补会导致哪个既有结论失效

**停手条件**：读取方列不全，或发现同一语义有两个读入口。

---

## 第二阶段：来源与校验状态判定

对每个候选源打一档，档位决定它能做什么，不能做什么。

| 档位 | 判定标准 | 允许用途 |
|---|---|---|
| A 有对拍 | 已与独立第二源逐值比对通过，记录了样本量、容差、差异项归因 | 可作为判定「值对不对」的依据 |
| B 仅自洽 | 只有内部一致性证据（行数、日期连续、价格台阶、首末行吻合） | 只能证明「没坏」，不能证明「对」 |
| C 完全未校验 | 接口直出、手工粘贴、单次抓取未复核 | 不得写入正式路径 |

判定要点：

- 同一源不同字段可能不同档，必须按字段分别标注（例如价格 A 档、估值 C 档）
- 远程库默认不是 A 档：库内数据未经校验，只能解释差异来源（DG-15）
- 本地 `pre_close` 若由因子派生，与事件表同源，不构成独立旁证；独立旁证只认 TDX `.day` 原始收盘价台阶、股本表增幅、外部公告

**验收证据**

- [ ] 来源档位表：字段 → 源 → 档位 → 档位依据（命令或报告路径）
- [ ] C 档源清单，以及「本次不使用它」的明确说明

**停手条件**：唯一可选源是 C 档，且无法补出对拍证据。

---

## 第三阶段：权威源选型

选型顺序固定，越靠前越优先：

1. 本地已验证源：TDX `.day`、已归档快照、公告与退市证据、名称快照
2. 有对拍证据的远程源（A 档）
3. 仅自洽的远程源（B 档），且只能用于填空，不用于改既有值

选型时必须写清三件事：覆盖区间够不够、粒度对不对（日频 / 月频 / 事件级）、有没有独立第二源。三者缺一，就在汇报里标明「该字段只能到 B 档」。

推不出的字段处理：留空 + 逐列写明「为什么推不出、缺哪条证据」，禁止从库里抄一个值凑齐（DG-16）。

**验收证据**

- [ ] 选型表：字段 → 选定源 → 档位 → 覆盖区间 → 粒度 → 未选其它源的理由
- [ ] 留空字段清单及逐列依据

**停手条件**：需要把推导管径改成外部源，或需要放宽容差才能对齐（属 DG-29 的「改变口径」）。

## 第四阶段：staging 构建

目标：不动正式文件，产出一份可验收的候选。

- 目录：`_staging/<任务>_<YYYYMMDD>/`（**仓库根**，不在 `data/` 之下；权威常量见 `src/data/staging.py` 的 `STAGING_ROOT` / `staging_dir()`），任务名用英文短标识（先例：`backfill_20190917`、`research_rebuild_20261109`）
- 写盘：单文件一律 `src/data/atomic_write.py` 的 `write_parquet_atomic` / `write_text_atomic`
- 断点：按 DG-7 三条判定（预计 ≥10 分钟 + 跨运行续跑 + 含外部采集）时，每完成一只 / 一块就落 `progress.csv` 或 `progress.json`；失败项落 `failed.csv`，含原因；改前备份与 SHA256 台账任何任务都不得省
- 分片：保留逐只或逐块 parquet，便于局部重跑；不要只留一个合并后的大文件
- 采集：串行与节流口径见 `task-scheduling.md`「网络采集限流」条，本文不重复；数据侧只补一条：返回空先区分「源端没有」与「链路未接线」
- 来源标记：外部来源的字段必须逐字段标记（先例：`source` 列写成 `pe=<来源>|pb=<来源>|...`）

**验收证据**

- [ ] staging 目录树清单（文件数、总行数）
- [ ] 进度文件计数：ok / failed / skipped，三者之和等于任务总标的数
- [ ] 断点复跑证据：中断后重跑，已完成项不重写（新增行数为 0 或只补未完成项）
- [ ] 正式路径文件 SHA256 在构建前后未变

**停手条件**：需要写正式目录才能继续；或采集被限流且无法降速解决。

## 第五阶段：对拍验收

五类检查全过才算通过，任何一类不通过禁止进入替换。

对拍前先确认字段的消费路径：`Grep` 消费方实际读取的列与表达式（如 `cash_div_fix.fill_null(cash_div)`、覆盖层、有效层派生），以那一层作为对拍对象；同一字段有原始层与修正层时，两层分别出结论，只比原始列不得判定「哪边错」（DG-30）。

| 类别 | 具体做法 | 通过标准 |
|---|---|---|
| 行数 | 候选行数 vs 上游应有行数；新增行数 vs 预期新增 | 守恒，差额可逐项归因 |
| 键 | `(ts_code, trade_date)` 唯一；日期严格递增；无重复键 | 重复数 = 0 |
| 逐值 | 与正式文件按键对齐比较；既有非空值逐列比对 | 既有非空值改动数 = 0（除非本次授权改该字段） |
| 抽样 | 随机 30 只 + 边界样本（首日 / 末日 / 除权日 / 停牌前后） | 逐值一致，容差写明（如 `pre_close` ≤ 1e-4） |
| 下游 | 用真实读路径端到端跑一次，确认读到新内容 | 读到新文件，且结论字段随之变化 |

空值语义必须单独查，不能只看行数：

- parquet 的 null 与 NaN 是两回事，`is_null()` 判不出 NaN
- 对数值列同时跑 `is_null().sum()` 与 `is_nan().sum()`，两者与预期都要对得上
- 用 numpy 数组回填会悄悄把 null 变成 NaN，写入时必须带内联断言
- 改动前后分别统计目标列 null 数，未命中映射的行必须保持原值；「空值从 0 变成 N」必须让断言失败，不允许用 null 参与会静默为假的比较（DG-31）

**验收证据**

- [ ] 字段消费路径清单：字段 → 消费方 `文件:行号` → 实际读取的层（原始列 / 修正层 / 有效层）
- [ ] 空值计数对比：改动前 / 改动后各目标列 null 数，未命中映射的行未被写成 null
- [ ] 五类检查各自的命令与输出（数字必须落地，不接受「符合预期」）
- [ ] 容差与样本清单
- [ ] 差异归因表：每一处非零差异对应到一条可核实的原因

**停手条件**：出现无法归因的差异；或为了让对拍通过而想放宽容差。

## 第六阶段：替换与记账

顺序不可颠倒，替换前一步没做完不进下一步。

1. 备份：把将被覆盖的正式文件 `copy2` 到 `logs/<任务>_<日期>/` 或 `_backup/<语义>_<日期>/`，记录旧 SHA256
2. 退役旧表：若整表被取代，把旧目录整体**移动**进 `_backup/`，给移动前后 SHA256 一致证明（DG-13）
3. 替换：用 `write_parquet_atomic` 落正式路径，禁止直接覆盖
4. 清理候选：删除本次 `_staging/<任务>_<日期>/`（仓库根，仅限本次任务目录；`_staging` 根本身保留）
5. 记账：写同目录 `manifest.json`，至少含 `version`、`status`、口径哈希（`codes_hash` 一类）、上游 mtime、行数、只数、`updated_at`
6. 登记路径：在 `docs/数据权威路径清单.md` 登记「语义 / 唯一正式路径 / 消费者 / 为什么是它」，被取代的旧路径写进「已废弃路径」表（含移入位置与 SHA256）；不可重建资产同步进 `tools/backup_critical_assets.py` 的 `CRITICAL_FILES` / `CRITICAL_DIRS`，外部依赖数据同步进 `extended_contracts.py` 契约
7. 汇报：改了哪些文件、哪些行、哪些标的、新旧 SHA256、验收结论、回滚命令

替换后必须再跑一次下游端到端，确认读到的确实是新文件，而不是命中旧缓存。

**验收证据**

- [ ] 替换前后行数 / 只数 / SHA256 对照表
- [ ] `manifest.json` 字段齐全，路径不带版本号
- [ ] 下游端到端复跑成功，输出中可见新数值
- [ ] 回滚命令一行可执行，且备份文件存在

**停手条件**：需要删除的目录不是本次 `_staging/` 任务目录；或替换后下游读数与预期不一致。

> 2026-11-10 起 `_staging/` 已迁出 `data/`（原 `data/local_store/_staging/` 不再使用），因此「删除本次 `_staging/<任务>/`」不再需要 `data/` 的删除例外——`data/` 恢复为一律不删（DG-8 已整条取消）。

## 全流程停手条件

判定口径与 DG-29 一致（三类：不可逆操作、外部条件不具备、改口径且无实测证据），这里只列数据侧的具体触发信号。出现以下任一，先报不先做：

- 需要删除 `data/` 下任何内容（`data/` 已无任何删除例外，staging 也已不在其中）
- 需要改写 Git 历史、清空或覆盖备份目录、批量清理工作区
- 源端无数据 / 限流 / 封禁 / 无权限，且降速无法解决
- 需要改变口径：把推导换成外部源、调 `strict` 名单、改复权口径、放宽容差、改准入阈值
- 对拍出现无法归因的差异
- 同一语义存在两套正式路径且无法确认哪套在用

## 反模式清单（本项目实际踩过）

1. **用 numpy 数组回填导致 null 变 NaN**
   现象：写完后 `is_null()` 查不出空，下游把 NaN 当有效值参与计算。
   正确：用 polars 写入并在写盘前加内联断言，验收时同时查 `is_null` 与 `is_nan`。
   出处：2026-11-10 `valuation_daily` 补写，发现后重新校验并全量比对才收口。

2. **`unique()` 未加 `maintain_order=True` 破坏幂等**
   现象：同样输入重复导入，新增行数与首次不同，行序漂移。
   正确：去重显式加 `maintain_order=True`，并补一个「重复执行新增行数为 0」的断言。
   出处：2026-11-09 事件表补录，行数从 119,915 涨到 122,883 后发现，修复后重导为 121,157 行。

3. **并发 `git commit` 撞共享 index**
   现象：自己只 add 了 A 文件，提交里却混进他人 B 文件。
   正确：提交前确认无人正在提交；无法确认时用 `GIT_INDEX_FILE` 指向临时索引，并在报告中写明。
   依据：`task-scheduling.md`「同一仓库提交必须串行」。

4. **按 mtime 或「今天」筛选备份**
   现象：历史文件永久缺席，越备越少，且每次都「看起来成功」。
   正确：按相对路径集合求差，补齐差额后逐文件 SHA256 比对。
   依据：实测缺口数字与判定见 `data-governance-detail.md` DG-28。

5. **先提交后验证**
   现象：HEAD 里已有未验证数据，回滚要动 Git 历史，成本翻倍。
   正确：对拍全部通过 → staging 替换正式 → 下游复跑 → 才允许提交。

6. **把「未接线」误判成「无数据」**
   现象：取数为空就下结论「这个标的没有数据」，实际是路径常量写错、开关默认关闭或时间范围错。
   正确：先查路径、开关（如 `data.allow_remote_sources`）、时间范围、表清单，再判定缺失。
   依据：`extended_contracts.py` 记录过「没数据 ⇒ 约束不生效，结论看起来正常」的系统性偏差。

7. **候选文件留在正式目录**
   现象：`*_candidate.parquet`、`*.new` 留在正式目录，下一次取数按通配命中半成品。
   正确：候选只放仓库根 `_staging/`，验收后删目录（DG-5、DG-6）。

8. **用库与本地差异反推「本地错了」**
   现象：一看到库里数不一样就改本地，结果把正确值改成错误值。
   正确：先按第二阶段定档，库只能解释差异来源，不能当标尺（DG-15、DG-17）。
